# 記録の移し方

作業の終わりに、成果物（spec・research・plan）から残す内容を移すときに読む。要約は SKILL.md「記録の移し方」にある。

`.tmp/sessions/` の成果物は 7 日で消える。spec・research・plan は commit しない。残す価値のある節だけを恒久の文書へ移す。移さなかった内容は、消えた後は戻らない。

## 移す節と行き先

| 元       | 節                                                                                                                                      | 行き先                               |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| spec     | Key Decisions、Alternative Approaches の却下した案、Risks、提供しない体験                                                               | ADR の Decision / Consequences       |
| research | 決定を支える数値（測った条件と一緒に）と事実                                                                                            | ADR の Context                       |
| plan     | 計画から外れた点、実装中に分かったこと                                                                                                  | 下の振り分けの表で中身ごとに決める   |
| どれでも | 範囲の外として次に回した課題                                                                                                            | `docs/plans/` の持ち越した課題の一覧 |
| 移さない | Tasks、Files、テストケース、Reviewer Outputs、Approval、Scope、検証の手順と出力、試しの記録、計画や spec からの差の経過、レビューの経過 | 残さない                             |

計画から外れた点と実装中に分かったことは、中身でこの表に当てる。上の表のどの行にも該当しない内容も、この表に当てる。

| 中身                                                                                         | 行き先                                                         |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 決定そのものが変わった                                                                       | ADR の Amendments（変えた後の決定は Decision に反映する）      |
| 計画との差のうち、決定の帰結として残る制約や限界（再検討するときに知らないと判断を誤るもの） | ADR の Consequences に 1〜3 行。差が生じた経過は書かない       |
| plan に無かった小さな判断                                                                    | その判断をした commit の本文（`decision:` / `rejected:` の行） |
| コードを読むと浮かぶ「なぜこうしないか」                                                     | そのコードのコメント                                           |
| 終わらなかったこと、後で確かめること                                                         | `docs/plans/`                                                  |
| 作業の経過（レビューの周回、試行錯誤、計画との差の物語）                                     | 残さない                                                       |

単層モードの `plan.md` は spec と plan を兼ねるので、spec の行と plan の行の両方を当てる。

## ADR に書くもの

ADR の `##` 見出しは、Status、Context、Decision、却下した代替案、Consequences、Amendments、References の 7 つに限る。`###` 以下は自由に使ってよい。Status、Context、Decision は必ず書く。

| 見出し         | 書くもの                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| Status         | 状態。他の ADR に改められたら、そのことを 1〜2 行のポインタで書く                                               |
| Context        | 決定を必要にした力学。数値は結論を支えるものだけを、測った条件（版・対象）と一緒に書く                          |
| Decision       | 決定と、その場で読むのに要る理由。決定の ID（K1 など）は振り直さない                                            |
| 却下した代替案 | 1 案につき 1〜3 行で、案と却下した理由                                                                          |
| Consequences   | 受け入れたトレードオフ、限界、再検討の条件。リスクの ID（R1 など）はここに置き、振り直さない                    |
| Amendments     | 決定を変えた日付と理由を 1 件 3〜5 行で。変えた後の決定は Decision に反映し、後の改訂に置き換えられた改訂は消す |
| References     | 他の ADR と外部の資料。実装のファイルとテストは並べない                                                         |

書かないもの:

- 検証の手順と出力、試しの記録、計測の内訳の表
- 関数名、定数、行番号、テスト名のコピー（コードとテストが原本）
- 作業の経過（計画や spec からの差の経過、レビューの周回）
- 未対応の課題（`docs/plans/` に置く）
- 操作の手順。他の決定やリスクが手順を要求するときは、利用者向けの文書に置き、ADR からはそこを指す
- 作業用ディレクトリのパス、既定のブランチから辿れない commit、PR の番号

見出し、作業用ディレクトリのパス、ADR への行番号の参照、ソースへの行番号の参照、存在しないパスは、リポジトリのテストが機械で検査する。それ以外は、この基準と記録を移すタスクのレビューで守る。

ADR を書かない作業では、表の「ADR の…」を「commit の本文」と読み替える。ADR も commit の本文の慣習も持たないプロジェクトでは、そのプロジェクトの記録の慣習に従う。

## 最後のタスクの書き方

移す作業は、計画の最後のタスクにする。単層モードでは `plan.md` の、二層モードでは最後に実行する `plan-N.md` の最後のタスクである。移す先の文書は、その計画の Files に載せる。

そのタスクの commit の本文に、次の 2 つを書く。

- 原本（spec・research・plan）の `##` 見出しの一覧
- 表の「移さない」以外の各行について、「移した先の文書と節」または「該当なし」。plan の行は、振り分けの表の行き先ごとに書く

表の「移さない」の行は書かない。原本があるうちに行う。抜けに気づいて原本から拾い直せるのは、成果物が消えるまでの 7 日の間だけである。

workflow dir に `followups/` があれば、中のファイルを、名前を変えずに `docs/plans/` へ移す。表の「範囲の外として次に回した課題」の行の行き先に、移したファイルを書く。

移して commit した後、次の Document Workflow を同じセッションで始めるときは、`workflow-cli reset` で wfDir 直下を `archive/<日時>/` へ退避する。手順は [escape.md](escape.md)（dry-run の出力を AskUserQuestion で見せ、承諾後に `--confirm` で実行する）。`followups/` にファイルが残っていると reset は拒否するので、先に `docs/plans/` へ移す。`/clear` で新しいセッションにするなら reset は要らない。

## 残件を書く時点

残件は、今の作業では扱わないと決めた課題である。やり残し、作業中の発見や着想、使ってみて分かった違和感の 3 種類がある。

残件が応答に出たら、応答を閉じる前にファイルに書き、書いた先を知らせる。自分が書いた残件にも、利用者が挙げた残件にも当てる。保存の前に利用者へ聞かない。最後のタスクを終えた後の報告と会話にも当てる。

- 今の作業の判定基準を満たすのに要る内容は、残件ではない。今の作業で扱う。計画の変更が要るなら、計画を改めて承認を得る。計画の無い作業では、元の依頼を満たすのに要るかで分ける。作業を終えた後に見つかった欠けは、残件として書く。
- それ以外は、先に書いて知らせる。今やる方がよいと考えるときだけ、知らせに理由を添えて勧める。そう考えないなら、今やることを提案しない。利用者が今やると言えば、書いたファイルか項目が作業の出発点になり、その作業の最後の commit で消す。
- 利用者が言っていない課題を挙げるときは、冒頭に「提案・未決」と書く。
- その項目だけで 1 つの計画になる論点は、出発点のファイルにする。終わった作業に付く小さな課題は、`<主題>-followups.md` の項目にする。同じ主題のファイルが既にあれば、そこへ足す。
- 以前の作業を使ってみて分かった違和感は、その作業の `<主題>-followups.md` に足す。どの作業か分からなければ、出発点のファイルにする。
- Document Workflow の計画の承認前は `docs/plans/` に書けない。その間は workflow dir の `followups/` に、`docs/plans/` に置くときと同じ名前と形で書く。最後のタスクが、名前を変えずに `docs/plans/` へ移す。承認に至らずに作業をやめるときは、やめる前に移す（workflow dir は 7 日で消える）。
- ファイルに書くことと commit は別である。commit は、その作業の commit に含めるか、利用者の依頼に従う。
- 置き場の慣習が別にあるプロジェクトでは、`docs/plans/` をその置き場に読み替える。

## `docs/plans/` に置くもの

`docs/plans/` には、今後やりたいことだけを置く。作業中の成果物と、終わった作業の成果物は置かない。

- **持ち越した課題の一覧**（`<主題>-followups.md`）: 終わった作業が範囲の外に回した課題を並べる。片付いた項目は消し、空になったらファイルを消す。項目を消す commit の本文に、消した項目の名前を書く。
- **未着手の作業の出発点**（主題の名前だけのファイル。冒頭に「未着手」と書く）: 調査、未解決の設計判断、次のセッションの起動プロンプトなど。その作業が終わったら、上の表に従って節を移し、最後のタスクと同じ commit でファイルを消す。

## 作業ツリーに無い記録の指し方

過去の記録が作業ツリーに無いときは、そのまま実行できるコマンドをバッククォートで囲んで書く。

```
`git show <commit>:<path>`
```

`<commit>` は 10 桁以上の hash で、既定のブランチから辿れるものに限る。書く前に `git merge-base --is-ancestor <commit> <既定のブランチ>` の終了コード 0 で確かめる。ファイルを指せば内容が、ディレクトリを指せば配下の一覧が返る。
