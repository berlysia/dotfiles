# 人が読む文書の必須検査

## 適用範囲

人が読むことを目的にする日本語の文書は、作成・改稿のたびに japanese-check で検査する。公開文書、社内文書、自分用のメモ、下書き、記事、README、仕様書、手順書、議事録、PR・Issue・commit の本文、メール、スライドを含む。公開・非公開、保存先、ファイル形式、長さ、スキルの指定は適用を外す理由にしない。

通常の会話、短い質問への回答、作業の進捗・完了報告は対象外。ただし、チャットで文書の本文を納品する場合は対象に含む。機械だけが読むコード・設定・データ・エージェント専用指示と、Document Workflow の成果物（workflow dir の research・spec・plan）は対象外。人向けの解説を兼ねる文書は対象とする。日本語を含む文書では日本語の部分を点検する。

これはどの入口スキルを使うかとは独立した必須手順である。yomiyasu 全体を自動起動したり、koncise や japanese-tech-writing の構成・文体の決まりを変更したりはしない。

## 実行手順

1. 改稿では、編集を始める前に原文を作業用の一時ディレクトリに保存する。原文と最終稿は別ファイルにする。Git の HEAD を原文の代わりにしない。既に原文の写しがあればそれを引き継ぐ。
2. 文書を書く。ファイルを作らずに納品する本文も、検査用の一時ファイルへ写す。Word・PDF・HTML・スライドなどは、実際に提出する文書の見出し・本文・表・図の説明からテキストを取り出し、読み順を保った Markdown にする。元の文書を別物として書き直した検査用テキストは使わない。
3. 次の check を実行し、表現・直訳候補・構成・用語・新出事実を確認する。指摘を機械的に全部直さず、正式名称、定着した用法、引用、条件の保持などの理由があれば残す。主体・動作・対象が不明でも推測で補わず、原文と資料の範囲で直す。
4. 本文を直した場合や、他の校正・textlint・yomiyasu の検査で本文が変わった場合は、すべての修正後に check をもう1回実行する。最終の本文と検査した本文を一致させる。check は合計2回まで。2回目の候補は、理由を付けて残せるものだけを残し、修正が必要なら未完了の草稿として返す。
5. 原文か資料と読み比べ、事実・条件・否定・確度を保ったことを確認する。検出ゼロでもこの照合を省かない。残す候補には文脈上の理由を付け、check の出力の hash を使って review を実行する。検査結果と判断の理由は文書の外の作業報告へまとめる。本文だけを返す指定がある場合も検査と判断の記録は省略せず、検証済みの本文だけを返す。

```bash
node ~/.claude/japanese-check/cli.ts check <提出する本文.md> --genre tech
node ~/.claude/japanese-check/cli.ts check <最終稿.md> --source <原文の写し.md>
node ~/.claude/japanese-check/cli.ts review <最終稿.md> --hash <出力のhash> --reason <残した各候補の理由>
node ~/.claude/japanese-check/cli.ts verify <最終稿.md>
```

Codex からも同じ CLI を呼ぶ。`--genre` は tech、business、essay から実際の用途で選び、決まらなければ省く。出力は常に JSON。個別の lint コマンドだけでは形態素解析を使う直訳候補を検査できないため、必須手順の代わりにしない。

## 既存の検査と重ねる場合

tanteki／yomiyasu の検査に組み込まれた check を、上の1回目として数える。同じ本文に独立した check を重複実行しない。最終稿が変わったときの2回目も、この手順の回数に含める。textlint と yomiyasu の run／verify の回数は増やさない。check のあとに本文を直して最終稿が変わったら、検査の残り回数で最終稿を確認できるまで完成扱いにしない。

検査用の原文・本文・抽出テキストは `mktemp -d` で作った作業ツリー外のディレクトリに置き、持ち主だけが読める権限にする。本文や検査結果の全文を新たにプロジェクトへ保存しない。既存の記録禁止・秘密の扱いを守る。ファイル保存を利用者が禁止している場合は写しを作らず、検査を実行できない理由を返す。

## 自動追跡と検査記録

Claude と Codex のフックは、ファイルの編集後に日本語の Markdown・テキスト・HTML と、Word・PDF・スライドを追跡する。Bash で書いたファイルは、1 回の呼び出しの前後で Git の一覧と各ファイルの内容を比べ、その間に現れたか変わったものだけを追跡に加える。呼び出しの前から未コミットだった変更は、その呼び出しが変えていなければ加えない。エージェント専用の AGENTS.md、CLAUDE.md、SKILL.md と、workflow dir（`.tmp/sessions/` の下）の文書は自動追跡しない。workflow dir の文書も、CLI の check を手で実行すれば検査して記録できる。

追跡済みの文書は、終了前に最新の検査記録があるかを確認する。未検査、検査後に変わった本文、判断が記録されていない候補があれば、終了を止めて不足する手順を返す。毎回の編集で Sudachi を起動するのではなく、check の記録を照合する。

check は `~/.claude/state/japanese-check/` に本文のハッシュ・検査器のハッシュ・候補数を記録する。置き場はリポジトリの外にあり、使う前に symlink でないこと、所有者が自分であることを確かめる。7 日以上使われていないセッションの状態は終了時に消える。review は残す理由を記録する。原文と最終稿の全文は保存しない。記録は検査した内容にだけ有効で、本文・成果物・検査器のいずれかが変われば無効になる。`--no-record` は検査記録を残さない指定であり、終了前の機械確認を通したことにはならない。

Word・PDF・スライドは、抽出テキストへの check に `--artifact <実際の成果物>` を付ける。成果物のバイト列にも記録を結び付け、抽出後の差し替えを検知する。抽出の正しさはエージェントが確認する。チャットで納品する本文や自動追跡できない文書は、フックに示されたセッション ID を使い `track <文書> --session <ID>` で登録する。check に同じ `--session` を付けてもよい。

検査できない草稿には、`defer <文書> --hash <hash> --reason <理由>` を使う。日本語を含まない成果物など、適用外と確認した場合は `exclude` に同じ引数を使う。未検証の草稿は終了報告できるが、公開前確認では未完了として扱う。これらの判断も本文が変われば無効になる。

## 完了条件

- 検査した本文が、実際に提出する本文と一致している。
- 候補を文脈で判断し、未解決の修正が残っていない。件数ゼロは完了条件ではない。
- 原文がある場合は同じ原文で比較している。`newFacts: null` は未比較であり、「新出事実なし」とは報告しない。
- Node・依存・Sudachi・入力・抽出の問題があれば、`japanese-check: 未検証（理由）` と報告する。目視だけで機械検査済みとはしない。

満たせない場合は、未検証または未完了の草稿として利用者に返す。完成品として外部へ送信・公開しない。新しい文章を生成して提出する直前にもこの条件を適用する。

Git の commit/push と gh の PR・Issue の作成・編集・コメントでは、追跡済み文書と本文ファイルに未検査・未判断があれば実行前に止める。日本語の本文はファイルを check して `--body-file` または `-F` で渡す。

次のものは自動では確認できない。適用範囲を狭める例外ではなく、上の手順で登録・抽出・原文照合を行う必要がある範囲である。

- フックが観測しないツール（MCP を含む）と、Git の外での任意のシェル書き込み
- `bash -c`・`eval`・`$(…)`・スクリプトの中で組み立てた commit や push、`--git-dir <path>` を付けた Git、文書を作ってすぐ commit する形
- 呼び出しの実行中に別のプロセスが書いた文書。前後の差分に混ざり、別の書き手の変更を自分のものとして追跡することがある
- `.tmp/sessions/` の下に置いた本文ファイルの内容
- チャット本文と登録ファイルの一致

検査記録は自己申告で、故障を起こせばフックを通り抜けられる。検査の抜けを減らすための仕組みであり、意図した迂回は防がない。フックは自身の故障では終了や公開を止めず、知らせるだけにする。記録が壊れた文書は check で作り直せる。検査記録は文章の正しさや自然さの保証にはならない。
