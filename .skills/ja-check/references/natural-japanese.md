# 日本語補助検査の設計と使い方

## 着想と独自実装の範囲

[natural-japanese](https://github.com/coji/natural-japanese) の commit `45ef3a06e583d3c90a6a938d51d555112301a133` を分析し、「検出は機械、判断は文脈」「表現・構成・用語・追加された事実を別々に見る」という考え方を取り入れた。

校正ロジックと CLI は、この dotfiles 用に TypeScript で独自実装した。上流の Python、検出器、fixtures は同梱せず、上流の検出件数や JSON 形式への互換性も目指さない。Python からの逐語的な移植や上流追従は行わない。

## 既存の規範との関係

| 観点             | 既存の持ち主         | 追加したもの                                     |
| ---------------- | -------------------- | ------------------------------------------------ |
| 事実・確度の保持 | ja-fact-preservation | 見出しや図表でも確度を強めない                   |
| 直訳・曖昧な比喩 | ja-notation          | 主体・動作・対象、動作の名詞化を点検する         |
| 構成と順序       | ja-structure         | 見出しの抽出で点検を助ける                       |
| 段落の組み立て方 | ja-paragraph         | 段落の先頭と末尾の文と文の数の抽出で点検を助ける |
| 読者と用語説明   | ja-doc-profile       | 用語の初出と説明らしい記述を示す                 |
| 機械検査         | ja-check             | 独自 CLI の候補を既存検査より前に確認する        |

新しい入口スキルは追加しない。既存の起動条件・文体・構成変更の権限を維持する。人が読む日本語文書には、常時規則から参照する `human-documents.md` により、この CLI を必須とする。スキルの指定がなくても適用し、提出する最終稿を検査する。既存の textlint と yomiyasu の検査回数は変えない。

## 実行環境

TypeScript を直接実行できる Node.js 24 以上を使う。Bun でも実行できる。配布先は `~/.claude/japanese-check/` で、Codex からも同じ場所を使う。

形態素解析には npm の `lindera`（Rust 製、バージョンは `~/.config/japanese-check/package.json` に固定）と、UniDic の辞書を使う。Python は不要である。解析器は `~/.config/japanese-check/` に `chezmoi apply` が入れ、辞書は同じ場所の `unidic/` に展開される（展開後は約 191 MB）。辞書は読み込む直前に、ファイルごとのハッシュが固定値と一致するか確かめる。実行中に原稿をネットワークへ送らない。

lindera-unidic のエンジンを利用し、単語・品詞・辞書形を校正ロジックへ渡す。辞書形は、表記を保った UniDic の書字形基本形である。係り受けの構文解析はしない。英字だけは UniDic が 1 文字ずつに分けるので、隣り合う半角英数字 1 字の並びを 1 語の名詞にまとめる（API、IPv6）。出力の `analyzer` 欄に、エンジン・パッケージ版・辞書の識別を記載する。解析出力が不正な場合はエラーにし、正規表現だけへ黙って切り替えない。

## 呼び出し

```bash
node ~/.claude/japanese-check/cli.ts check draft.md --genre tech
node ~/.claude/japanese-check/cli.ts check revised.md --source original.md
```

JSON に次の情報をまとめて出す。原文と最終稿は別ファイルを指定する。Git から原文を読み出す機能は持たない。

| 欄         | 得られるもの                                       | 限界                                                   |
| ---------- | -------------------------------------------------- | ------------------------------------------------------ |
| findings   | 名詞化、冗長表現、対比、漢字連続、長文、文末反復   | 表現の要否や自然さは確定しない                         |
| calques    | 動詞・場所の比喩と語の一覧の候補                   | 字義どおりの用法や定着した専門用語も出る               |
| outline    | 見出し・段落の先頭と末尾の文と文の数・箇条書き・表 | 構成を変えるべきかは判断しない                         |
| terms      | 用語候補の初出と直後の説明らしい記述               | 専門用語の網羅や説明の正しさは保証しない               |
| paragraphs | 行番号付きの段落一覧                               | 意味の一致は判断しない                                 |
| newFacts   | 最終稿だけにある数値・固有名詞・英字の語           | 普通名詞で加えた細部、確度、発言者の変化は検出できない |

`--source` を省くと `newFacts` は `null`。比較して新出語がなければ空配列になる。「検査していない」と「検査したが候補がない」を区別する。

既定の長文の目安は100字、business は80字、essay は120字である。essay では文末反復を指摘しない。数値は見直す場所を示す目安で、合格基準ではない。

用途を絞る場合だけ、`check` の代わりに `lint`、`calques`、`outline`、`terms`、`paragraphs`、`newfacts` を使える。`lint` は文字列の検出規則だけを実行する。個別コマンドの `calques` も語の一覧を使う。`calques`、`terms`、`newfacts` と、まとめて見る `check` は形態素解析器を使う。`--genre` は check/lint、`--source` は check/newfacts でだけ使える。出力は常に JSON で、`--json` は不要。

終了コードは 0 が検査実行成功（候補ありも含む）、2 が引数・入力・依存・解析のエラー。エラーは stderr に出し、不完全な検査結果を成功として返さない。本文は書き換えない。check のハッシュ記録、review の判断記録、verify の照合、フックとの接続は `human-documents.md` に従う。verify は未検査・古い記録・未判断・草稿を終了コード1で示す。`--no-record` は check の記録を残さない。

## 対象と判断

Markdown の frontmatter、コードフェンス、インデントされたコード、HTML コメント、インラインコード、リンク先を検査から除く。見出し・表の文言は候補検出の対象に残す。一文一行の地の文は空行まで同じ段落として扱う。Markdown の全構文を網羅する解析器ではない。

位置は元のファイルの1始まりの行番号と、JavaScript の文字列に対応する UTF-16 単位の列番号で返す。絵文字の後でも、除外した部分を空白に置き換えて位置を保つ。

同じ本文の解析結果は一つの実行内で共有する。check を使った後に同じ本文へ個別コマンドを重ねない。候補は既存の事実保持・構成・読者の規則で判断し、修正しない場合は理由を付ける。本文を直した後、修正前の検査結果を最終稿の結果として報告しない。

## 採用しないものと検証

自然さの点数による合否判定、全見出しの結論化、無制限の修正、約1 GB のモデルによる意味の類似度検査は採用しない。数値や語の追加がなくても意味は変わりうるため、原文を読む照合は省略しない。

独自テストでは Markdown の除外と位置保持、実際の lindera-unidic による活用語の辞書形、用語の初出、数値・固有名詞の追加、移動した文を追加としないこと、意味の変化を検出できない限界、CLI の入力エラーを確認する。ルールを更新するときは、この dotfiles の規範に合う検出例と残す例を追加する。
