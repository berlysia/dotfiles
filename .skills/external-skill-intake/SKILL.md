# 外部スキルの取り込み

## 導入方式を選ぶ

1. 専用の空ディレクトリで取得物を読み、検査前のスクリプトは実行しない。description の起動条件、既存規範や hooks との競合、兄弟スキルへの相対参照、配布用サブディレクトリを調べる。参考にするだけならインストールせず読む。
2. コピー・APM・plugin の実際の配置先、検査、更新時の置換、独自変更を適用し直す手間を比較する。Claude と Codex の両方を確認する。APM が隠し Unicode で失敗しても、plugin や手コピーでは同じ検査が行われない場合がある。方式変更を検査の代わりにしない。兄弟参照に必要な集合と相対位置を維持する。
3. 必要な配置と改変を満たす方式を選ぶ。配備先を直接直すと更新で消えるので、変更は同期元か配備物の外に置く。コピーでは原典と commit、手元の差分、帰属、本体と同梱データそれぞれのライセンス通知を保持する。

## 導入経路を検査する

- 現在の manifest・lock・スクリプトで、依存の install と同期の順序、rsync 除外を確認する。APM の lock に同名が残ると `.skills/` から同期されない場合がある。スキル内の依存は、同期前の install や撤去時の未管理ファイルと衝突しうる。
- 依存コマンド不在と一部取得失敗を試し、終了コードと次回の再実行を確認する。`run_onchange_` は正常終了を記録するので、未導入のまま exit 0 にすると再試行されない。APM の失敗コードは推測せず測る。
- 取得ハッシュに加え、展開後の必須ファイル集合と配置を照合する。`stripComponents` の誤りは exit 0 でも起こる。`.claude-plugin/plugin.json`、`.mcp.json`、兄弟参照先など、対象の実行に必要なファイルを期待値に含める。
- marketplace の宣言名と登録名、推奨する agent・skill の実在を照合する。上流の構成変更で名前だけが残ると、導入済みに見えても起動できない。
- skill-inventory の許可出力を変更前後で比較する。外部スキルの未掲載行は未チェックで追記される。settings 生成より後に追記される場合、許可への反映はその次の apply になる。

## 更新・撤去を確認する

- 更新は原典の commit と手元の差分を突き合わせ、独自変更を上書きしない。追跡を続けるコピーでは整形だけの差分も負担になる。上流のテストが複製間の一致検査なら、手元の変更の正しさは別に検証する。
- 撤去は実行時点の manifest と lock で dry-run を取り、実行後に lock、各配置先、同期除外、許可一覧を照合する。宣言の削除だけでは撤去済みとしない。lock が残ると許可行が再追記され、同期対象外のディレクトリや未管理の依存も残りうる。想定外の残存は範囲と副作用を報告し、追加の削除判断を求める。
