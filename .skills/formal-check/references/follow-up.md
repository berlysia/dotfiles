# 追従の 1 周での分け方

追従の 1 周では、check ごとに結果を 4 つのどれかで返す。
updated と bug が両方当てはまることもある。

## 結果の 4 つ

- **in sync**: 覆うファイルの変更が、モデルが表している範囲に影響しない。モデルは直さず、sync だけを書き直す。
- **updated**: 実装の変更に合わせてモデルを直し、検査が期待どおりになった。実コードを壊す確認も期待どおりになった。
- **bug**: 実装の変更で、守っていた性質が成り立たなくなった。witness を実コードでたどり、すべての歩が起こりうると確かめた。導入した commit を名指しし、finding として登録する。
- **blocked**: 最後まで進められない。理由（ランタイムや java の欠け、モデルを直せない、実装の依存を用意できない）を、表の error の code と `Recover with:` の行と一緒に書く。sync は書き換えない。

## 差分の変更の分け方

覆うファイルの差分にある変更を 1 つずつ、次のどれかに分ける。

- **影響なし**: 書式、コメント、ログ、モデルが扱わない関数の変更。
- **モデルが表していない**: 性質に関わるが、モデルの範囲の外（新しい入力の種類、新しい状態）。モデルを広げるか、台帳の「対象外」の欄に書く。
- **意図した変更**: 実装が性質そのものを変えた。根拠（commit のメッセージ、issue、利用者の説明）を示し、変える前と後の性質の文言を台帳に書く。
- **成り立たなくなったかもしれない**: 意図の根拠が無いのに、性質に関わる振る舞いが変わった。検査で確かめ、反例が出たら bug として扱う。

改名、分割、移動した関数と、守る状態に新しく書き込むコードは、差分の外にあることが多い。
覆うファイルの外も検索する。

## 確かめた commit が履歴に無いとき

`sync.commit` が履歴に無いこと（shallow clone、squash、rebase）がある。
そのときは差分を読まず、覆うファイルを今の内容で 1 から読み直す。
remote から fetch して commit を取り戻そうとしない。
第三者のリポジトリの remote を信頼できるとは限らないためである。
