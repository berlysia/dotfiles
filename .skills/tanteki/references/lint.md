# 検査コマンドの使い方

textlint を使い、日本語の表現や文書の形式を機械的に検査します。内容が正しいかどうかは、執筆者が別に確認します。

## コマンドを実行する

このスキルの `SKILL.md` があるディレクトリを「スキルルート」と呼びます。初回はスキルルートで `npm ci` を実行し、必要なパッケージをインストールしてください。その後、`scripts/lint.mjs` を実行します。

`--type` は必須です。`design-doc`、`prd`、`adr`、`rfc`、`stock`、`flow`、`record` を指定できます。選び方は[文書分類](document-types.md#検査コマンドの指定値)を参照してください。最初の5種類では、参照用の文書に作業進捗が混ざっていないかも検査します。`flow` と `record` では、この検査を外します。

別のディレクトリから実行する場合は、スクリプトと入力ファイルを絶対パスで指定できます。次は設計書と進捗報告の検査例です。

```sh
node /absolute/path/to/tanteki/scripts/lint.mjs \
  --type design-doc /absolute/path/to/design.md
node /absolute/path/to/tanteki/scripts/lint.mjs \
  --type flow --format json /absolute/path/to/status.md
```

`--format` には、画面で読むための `pretty-error`（既定）か、機械処理用の `json` を指定できます。入力には1つ以上の Markdown ファイルを指定します。同じ種類なら、複数ファイルをまとめて検査できます。

未知のオプション、未対応の拡張子、存在しないファイルを指定するとエラーになります。検査によって入力ファイルが書き換わることはありません。

## 検査するルール

| ルール名 | 検査する内容 |
|---|---|
| `preset-japanese` | 助詞の重複や二重否定など、日本語の文法上の問題 |
| `no-ai-jargon` | 語と述語の組み合わせが不自然な直訳調・抽象表現 |
| `no-opaque-compound` | 対象・抽象的な変化・仕組みを重ねた、意味の分かりにくい名詞句 |
| `no-vague-action` | 程度や条件、指示語の参照先が不明確になりやすい表現 |
| `stock-boundary` | 参照用の文書に混ざった作業進捗や追跡情報 |
| `table-cell-length` | 表の見出しと本文セルの文字数 |

`stock-boundary` は `stock` と同じ検査を行う文書に適用します。作業進捗、チェックボックス、PR番号、PR・Issue・Jira の URL が対象です。その他のルールは全区分に適用します。

## 日本語の文型と検出範囲

独自の文章ルールは、[kuromojin](https://github.com/azu/kuromojin) で文を意味のある最小単位（形態素）に分けます。各語の基本形・品詞と、助詞のつながりを調べます。例えば `適切に対応しました`、`適切な対応を行う`、`十分なリスク評価を行う` は、動詞の形や名詞への言い換えにかかわらず、判断基準が書かれているか確認する対象です。指示語の後の `を`、`に`、`については` なども、動作との関係として扱います。助詞を一律に削って照合することはありません。

名詞を組み合わせた表現は、登録済みの造語と完全に一致しなくても検出します。例えば `業務の効率化の基盤` は対象・変化・仕組みの連結として検出します。既存の仕組みに対する操作を表す `画像処理システムの最適化` とは、語の順序で区別します。長い専門用語を文字数や名詞数だけで指摘しません。

文脈に合う言葉かどうかは執筆者が判断します。一方、`段3` のように再現できる不自然な番号表記は既知の候補として検出します。`3段` の助数詞や `階段`、`段落` まで一律に禁止しません。

段落・見出し・表セルごとに表示される本文を集めるため、強調やリンク表示文にまたがる表現も検査します。コード・引用・URL・画像・HTML・明示的な改行を境界として扱い、前後を連結して架空の文型を作りません。通常の折り返し改行は文を分けません。検出した箇所は、元の Markdown 上の位置で示します。否定や補助的な述語も確認できる範囲を指摘します。

実装は [no-doubled-joshi](https://github.com/textlint-ja/textlint-rule-no-doubled-joshi) の文分割と原文位置への復元、[no-double-negative-ja](https://github.com/textlint-ja/textlint-rule-no-double-negative-ja) の基本形・品詞・助詞による照合を参考にしています。[morpheme-match](https://github.com/textlint-ja/textlint-rule-morpheme-match) も、文字列の見た目だけでなく、語の性質を使う設計の参考です。文分割に [sentence-splitter](https://github.com/textlint-rule/sentence-splitter)、原文位置の復元に [textlint-util-to-string](https://github.com/textlint/textlint-util-to-string) を使います。

文を語に分けても、語同士の修飾関係や意味の正しさまでは判定できません。検査で扱っていない表現や、離れた語同士の修飾関係、文脈に合う訳語かどうかは、執筆者が確認します。検出済みの語も、原資料で範囲・条件が明確な場合や専門用語として必要な場合は文脈を確認します。未知の問題を見つけたら、同じ構造の言い換えと、それに似た正しい用例をテストに加え、検出漏れと誤検出の両方を確認します。

## 表の文字数

`table-cell-length` は、表示上61文字以上のセルを指摘します。Markdown の装飾記号とリンク先URLは数えず、リンク表示文とインラインコードは数えます。セル前後の空白は数えません。結合文字と複数コードポイントの絵文字は、表示上の1文字として数えます。セル内で改行しても、セル全体で数えます。

引用原文とコード例はこのルールの対象外です。HTML や Markdown 以外の表にも同じ上限を適用し、執筆者が確認します。長い説明を表へ詰め込まず、表の外へ移してください。条件や例外を削ってはいけません。意味のない分割や独自の略語で文字数だけを減らしてもいけません。

## 終了コード

実行後の終了コードで、検査が完了したかを確認できます。

| 終了コード | 意味 |
|---|---|
| `0` | 検査が完了し、指摘がない |
| `1` | 検査が完了し、指摘がある |
| `2` | 引数・設定・ファイルの読み書きにエラーがある |

必要なパッケージがなく、スクリプトを起動できない場合も未検証として扱います。

指摘された表現は、文の意味を確認してから直し、最終変更後に再検査してください。検査に通っても、辞書やパターンにない表現、文をまたぐ指示関係、事実の正しさは保証されません。日本語の意味は [日本語の基準](japanese.md)、節の分担と形は [文書の構成と本文の形](structure.md) に沿って確認します。一般の技術語を長さだけで禁止しません。

## `allow` 設定

`allow` は、必要な用語を検査の例外として登録する設定です。正確な意味を伝えるために残す用語は、[`.textlintrc.json`](../.textlintrc.json) の該当ルールへ `allow` の文字列として追加できます。既存の `rules` の該当設定だけを変更してください。この検査コマンドはスキルルートの設定を読み込みます。例えば次の設定は、「レバレッジ比率」と一致する範囲だけを `no-ai-jargon` の検査対象から外します。

```json
{
  "rules": {
    "no-ai-jargon": { "allow": ["可観測性", "レバレッジ比率", "ロバストな推定"] },
    "no-opaque-compound": { "allow": [] },
    "no-vague-action": { "allow": [] },
    "stock-boundary": true,
    "table-cell-length": true
  }
}
```

同じ設定方法を `no-opaque-compound` と `no-vague-action` にも使えます。例外とする理由を確認した用語だけを指定してください。検査を通すためにルール全体を無効にしたり、問題のある文をコードや引用へ移したりしてはいけません。`allow` は用語の一致範囲だけを除外し、同じ段落の他の表現は検査します。表セルの上限は `allow` で緩められません。
