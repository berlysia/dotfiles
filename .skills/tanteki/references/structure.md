# 文書の構成と本文の形

[種類別の参照資料](document-types.md#カテゴリから参照先を引く)で説明すべき内容を確認し、原資料と読者に合わせて構成を決める。読者が必要な情報を探し、その関係を理解できるように並べる。情報が足りないことを、見出しを増やして補わない。

## 文書全体の構成を決める

まず、その文書を読んで何を理解・判断・実行できるようにするかを一文で定める。提案書なら提案とその理由、手順書なら操作の目的と完了条件、調査記録なら確かめたことと分かった範囲が中心になる。冒頭には、読者が文書の要点や用途をつかめる説明を置く。

次に、資料にある情報を、文書の役割に沿って結び付ける。設計の選択理由は目的や制約に照らして説明し、操作には実行条件と結果の確かめ方を対応させる。調査の解釈は調べて得た事実に基づけ、方法や対象から生じる限界を示す。この関係を確かめてから、各節で答える問いを決める。

構成は次の順に検討し、必要な情報を伝えられる最も簡単な形を選ぶ。

| ステップ | 構成 | 必要になる条件 |
|---|---|---|
| 0 | 見出しなし | 必要な説明を一つの問いで扱える |
| 1 | 並列の節 | 独立して参照する問いが複数ある |
| 2 | 親子の節 | 一つの問いの中に、分けて説明すべき問いがある |

節に名前を付けられるだけでは分けない。親子の構成も、下位の問いが必要な部分にだけ使う。短い案内の構成案は、答える問いと含める情報を一文で示せばよい。

構成案の「答える問い」と「含める情報」を読み、読者が知りたいことと、情報同士の関係から節を組む。種類別の参照資料が説明する内容を、そのまま同じ階層の見出しにしない。同じ階層の節はそれぞれ別の問いを受け持つ。

読者が必要とする順序で節を並べる。結論を先に示す場合は根拠をたどれるようにし、操作を説明する場合は実行前に条件を確認できるようにする。ユーザーが指定した構成や見出しは守る。

### 包含関係から節をまとめる

見出しは節全体を代表する名前であり、本文の話題の一覧ではない。目的やスコープが、なぜこの検討が必要かを説明する一部なら、「背景と目的」「背景とスコープ」は「背景」でよい。目的やスコープの記述は本文に残す。「結果」が利点や負担を含む場合の「結果と代償」も、全体とその一部を並べている。

包含関係（一方の情報が、他方の情報の一部に当たる関係）は、語だけで決めず、その文書での情報の役割から判断する。成功条件を目的と照合する、対象内外を実装や受入判定で繰り返し参照するなど、独立して探す必要があれば「目的」「スコープ」を分ける。

「背景」を何でも入れる節にせず、同じ説明や同じ根拠を複数の節に重ねない。説明をまとめて置く節を一つ決める。「結果と未決定事項」のように役割が違う情報は、それぞれ必要な場所へ分ける。「在庫と注文の更新」のように二つの対象の関係を扱う見出しは保てる。「と」の有無や文字数で一律に決めない。

例えば「背景」の構成案に処理方式と結果提示の遅延を置き、「設計」に同じ処理方式、「影響」に同じ遅延を置いたなら、節名を短くするだけでは重複が残る。処理方式は設計、遅延は影響へ集約し、背景に独自の前提や理由が残らなければ、その節を省く。独立した役割がある情報まで一つの節へ押し込まない。

### 意味を増やさない修飾を削る

「改善課題」は通常「課題」でよい。課題には改善・解決すべきことという意味があり、「改善」を足しても対象や性質を区別できないためである。これは節の包含関係とは別に、修飾語が情報を増やすかという判断であり、本文の情報を移す必要はない。

修飾語を外しても指す内容が変わらないかを確かめる。「運用上の課題」が技術や費用の課題と区別する役割を持つなら、その限定は残す。正式名称や指定された分類名も保ち、漢字の連結や「改善」という語だけを理由に削らない。原資料に語が現れるだけでは、変更できない正式名称や指定見出しとは扱わない。

## 見出しと論旨を照合する

構成案の合格後も、執筆した本文を各節の問いと照合する。節ごとの説明が揃うだけでなく、文書全体で判断の理由や操作の条件などをたどれるか確かめる。背景に設計の詳しい説明が入り、影響に同じ仕組みが再登場するなど、節の分担が変わっていれば、情報の置き場所を直す。新しい問いや小節が必要なら、該当部分の構成を再検査する。

見出しで掲げた問いに、本文が答えているかを確かめる。比較の基準を示したら、各案の分析と結論もその基準に照らす。「運用負担の比較」という節に価格しか書かれていないなら、運用負担の根拠を確認するか、資料で答えられる範囲に見出しと結論を直す。見出しを埋めるために説明を創作しない。

「制約」という節には、選択や実行を制限する条件が必要である。採用した方式やその影響だけなら、それぞれの役割に合う場所へ移す。複数の役割を掲げた見出しも、本文が各役割に答えているかを確かめる。条件の記載がないことを「制約なし」と断定せず、確認が必要な点と、本文に不要な節を区別する。

比喩が暗示する因果関係や比較を、本文の事実で説明できるか確かめる。例えば、相関しか分からない二つの現象を「病気と症状」に例えると、原因まで判明しているように読める。対応を説明できなければ、実際に分かっている関係を書く。大きな問いを掲げる前置きや結論の言い直しも、事実・条件・理由・判断を増やさなければ削る。

この点検は、todesking の[「AIっぽさはどこからくるのか」](https://zenn.dev/todesking/scraps/da4b4a01cec42b)を参考にした。記事は比喩と論旨の不一致、掲げた基準と後続の分析の不一致を指摘している。本スキルでは文章の内容を点検する基準として使い、AI による執筆を見分ける証拠とは扱わない。引用や専門語まで削ったり、語尾や記号を機械的に変えたりして、人間らしい外見だけを作らない。

## 本文の形を選ぶ

各節で、必要な情報を伝えられる最も簡単な本文の形を選ぶ。次のステップ番号は、文書全体の構成を選ぶ際の番号とは別に扱う。

| ステップ | 本文の形 | 必要になる条件 |
|---|---|---|
| 0 | 一文 | 必要情報と関係を一文で伝えられる |
| 1 | 一段落 | 結論に理由や条件を添える必要がある |
| 2 | 複数段落 | 同じ問いに複数の説明が必要 |
| 3 | 小節 | 独立して参照する下位の問いがある |

全ての節を同じ形式にそろえない。複数の要素を並べるときは、要素同士の関係で形を決める。

| 要素の関係 | 形 |
|---|---|
| 理由・対比・条件・帰結の関係がある | 段落 |
| 並列で、比較・対応する同じ属性（型・既定値・役割など）を持つ | 表 |
| 並列で、属性がそろわない。または短い名称・確認事項の列挙 | 箇条書き |
| 実行順序が必要な操作 | 番号付きリスト（手順） |

背景は検討の前提、設計は処理と条件、影響は採用による変化というように、その節の問いから形を判断する。小節や新しい論点が必要になったら、該当部分の構成案を直して再検査してから書く。細分化することだけを目的に構成の段階を上げない。

## 文章のまとまりを判断する

文章で説明する箇条書きが5項目以上になる場合は、項目の間に理由・対比などの関係があるときだけ、意味のまとまりごとの段落にまとめる。並列なら表か箇条書きのままにする。見出しは、独立して参照する問いがある場合だけ付ける。項目数を見出しの必要性の根拠にしない。4項目以下でも、一項目が長い場合や因果・条件・対比を追う必要がある場合は段落を使う。

見出しは論点を示し、段落はその中の結論と理由、条件と結果などの関係を伝える。一項目ずつ見出しに変えたり、4項目ずつ別のリストに割ったり、入れ子に移したりして数だけ減らさない。全項目を一つの長い段落に詰め込まず、必要な情報を保って意味のまとまりで分ける。

段落の第1文に、その段落の結論を書く。1段落で扱う論点は1つにする。前の段落との関係が理由・対比・条件・帰結に当たるときは、段落の冒頭に「そのため」「ただし」などの接続詞で示す。

短い名称・値・選択肢の列挙、個別に確認するチェックリスト、実行順序が必要な番号付き手順は、5項目以上でもその形を保てる。ただし、説明文に番号を付けただけなら手順ではない。項目どうしの関係で判断する。ユーザーが箇条書きや既存形式の維持を指定した場合は、その指定を守る。

### 組み替える前

- 申請者は申請フォームから利用申請を送る。
- チーム責任者が申請内容を審査する。
- 必須項目が不足していれば、責任者は申請者へ差し戻す。
- 審査結果は申請者にメールで届く。
- 却下された場合、申請者は理由を確認してから再申請する。

### 組み替えた後

#### 申請と審査

申請者は申請フォームから利用申請を送る。チーム責任者が内容を審査し、必須項目が不足していれば申請者へ差し戻す。

#### 結果の確認と再申請

審査結果は申請者にメールで届く。却下された場合は理由を確認してから再申請する。

## 図の型を選ぶ

節ごとに図の型を決める。型を決めずに描くと、役割の違う図が1枚に混ざる。

| 示すもの | 型 |
|---|---|
| システムと外部の関係 | C4 のシステムコンテキスト図 |
| 誰が何をできるか | ユースケース図 |
| 時系列の相互作用 | シーケンス図 |
| 状態の遷移 | 状態遷移図 |
| ユースケースごとの操作とイベント | ロバストネス図 |
| 組織や業務の範囲 | ビジネスコンテキスト図 |

1枚に2つの型を混ぜない。ビジネスユースケースと業務フローは別の図にする。概念モデルとシステム構成も分ける。図に収まらない情報は表へ出す。参照する集約・操作・イベントは表にまとめ、本文へ埋め込まない。

Mermaid で描く。ロバストネス図は flowchart と classDef で代替する。usecase-beta は Mermaid v12 専用で、v11 系の mermaid-cli では描画できない。

## 表の一覧性を保つ

表は短い項目や値の違い、対応関係を見渡すために使う。見出しセルも含め、1セルでも61文字以上ある表は禁止する。全セルを60文字以内に収めても、説明を読み込まないと比較できない表は見出しと段落に組み替える。

文字数は表示上の文字で数える。句読点、数字、内部の空白、リンクの表示文、インラインコード、画像の代替文を含める。セル前後の余白、Markdownの装飾記号、リンク先URLは含めない。結合文字や複数コードポイントの絵文字は、表示上の1文字として数える。セル内で改行しても、セル全体の文字数で判断する。

長い説明は表の外へ移し、表には比較に必要な短い要点だけ残す。表を求められた場合も同じ上限を守る。意味のないセル分割、独自の略語、条件や例外の削除で数だけ減らさない。列を増やすと生じる空欄を、資料にない値で埋めない。表をやめた結果、文章の箇条書きを大量に並べることも避ける。

例えば権限の比較表なら、表には「編集者」「編集可」などの対応だけを残し、編集できる範囲や例外は「編集権限」の節で説明する。詳細との対応が分からなくなるなら、表全体を論点ごとの見出しと段落へ変える。
