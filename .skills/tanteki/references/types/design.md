# 設計・意思決定

## Design Doc

Design Doc は、何をどう実現し、なぜその方式を選ぶかを説明する設計書である。開発者、設計担当者、レビュー担当者、関係チームが、設計の前提、実現方法、採否の理由、引き受ける影響を理解するために使う。区分は `stock` とする。

背景にある課題と今回の目的を示す。設計で扱う対象は「スコープ」、扱わない対象は「スコープ外」と表す。未決定の事項は、それだけでスコープ外にはしない。

制約は、利用する技術の上限や組織上の要件など、実現方法の選択を制限する条件である。原資料にある条件と、それによって選べる方式がどう限られるかを説明する。例えば、キューの1MB上限は制約、保存先だけをキューへ送るのは実現方法、非同期化による結果提示の遅れは採用後の影響である。制約と、選んだ方式やその影響を混同しない。

採用案と代替案は、背景・目的・スコープ・制約から導いた同じ基準で比較する。どの条件を満たすためにその案を採り、なぜ他の案を退けるかを説明する。不採用案に利点があれば、それでも今回は何を優先するのかを書く。今回のスコープでは不要なことと、案自体の欠点は区別する。

実現方法は、構成とデータの流れ、通常時と重要な失敗時の動作から説明する。それらによって、スコープの中で目的をどう満たすかが分かる必要がある。

採用後の変化、負担、リスクを説明し、システムや手順のどこまで影響するか、変更を元に戻せるかを示す。その影響を引き受ける理由も、目的と比較結果に照らして説明する。未解決点は関係する設計内容と結び付け、採否を左右するものは判断への影響を明記する。未確認の条件を満たしたものとして、採否を確定させない。

外部 API・仕様・測定結果や別 ADR など、判断の根拠となる資料を参照する。リンクだけでは結論や理由を追えないなら、必要な事実を本文に残す。根拠がチケットにしかない場合は、事実を本文へ抜き出し、未確認の点を明記する。作業の進捗はチケットや進捗文書で管理し、PR/Jira一覧、完了率、今週やることを本文に入れない。

## RFC/技術提案

複数チーム、標準化参加者、レビュアに向けた技術提案書である。技術・運用上の提案と、広い合意が必要な論点を説明する。作業計画や実装進捗の管理には使わない。区分は `stock` とする。

誰に何の変更への合意を求めるかを示し、その提案で解決する問題と適用範囲を説明する。代替案との比較と採否の理由は、解決したい問題や関係者への影響に照らして示す。何が合意済みで、どの論点について意見や判断が必要かを区別し、提案の状態を残す。レビュー依頼の宛先・期限と作業台帳は他へ移す。

## ADR

ADR（Architecture Decision Record）は、設計上の決定を記録する文書である。技術責任者、開発者、将来の保守者へ、一つの重要な決定と、その理由・結果を説明する。詳細設計、実装進捗、作業チケットの管理には使わない。区分は `stock` とする。

決めた内容は「決定」と呼び、理由や日付も「決定理由」「決定日」と表す。選択肢を評価する行為や基準を指す「判断」と区別する。

どの背景や制約のもとで何を選び、なぜその決定に至ったかを残す。代替案と不採用理由は、その決定を理解するために必要な範囲で説明する。採用による利点、負担、制約、その他の影響を決定に結び付け、後から理由と結果をたどれるようにする。決定の状態と資料にある決定日も残す。

ADR の「提案・採用・廃止・置換」は決定の状態であり、実装の「未着手・作業中・完了」とは別である。決定を変える場合は旧 ADR を上書きせず、新しい ADR には置き換える旧 ADR への参照を記す。採用/廃止/置換の日付と代替 ADR への参照は記載してよい。Design Doc のレビュー期限、PR 番号、Jira 課題ID、作業状況は依頼文やチケット・進捗文書で管理する。

### ADR の決定と結果を残す

一つの重要な決定について、背景、決定とその理由、結果を記す。これらは固定の章立てではなく、決定を追うために必要な内容である。「結果と代償」という言い方では意味が重なる。通常の費用や運用負担を一括して「代償」と呼ばず、「DB の保存量が増える」「障害時の切替操作が必要になる」のように、何が変わるかを書く。想定される影響と、実際に確認した結果は区別する。

#### 未決定事項を扱う範囲

「未決定事項」は必須の節にしない。後続の詳細設計や作業の TODO は、それを管理する設計書や作業文書へ分ける。原資料に未決定の項目があるという理由だけで、全てを ADR に転記しない。既存の管理先が判断に必要なら参照し、存在しない文書やリンクは作らない。

採否を左右する未確認事項は、提案中の ADR の背景や採用条件として残す。未確認事項を消して採用済みに見せない。採用済みでも、その決定が依存する仮定や、引き受けたリスク、資料で定めた再検討条件は残す。

[Nygard の原典](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)は、結果に良い影響・悪い影響・中立の影響を含める。[MADR のテンプレート](https://adr.github.io/madr/#full-template)にも、未決定事項を必須にする指定はない。結果の扱いと未決定事項の振り分けは、これらを踏まえた本スキルの方針である。

## セキュリティ設計/脅威モデル

セキュリティ、開発、運用の担当者に向けた設計書である。資産をどの境界で守り、どの脅威へどの対策を行い、何を残余リスクとして誰が負うかを説明する。セキュリティ審査の進捗報告には使わない。区分は `stock` とする。

資産と境界は守る対象を定める。脅威はその対象に生じるリスクを示し、対策は脅威に対応させる。対策後も残るリスクと責任を持つ担当者や組織を残す。

## データモデル設計

開発者、DBA（データベース管理者）、データ利用者に向けた設計書である。エンティティ、関係、整合性を定める。実行中の移行手順の管理には使わない。区分は `stock` とする。

エンティティと属性の意味を定め、関係と制約で整合性を説明する。変更方針は、これらの意味と整合性を変更時にも保つ条件として扱う。

## UI 振る舞い仕様

デザイン担当者、FE（フロントエンド開発）担当者、QA（品質保証）担当者、PdM（プロダクトマネージャー）に向けた仕様書である。画面状態、操作、遷移、文言を揃える。ビジュアルデザインの好みや開発進捗の管理には使わない。区分は `stock` とする。

どの状態でどの操作が可能か、操作でどこへ遷移するかを定める。文言とアクセシビリティは、その状態と操作を利用者が理解・利用できる条件として扱う。

## 同じ題材の最小例

架空の資料: 利用者は応答が途切れると注文を再送する。新規注文 API で同じキーの再送を24時間以内は一件として扱う。同じキーで内容が異なる場合は409を返す。既存注文の変更は対象外。設計案では利用者とキーの組を一意にし、注文とキーを同じ DB トランザクションで保存する。同内容の再送には保存済みの応答を返す。別キャッシュ案は同時更新の処理が増えるため不採用。DB の保存量が増える。保存先は提案段階で、24時間後のキーの扱いは未決定。

### PRD

利用者が応答を受け取れず注文を再送しても、注文を重複させない。同じ利用者が同じキー・同じ内容で24時間以内に再送した場合、注文は一件となる。同じキーで内容が異なる場合は409を返す。既存注文の変更は対象外とする。

### Design Doc

利用者が応答を受け取れず注文を再送しても、24時間以内は重複した注文を作らない。そのため、設計案では注文と再送判定用のキーを同じ DB トランザクションで保存する。スコープは新規注文 API とし、既存注文の変更はスコープ外とする。

利用者とキーの組を一意にし、同時に届いた再送でも注文を一件にする。24時間以内の再送は内容を比較し、同じなら保存済みの応答、異なれば409を返す。

保存先の比較では、重複を防ぐために注文とキーの同時更新を保証する必要がある。同じ DB なら両者を一つのトランザクションで確定できるため、この案を採る。別のキャッシュへの保存は、その保証に必要な処理が増えるため採らない。採用案では DB の保存量が増える。24時間後のキーの扱いは未決定である。

### ADR

状態: 提案。注文の再送による重複を防ぐため、再送判定用のキーは注文と同じ DB に保存する。両者を同じトランザクションで確定するためである。別のキャッシュは同時更新を保証する処理が増えるため採らない。DB の保存量が増える。

この ADR が扱うのは保存先の決定である。24時間後のキーの扱いは上の Design Doc に残し、ADR の必須項目にはしない。保持要件が保存先の採否を左右すると分かった場合は、その条件を ADR にも残す。
