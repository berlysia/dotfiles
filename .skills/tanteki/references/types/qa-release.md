# QA・リリース

## テスト計画

QA（品質保証）担当、開発者、PdM（プロダクトマネージャー）、リリース責任者に向けたテスト計画である。対象をどの観点、環境、データで確認し、誰がどの終了条件を判定するかを定める。実行済み結果や日々の進捗の記録には使わない。区分は `flow` とする。

対象と対象外を示し、確かめたいことに合わせて環境とデータを定める。実施する役割と判定する役割を示し、何を満たしたらテストを終了できるかを明記する。実施結果と証跡はテスト結果へ残す。

## テスト結果

QA、開発者、PdM、責任者に向けたテストの記録である。どの版をどの環境でどこまで試験し、何を根拠にどう判定したかを保存する。次の作業の正式な管理先にはしない。区分は `record` とする。

実施したテストごとに結果と証跡を示し、判定の理由を説明する。失敗、範囲外、未実施を区別し、残った課題も記す。残課題の進捗・担当・期限はチケット側で管理する。

## リリース/ロールアウト計画

開発者、SRE（信頼性エンジニアリング）担当、CS（カスタマーサポート）担当、責任者に向けた展開計画である。何をどの段階で展開し、何を監視して続行・撤回を判断し、誰へ連絡するかを決める。プロジェクト全体の進捗報告には使わない。区分は `flow` とする。

対象を段階に分け、各段階で監視する項目と、続行・撤回の判定条件を対応させる。撤回する方法と、判断結果を誰にどう連絡するかも示す。

## データ移行計画

開発者、DBA（データベース管理者）、運用担当に向けた移行計画である。移行と切戻しを安全に実施する。恒久的なデータ仕様の複製には使わない。区分は `flow` とする。

対象と前提を示し、移行と切戻しの手順を実行できるようにする。移行前後のデータを何で照合し、その結果から続行・停止・切戻しをどう判断するかを定める。

## 変更履歴（Release Notes）

利用者、CS、運用担当、開発者に向けた変更履歴である。利用者に影響する変更を知らせる。内部設計や未完了タスクの説明には使わない。区分は `record` とする。

どの版でいつ何が変わったかを示し、影響を受ける利用者に必要な移行や注意事項を伝える。

## 受け入れテスト手順書

実施者と依頼元に向けた受け入れテスト手順書である。変更が期待どおり動くことを、実行できる操作と判定で確かめる。テストコードの設計や網羅率の議論には使わない。区分は `record` とする。

何を確かめるテストかを示し、実行前に満たす条件を定める。シナリオごとに操作、期待する結果、合否判定を対応させ、チェックボックスで実施を記録する。検証観点とシナリオの対応を示し、実施記録から何を確認した結果か追えるようにする。関連文書は要求や仕様との対応を示すために参照する。

チェックボックスが本文の一部になるため、`record` で検査する。参照用の文書として検査すると、すべてのチェックボックスが作業進捗として指摘される。
