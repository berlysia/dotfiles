# 運用・障害

## 運用 Runbook

SRE（信頼性エンジニアリング）担当、オンコール担当、サポート担当に向けた運用手順書である。定型作業や障害対応を安全に再現できるようにする。事故の原因分析や作業の進捗報告には使わない。区分は `stock` とする。

実行者と前提を示し、何を検知したら手順を始めるかを定める。操作は実行する順に書き、各操作の期待結果と確かめ方を対応させる。安全に続けられない場合の停止条件と、復旧方法・連絡先も示す。短くしても危険な操作の条件を落とさない。

## SLI/SLO 方針

SRE、開発、PdM（プロダクトマネージャー）、責任者に向けた信頼性方針である。SLI（信頼性を測る指標）と SLO（その目標値）、測定方法、対応方針を定める。直近リリースの達成状況を日報化する文書ではない。区分は `stock` とする。

指標、目標、集計期間、集計から除く対象や条件を対応させ、何をどの条件で測るかを定義する。目標を満たさない場合の対応方針は、この定義に基づいて取る行動である。

## インシデント記録

オンコール担当、運用担当、関係チームに向けた、発生中の障害の記録である。影響、出来事の順序、対応の状況を共有し、次の判断を支える。恒久対策の設計や個人の評価には使わない。区分は `flow` とする。

影響と検知を起点に、確認済みの出来事と、それに対する対応を時系列で残す。現在の状態と次に判断することを分け、推測した原因を確定した事実として書かない。

## ポストモーテム

関係チーム、責任者、将来の保守者に向けた障害の振り返り記録である。影響、原因、再発防止を学べるようにする。個人を責めず、チケットの進捗の正式な管理先にはしない。区分は `record` とする。

検知時刻、影響、経過を残し、原因と寄与要因は確認した事実と仮説を区別して説明する。改善策がどの原因や寄与要因に対処するかを示し、対応課題を参照できるようにする。対応課題の進捗・担当・期限の正式な管理先はチケット側に置く。

## 廃止/移行告知

利用者、社内利用チーム、CS（カスタマーサポート）に向けた移行告知である。旧機能や API の終了と移行先を知らせる。代替設計の全詳細や個別タスクの管理には使わない。区分は `stock` とする。

何がなぜ終了し、いつまでに誰が影響を受けるかを説明する。移行先と問い合わせ先を示し、利用者が必要な対応を判断できるようにする。

## 手順や記録では残すものが違う

[進捗報告](knowledge.md#進捗status-report)は、運用手順や障害の振り返りと分けて、作業の状況と判断依頼を伝える。

コマンドはそのまま実行できる形で書く。山括弧で囲んだ仮の値を、未記入のまま残さない。値は変数定義にまとめ、権限の切り替えを含めて実行できる形にする。

報告では個人名を書かない。見解はチーム名で示す。他の案に懸念がある場合は、その案のどの性質が問題かを書く。
