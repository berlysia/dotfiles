# 戦略・プロダクト

## ビジョン・戦略

経営、PdM（プロダクトマネージャー）、責任者に向けた戦略文書である。目指す価値と進む方向を共有し、個別の判断がその方向と矛盾しないようにする。個別機能の仕様や実装手順は決めない。区分は `stock` とする。

背景から、誰にどの価値を届け、どの状態を目指すかを説明する。対象と目標を示すとともに、今回は目指さないことと、方向を選ぶ際に守る制約を明記する。成果指標は、目標へ近づいたかを確かめるために置く。

個別の製品企画や要求は Product Brief や PRD、実現方法は設計文書で具体化する。ロードマップはこの方向を予定へ移した文書であり、戦略自体の根拠や正式な参照先にはしない。

## 製品企画の概要（Product Brief）

PdM、デザイン担当、開発者に向けた製品企画の概要である。誰のどの問題に、どの価値を提供できるかという仮説を共有し、詳細化すべき企画の輪郭を定める。詳細要件や技術設計は確定しない。区分は `stock` とする。

対象となる利用者の問題に対して、どんな解決方法で価値を提供できるかを仮説として示す。成功条件はその仮説を確かめるために置き、今回はどこまで扱うかも示す。背景となる戦略があれば、企画がどの方向に寄与するかを参照できるようにする。

仮説を合意済みの要求として扱わない。要求、対象外、受入条件は PRD で定め、実現方法とその採否は設計文書で扱う。

## PRD

PdM、開発者、QA（品質保証）担当、CS（カスタマーサポート）担当に向けた製品要求書である。誰の何の問題を、どの振る舞いで解決し、何を満たせば受け入れるかを合意する。内部アーキテクチャ、実装担当、作業進捗の管理には使わない。区分は `stock` とする。

問題の根拠、関係者に提供する価値、対象となる利用者は、業務要求と機能要求が必要な理由を支える。対象外は要求の適用範囲を限り、成功条件と受入条件は、要求が満たされたことを測定・確認する基準にする。目的だけ、または機能だけを孤立させず、それぞれが誰の問題と受入判断にどう結び付くかを説明する。

要求を満たす実現方式の選択は Design Doc や ADR、作業の分担と進捗は計画・チケット・進捗報告に置く。

## ロードマップ

経営、PdM、関係チームに向けた予定表である。期間ごとのテーマ、順序、先に必要な作業・条件を示し、どの方向へ何を進める見込みかを調整する。確定納期や個々のタスクは約束しない。区分は `flow` とする。

テーマと成果は期間に対応させ、前提や先行条件は順序が成り立つ理由として示す。予定が実現する見込みの確かさは、確定事項と仮定を混同しないために残す。戦略や PRD を参照してよいが、それらの内容を予定表へ複製しない。

実行単位の担当、期限、阻害要因はプロジェクト計画や進捗報告で管理する。完了後にも参照すべき要求・判断・結果は、対応する `stock` または `record` に残す。
