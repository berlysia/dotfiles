# 要求・仕様

## 要求仕様

PdM（プロダクトマネージャー）、開発者、QA（品質保証）担当、顧客・業務担当に向けた要求書である。必要な能力、制約、優先度を明文化し、何を満たすべきかを共有する。実現方式は固定しない。区分は `stock` とする。

各要求がなぜ必要かを根拠とともに説明し、制約や利用者への影響に照らして優先度を示す。検証方法は、要求を満たしたかを確認するために置く。設計の選択や実装計画は別文書に置く。

## ユーザーストーリー

PdM、開発者、QA担当に向けた利用者要求の記述である。利用者が何をしたいか、なぜ必要かを、実装可能な単位で示す。技術設計や進捗台帳にはしない。区分は `stock` とする。

利用者、行動、価値を結び付け、受入条件でその要求が満たされたことを確かめられるようにする。実現方法は設計文書、作業の状態は計画やチケットで扱う。

## ユースケース

業務担当、開発者、QA担当に向けた利用手順の記述である。誰がどの前提で何を行い、通常時と例外時にどう終わるかを記述する。画面の見た目だけを定める文書にはしない。区分は `stock` とする。

操作する人や外部システム、前提、通常の流れ、例外、結果を一つの利用場面として対応させる。画面状態や文言の詳細は UI 振る舞い仕様で扱う。

## 機能仕様

開発者、QA担当、PdMに向けた機能の仕様書である。入出力、状態、ルール、エラーを、実装できる詳しさで定める。アーキテクチャ判断やタスク分解は行わない。区分は `stock` とする。

入力がどの状態とルールで扱われ、どの出力またはエラーになるかを明確にする。例は規則の適用を確認するために使い、規則の代わりにしない。

## 非機能要求

開発者、SRE（信頼性エンジニアリング）担当、セキュリティ担当、QA担当に向けた品質基準の仕様書である。性能、可用性、保守性、安全性の基準を定める。具体的な製品や実装を無条件には選ばない。区分は `stock` とする。

指標、目標値、測定方法を対応させ、制約と例外で基準の適用範囲を明らかにする。実現方式の選択は設計文書に委ねる。

## API 仕様

API 利用者、開発者、QA担当に向けた外部接続の仕様書である。外部との入出力契約と互換性を定める。サーバ内部のクラス設計は説明しない。区分は `stock` とする。

エンドポイント、型、認証、エラーは利用者が呼び出しと結果を理解するための契約である。互換性はその契約を変更するときに守る条件として扱う。

## データ/イベント仕様

開発者、データ基盤担当、分析担当、QA担当に向けたデータ仕様書である。データの構造、各項目の意味、バージョン、保持期間を共有する。業務全体の手順や分析結果は記録しない。区分は `stock` とする。

各項目が何を意味し、どの型で表され、省略できるかを定める。版ごとの違いと保持期間を示し、利用者がデータをいつまで、どの定義に従って扱えるかを確認できるようにする。

## 仕様書の2つの形

要求を定める文書と、運用や監視の設定を確認する文書では、説明すべきことが異なる。前者は満たすべき振る舞いと検証方法を扱い、後者は対象ごとの設定値、適用条件、設定を確かめる方法を扱う。求める振る舞いと現在の設定を混同せず、それぞれの役割に合わせて説明する。
