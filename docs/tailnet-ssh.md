# Tailscale経由のSSH

秘密鍵は各端末でOpenSSHのEd25519鍵として生成し、その端末の`~/.ssh/tailnet-keys/`だけに保持する。
1Passwordには公開鍵・指紋・端末一覧だけを保存し、秘密鍵を保存・取得・配布しない。
Tailscale用のSSHは`IdentityAgent none`で共有Agentを使わず、その端末の秘密鍵ファイルを明示して接続する。

現在の自動生成はパスフレーズなしで、秘密鍵ファイルは600、鍵ディレクトリは700とする。
同じOSユーザーや管理者による読み取りまでは防がないため、端末のアクセス制御とディスク暗号化を前提に運用する。
端末を紛失した場合に秘密鍵を1Passwordから復元する仕組みはなく、新しい端末で新しい鍵を生成して再登録する。

公開リポジトリにはマシン一覧、IP、ユーザー名、公開鍵と端末の対応、1PasswordのアイテムIDを置かない。
一覧は1PasswordのSecure Note `Tailnet SSH inventory`の`notesPlain`に保存する。
各端末の設定はGit管理外の`~/.config/tailnet-ssh/settings.json`に保存する。
設定ファイルは600、設定ディレクトリは700とする。
ヘルパーはTypeScriptのES Modules（`.mts`）で、Node.js 24.12以降を使う。
型チェックはリポジトリの`pnpm typecheck`で行う。

## 信頼するデータと変更の確認

配布対象にできる鍵は、非公開一覧に公開鍵本体とSHA256指紋を登録した鍵だけとする。
取得した公開鍵の指紋が登録値と違えば、反映前に中止する。
端末自身の秘密鍵から導出した公開鍵も照合し、秘密鍵がない場合、指紋が違う場合、権限が600でない場合は中止する。
端末から取得した公開鍵は登録済みの現行鍵・旧鍵との照合にだけ使い、配布対象に追加しない。
端末の公開鍵が未登録の鍵へ置き換わっていた場合は、全端末への反映を中止し、その端末をローカルで確認する。

`plan`は各端末の受信設定を取得し、追加・削除する鍵の指紋、接続元の鍵の変更、旧鍵の一時保持、配布するヘルパーのハッシュを表示する。
`plan`と確認ハッシュを指定しない`sync`はSSH設定を変更しない。

```sh
node ~/.local/bin/tailnet-ssh.mts plan
# 表示された変更を確認し、出力されたコマンドを実行する
node ~/.local/bin/tailnet-ssh.mts sync --approve <表示されたハッシュ>
```

確認ハッシュは登録内容、取得した公開鍵、端末ごとの設定、known_hosts、ヘルパーの内容に対応する。
反映時に読み直した内容が違えば、書き込まずに新しいplanの確認を求める。
各受信端末でも、書き込み直前に設定のハッシュを比較する。
配布中に一部の端末で変更・障害が起きた場合はそこで中止する。反映済みの端末を自動で巻き戻す処理はない。

SSH接続では既存の`known_hosts`を使い、未知・変更されたSSHホスト鍵を自動承認しない。
Agent転送とSSHの転送設定を無効にし、登録済みの接続元の鍵を明示して使う。
受信側で管理する公開鍵は、TailscaleのIPv4・IPv6アドレス範囲からの接続に制限する。

この仕組みは、1Passwordの一覧を編集できる人と、実行するヘルパー・端末の同じユーザー権限を信頼する。
指紋の登録や確認ハッシュは独立した電子署名ではなく、変更の照合と確認のためのものである。
同じユーザー権限を奪われた場合や、改ざんされたヘルパーを実行した場合まで防ぐものではない。
`authorized_keys`の管理ブロック外にある既存の鍵は保持するため、既存の許可も別途管理する。

## 非公開一覧の形式

一覧は`version: 3`、`vault`、`machines`を持つJSONとする。
古い形式や、指紋のない登録は自動で信頼せず中止する。
実データは公開リポジトリへ追加しない。

| フィールド       | 内容                                                                      |
| ---------------- | ------------------------------------------------------------------------- |
| `name`           | SSHの別名。端末間で重複不可                                               |
| `hostname`       | 接続先のMagicDNS名またはTailscale IP                                      |
| `user`           | 接続先のOSユーザー                                                        |
| `platform`       | `darwin`または`linux`。WSLは`linux`                                       |
| `localHostname`  | OSのホスト名。大文字小文字と末尾の`.local`は区別しない                    |
| `publicKey`      | その端末で生成した現行のEd25519公開鍵本体                                 |
| `keyFingerprint` | 現行鍵の`SHA256:...`指紋                                                  |
| `previousKeys`   | 更新中だけ保持する旧鍵の配列。各要素は`publicKey`と`keyFingerprint`を持つ |

同じ接続先ユーザー、同じOS・ローカルホスト名、同じ鍵を重複登録できない。
公開鍵と指紋は、その端末で実行した`keygen`の出力と照合する。
旧鍵も公開鍵・指紋だけを1Passwordの一覧に登録する。秘密鍵を転送しない。
登録した全端末の現行鍵は、全端末の指定ユーザーに許可される。

## 新しい端末の追加

1. 新端末でTailscale、SSHサーバー、Node、dotfilesを設定する。
2. 新端末のローカルターミナルで`keygen`を実行する。
3. 出力された公開鍵・指紋と、新端末の接続情報・OSホスト名を1Passwordの非公開一覧へ追加する。
4. 既存の配布元端末で初期設定JSONを生成し、信頼できる経路で新端末へ渡す。
5. 新端末のローカルターミナルで`import`する。
6. 配布元端末で新端末のSSHホスト鍵を、端末のコンソールなど独立した経路で照合して`known_hosts`へ登録する。
7. 配布元端末で`plan`を確認し、その確認ハッシュを指定して`sync`する。
8. 新端末で接続先のSSHホスト鍵を登録し、`check`する。

```sh
node ~/.local/bin/tailnet-ssh.mts keygen
```

このコマンドは秘密鍵・公開鍵をその端末に作成し、標準出力へ公開鍵・指紋のJSONだけを出す。
秘密鍵の保存先は公開鍵のSHA256値に対応するため、更新時も既存の鍵を上書きしない。
`keygen`だけでは選択済みの接続元鍵や許可鍵を変更しない。

初期設定の生成は1Passwordの登録済み情報だけを使い、新端末へのSSH接続を必要としない。

```sh
umask 077
node ~/.local/bin/tailnet-ssh.mts bootstrap <登録した端末の別名> > /path/to/private-settings.json
```

新端末に渡した後、その端末で実行する。

```sh
node ~/.local/bin/tailnet-ssh.mts import < /path/to/private-settings.json
```

このJSONは現行鍵と、一覧に明示した更新中の旧鍵を許可する。
初期登録が終わるまでは、`sync`で新端末へ接続できない。
Tailscaleへ参加しただけでSSHの許可を得たり、自動で一覧に追加されたりはしない。

Macでは「一般 → 共有 → リモートログイン」で対象ユーザーの接続を許可する。
WSLではWSL内のTailscaleとOpenSSHサーバーを起動する。
Tailscale用のSSHはMac・WSLとも端末内の鍵ファイルを使い、Windowsの1Password SSH Agentや`wsl2-ssh-agent`に依存しない。
それらは他のSSH用途向けの既存設定として保持する。
WSLが停止している間は接続できない。

## 通常の鍵更新

1. 更新対象端末で`keygen`を実行する。旧秘密鍵はその端末に残す。
2. 非公開一覧で旧公開鍵・指紋をその端末の`previousKeys`へ移し、`publicKey`・`keyFingerprint`を新しい出力へ変更する。
3. 配布元端末で`plan`を確認して`sync --approve`する。
4. 更新した端末で`check`を実行し、その端末用の新鍵で接続できることを確認する。
5. `previousKeys`から旧公開鍵を外し、もう一度`plan`を確認して`sync --approve`する。
6. 最後に旧秘密鍵とその公開鍵ファイルを、生成した端末内で削除する。

一括反映は以下の順番で行う。

1. 全端末へ、登録済みの新旧鍵を許可する。各端末の接続元の鍵は維持する。
2. 配布元の新しい秘密鍵ファイルだけを指定して各受信端末に接続できることを確認する。
3. 各受信端末の許可を現行鍵だけへ絞り、接続元の鍵も新鍵へ切り替える。
4. 最後に配布元端末自身を切り替える。

新鍵の接続確認に失敗した場合は、旧鍵と旧接続元の設定を残した状態で中止する。
一部の端末が最終反映まで進んだ場合でも、配布元は登録済みの新旧鍵を使って再接続できる。
復旧後は新しく`plan`を確認して再実行する。

```sh
node ~/.local/bin/tailnet-ssh.mts check
```

`check`はその端末の選択済み公開鍵に対応する端末内の秘密鍵だけを使い、他の登録端末への認証を確認する。
配布元の`sync`では全端末に対応する秘密鍵が存在することも確認するが、受信端末からのネットワーク到達性までは確認できない。
新端末・更新した端末自身での確認を省かない。

旧鍵を紛失していて他の許可済み鍵でも接続できない場合は、ローカル操作での復旧が必要になる。
鍵漏洩時は通常更新中の旧鍵保持を使わず、対象端末の隔離やローカル操作を含めて旧鍵の許可を除去する。
1Passwordからの削除だけでは、接続先に残った公開鍵は失効しない。
一覧から端末を削除した場合、残る登録端末からその鍵を除去できるが、一覧から外した端末自体は更新されない。

## ローカルの再反映

`chezmoi apply`は保存済み設定を再反映する。1Passwordからの取得や他端末への一括配布は行わない。

```sh
node ~/.local/bin/tailnet-ssh.mts apply
```

`~/.ssh/config`と`authorized_keys`では、`BEGIN/END chezmoi tailnet-ssh`で囲んだ部分だけを更新する。
既存の鍵やOrbStackのIncludeは保持する。
管理ブロックのマーカーが壊れている場合は更新を中止する。
Tailscale用の管理ブロックを既存のInclude・共通設定より前に置き、`IdentityAgent none`などが先に適用されるようにする。
ブロック末尾で`Host *`へ戻し、既存のInclude・共通設定の適用範囲を保持する。
実効設定は`ssh -G <別名>`で確認する。
一括配布・接続確認では通常のSSH設定を読み込まず、Agent無効化、接続先、秘密鍵ファイル、known_hostsを明示する。
保存済み設定を先に書き込み、受信設定、接続設定、接続元の鍵の順に反映する。
途中の書き込み失敗ではエラーで終了し、保存済み設定から再反映できる。

## 旧1Password秘密鍵方式からの移行

旧鍵を新端末へコピーせず、各端末で新しい鍵を生成する。
その出力を現行の公開鍵として登録し、旧公開鍵を`previousKeys`へ登録する。
初回移行中に限り旧公開鍵の登録へ`legacyAgent: true`を付け、旧Agentによる接続を維持する。
現行鍵へこのフラグを付けることはできない。

新鍵で双方向の接続を確認したら、`previousKeys`から旧公開鍵を除去して再反映し、1Passwordの旧SSH Keyアイテムも削除する。
移行後は共有Agentを使う接続設定や旧鍵の許可を残さない。
1Passwordの通常の削除では旧アイテムがRecently Deletedに30日間残るが、その鍵による管理対象のSSH認証は既に失効している。
旧方式の一覧は自動で現行方式として扱わず、公開鍵だけのversion 3へ明示的に移行する。
