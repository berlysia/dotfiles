# ADR-0057: route に先読みと週枠の余りを足し、レビュアーを route と台帳に乗せる

## Status

accepted (2026-10-29)

ADR-0055 K5 の週枠の判定と K6 の試す候補を、この ADR で広げた。
ADR-0055 の本文は書き換えない。
ADR-0055 の「線」を、この ADR から「目安」と呼ぶ。

## Context

2026-10-29、利用者は followups 文書の節「route を週枠の消費に合わせて改める」を始めるよう求めた。
節は次の 3 案を挙げていた。

- 予想で判定する（usage-line の「リセット時の予想」が 100% を超えたら ahead とする）
- レビュアーを route の対象に入れる（Claude の週枠が ahead のとき、定型のレビュアーを Codex か OpenCode に回す）
- 余っている外部の枠を使う（リセットが近く、目安との差が大きい外部を、規模を問わず試す候補に出す）

調べると、次の事実が分かった。

- 2026-10-29 03:31Z の ai-usage では、Claude の週は 11% で、週の始まりから約 3.5 時間だった。目安は 16.4% なので week は under になる
  - 作業中の速さは 3.17pt/h だった。このまま続ければ数時間後に目安を超えるが、その間 route は sonnet を勧め続ける
- 同じ時点で、OpenCode の週は 4% で、リセットまで約 2.9 日だった。リセットで失われる量が大きいが、規模 S 以外では何も示さない
- usage-line の予想をそのまま使うと、作業中はほぼ常に ahead になる
  - 予想は「直近の連続した作業時間の中での速さ」を、睡眠を含むリセットまでの壁時計の時間に掛ける。観測の区間は、サンプルの間隔が 25 分を超えると打ち切られる
  - 予想が 100% を超える条件は、速さが (100 − 使用率) ÷ リセットまでの時間 を上回ること。この時点なら約 0.54pt/h である。週の枠を 7 日、1 日 10 時間の作業で使い切る速さが約 1.43pt/h なので、それより遅い作業でも超える
  - 予想が答える問いは「今の速さで作業し続けたら」であり、route が知りたい「週の終わりに足りるか」とは別である
- レビュアーは週枠の 13〜20% を使っていた（メインループが 7〜8 割）
- 直近 3 日のレビュアーの Agent は約 820 件あり、約 720 件（約 88%）が model を省いていた
  - Mod は入力の model が sonnet の Agent だけを拾うので、省いた Agent は台帳に載らない。規約は既に「model を明示する」と定めているのに、この割合だった
- Codex 経路のレビュアーは、Agent を `model: "haiku"` で起動する。中の Bash は Mod の `tool.call` に届き、codex-cli の行として載る
  - 2026-10-29 の probe では、subagent の中の Bash で起動した `opencode run` が pending になった

## Decision

この ADR の決定を K1〜K6 と書く。ADR-0055 の決定は「ADR-0055 K5」のように ADR 名を付けて書く。

- **K1: Claude の週枠に、作業中の速さで 3 時間以内に目安を超えるかの先読みを足す。**
  - 目安の判定が under で、かつ 使用率 + 速さ × 3 時間 が 3 時間後の目安を超えるとき、ahead にする。目安の判定が ahead・exhausted・unknown のときは上書きしない。等号は under に倒す
  - 3 時間後の目安は、今の目安と同じ式で、100 で頭打ちになる。リセットまでが 3 時間未満のときは、リセットの後まで外挿することになるので先読みを使わない
  - 速さは usage-line が書く予想ファイルの値を読む。観測時間が 2 時間未満のときは使わない。週の使用率は整数なので、1 時間の観測では速さの刻みが 1pt/h になり、目安の傾き（約 0.595pt/h）を超えてしまうためである
  - 使用率は ai-usage の今の値、予想ファイルは最大 25 分古い。両者の時刻のずれによる誤差は 25 分 × 速さ程度で、閾値の粗さより小さいので受け入れる
  - rate が目安の傾き以下でも、頭打ちの近くでは ahead になりうる。反例は、目安 99.5%、使用率 99.4%、速さ 0.5pt/h、リセットまで約 24.8 時間のとき。3 時間後の目安は 100 で、99.4 + 1.5 = 100.9 がそれを超えるので ahead になる
  - 出力は、ahead の理由を目安と先読みで分ける。規則 2 の行に `(先読み)` を付け、「窓:」の行の week の値は変えない
  - 外部の週枠は目安だけで判定する。規則 2 で Claude の側は振り分けの引き金なので、早く引くほど Claude の枠が残る。外部の側は「under なら渡してよい」という条件で、先読みで狭めると外部の記録が増えない。そもそも外部には速さの時系列が無い
- **K2: 予想ファイルは読むだけにし、usage-line のコードは import しない。**
  - usage-line は `~/.claude/mods/` に、delegation は `~/.local/share/delegation/` に別々に配備される。別の配備物の import が古くなって壊れた事故が、ADR-0055 の Consequences にある。予想ファイルは版つき（`v: 1`）の出力で、statusline が既に読んでいる
  - 置き場の規則は usage-line と同じにする。`XDG_RUNTIME_DIR` が絶対パスで `..` を含まなければその下、そうでなければ `/var/folders/` で始まる `TMPDIR` の下の `usage-line/` である。テストは環境変数でディレクトリを差し替える
  - 読むファイルは、名前が `^[A-Za-z0-9-]{1,128}\.json$` に合うものを昇順に並べた先頭の 256 件までに限る
  - 守りは 3 層にする。(1) lstat で通常ファイル（symlink は追わない）・自分の uid・16KB 以下を確かめる。(2) symlink を追わず、待たない指定で開く。(3) 開いた後に fstat で通常ファイルと大きさを確かめ直す。FIFO で止まらないのは、どの層も単独で拒否するか待たずに返るためである
  - 採るファイルは、次をすべて満たすもののうち `at` が最大のもの。同値なら名前の昇順で最初のもの
    - `v` が 1
    - `at` が現在から 60 秒先〜25 分前の範囲にある
    - 週の `resetsAt` と、ai-usage の Claude の週の `resetsAt` の差が 1 時間以内
    - 速さが 0 以上 100 以下の有限の数
    - 観測時間が 2 時間以上 168 時間以下の有限の数
  - 先読みを使えない理由は 6 つの enum で出す。直し方が違うので分ける
    - `no-dir`: この環境では usage-line が書けない。agent-vm などでは常にこれになりうる
    - `no-file`: usage-line の Mod が動いていない
    - `stale`: 25 分以内に作業した session が無い（通常の状態）
    - `mismatch`: 週が切り替わった直後か、単位の取り違え
    - `no-rate`: 形の変化か、速さの値の異常。JSON が壊れている、`v` が 1 でない、必要な欄が object でないときもここに入る
    - `short`: 観測が 2 時間未満（作業を始めた直後の通常の状態）
  - 複数のファイルが別々の理由で落ちたときは、検査を最も先まで進んだファイルの理由を出す。順は `no-file` < `stale` < `mismatch` < `no-rate` < `short`。同じ入力なら同じ理由が出る
  - route は「窓:」の下に 1 行を足す。読めたときは速さと、目安を超えるまでの時間（小数 1 桁）を出し、すでに超えているときと超えないときはその旨を出す。読めないときは理由を出す。出力に通すのは enum と数だけで、ファイル名、JSON の中の文字列、例外の文、ディレクトリのパスは出さない
  - 複製のずれは、予想ファイルの形と置き場の規則を 1 つの fixture に固定して検出する。delegation のテストは fixture を読み、usage-line の本物の関数に同じ入力を通して照合する。この照合は CI が実行するテストの側で行う（CI は Mod のテストを走らせない）
- **K3: 余っている外部の枠を「試す候補」に出す。推奨は変えない。**
  - 余り = (100 − 使用率) × (1 − リセットまでの時間 ÷ 週の長さ)。usage-budget の式と同じで、週の長さは ai-usage の値を使う。リセット時刻か週の長さが読めないときは出さない
  - 出す条件は、kind が mechanical・triage・draft で、外部の 5 時間枠と週枠がどちらも under、余りが 25pt 以上のとき。規模は問わない
    - 種類を絞るのは、mechanical と triage は出力の形で正しさを確かめられ、draft はメインループが読んでから使うため。impl・research・review は誤りが後の判断に入り込むので、記録の無い外部へ規模 L で渡す候補にはしない
    - 25pt は目安の約 1.75 日分である。1 日分に満たない余りは、行を毎回出すほどの量ではない
  - 週枠は provider のものなので、行は provider ごとの 1 行とする。Terra と Luna max は Codex の週を共有する。行に出す委譲先は、その kind の順（ADR-0056）で最初のものとする。mechanical・triage では Luna max、それ以外では Terra である
  - 推奨がその外部なら出さない。規模 S で記録が足りない外部の試す候補（ADR-0055 K6 の 4）と同じ外部を選んだときは 1 行にまとめ、末尾に余りを足す
  - 2026-10-29 03:31Z の値では、OpenCode は 96 × (1 − 69.6 ÷ 168) ≈ 56pt で出る。Codex は週が ahead なので、余りを見る前に条件から外れる
  - この決定は ADR-0063 により上書きされた。
- **K4: model を省いた Agent も、agent 定義が Claude のモデルを指定していれば台帳に載せる。**
  - `delegation open` は、Agent の model が文字列ならそのまま判定し、`codex:codex-rescue` も今までどおりにする。model が無いときは、subagent_type が `^[a-z0-9][a-z0-9-]{0,39}$` に合うときだけ `$HOME/.claude/agents/<名前>.md` を読む。合わなければパスを組まず、対象外（終了コード 1）とする
  - 読み方は K2 と同じ 3 層の守りで、64KB 以下に限る。agents ディレクトリそのものが symlink であることは許す（chezmoi の配備で symlink になりうる。symlink を追わない指定が守るのは最後の要素だけ）
  - frontmatter は、先頭の BOM を 1 つだけ除いた 1 行目が `---` で、次の `---` までとする。CRLF は許す。行頭が `model:` の行がちょうど 1 行のときだけ読む。0 行と 2 行以上は対象外とする。重複キーの扱いは YAML の実装ごとに違い、後の値を採るものが多く、最初の行を採ると実際に使われるモデルと食い違うため、決められない入力は載せない
  - `model:sonnet`（コロンの直後に空白が無い）は YAML ではキーではなく 1 つの文字列なので、`model:` の行とみなさない
  - 値は sonnet・opus・haiku・fable のどれかと完全に一致したときだけ受け入れる。`inherit`、一覧に無い値、空、末尾のコメント付きは対象外とする。定義の経路が対象外のとき、stderr には何も書かない
  - Mod は、model が sonnet、`codex:codex-rescue`、または model を持たず名前が上の正規表現に合う Agent を CLI に渡す。model が haiku などの Agent は渡さない。Codex 経路のレビュアーを、Agent と中の Bash で二重に載せないためである。この区別は、Codex 経路の Agent を `model: "haiku"` と明示して起動することに依存する
  - Mod と CLI の v1 の入出力（stdin の欄、出力の 4 語、終了コード 0 / 1）の形は変えない。変わるのは、model の無い Agent を CLI が対象外と答えうることだけである。CLI と Mod は同じ commit で変える。引数なしの `chezmoi apply` は CLI を先に書いてから Mod を `~/.claude/mods/` に同期するので、新しい Mod が古い CLI と組むことは無い
  - 台帳の model は agent 定義の値で、環境変数などで実際のモデルが変わっても追わない
- **K5: レビュアーの委譲は、規約で route を引き、triage の後に記録する。**
  - round ごとに 1 回、レビュアーを起動する前に `delegation route --kind review` を引く。同じ round の全レビュアーに同じ推奨を使う
  - 規模は、レビュー対象の文書の、最初の `## Reviewer Outputs` の行より前の行数で決める（見出しが無ければ全行）。150 行以下は S、151〜400 行は M、401 行以上は L である。誰が数えても同じ値になり、round を重ねるだけでは規模が変わらない
  - 推奨が codex（Terra か Luna max）なら、帳簿に載るレビュアーを `executor: codex` の経路で起動する。依頼の model と effort は推奨行の値を書き、Agent は `model: "haiku"` を必ず明示する。推奨が sonnet か opencode のとき、または route が失敗したときは、今までどおり Claude で起動する。OpenCode でレビュアーを動かす経路は無いので、opencode を勧められても sonnet で起動する
  - triage の後、各レビュアーの委譲を `delegation record` で `--kind review` を付けて記録する。verdict は、採用した指摘をそのまま反映したら adopted、一部を直して反映したら patched、全部を除外したら discarded とする。Codex の失敗で Claude に切り替えたときも、記録するのは結果を使った行だけで、redone は使わない
  - Codex 経路のレビュアーの行は `[delegation]` の行に出ないので、ADR-0056 の手順で pending の行を選んで記録する。この ADR は手順を持たない
  - 毎回読む operator guide（workflow.md）には、共通フロー 5.4 と 6 に 1 行ずつ、route を引くことと記録することだけを書く。規模の区切り、起動の分け方、verdict の決め方は reference skill の節に置く。operator guide は全 session で読み込まれ、大きさの上限をテストで守っている。この 2 行はレビューの round ごとに読まれる必要があるので、上限を 512 バイト上げた
  - レビュアーの推奨文を出す hook は変えない。規約の 1 か所で足りる
  - OpenCode でレビュアーを動かす経路（runner と各 agent 定義の分岐）は作らない。外部でのレビューの質がまだ記録に無いため、followups に残す
- **K6: 決定はこの ADR に書き、ADR-0055 は Status のポインタで辿れるようにする。**
  - route の出力の 1 行目は `delegation route v1` のままで、既存の行の形は変えず、行を足すだけにする
  - 閾値の見直しを起動する観測は Consequences に書く

## 却下した代替案

- **目安の猶予を 1 日から 0.5 日に縮める**: 猶予は週の初めの 1 回の委譲で ahead にしないための値である。0.5 日にしても、速さを見ないので、ゆっくり使う日にも同じ時刻で ahead になり、速く使う日に先回りする効果は無い
- **試す候補から規模 S の条件を外すだけにする**: 余っていない外部まで、規模 L の試す候補に出る
- **規約に「レビュアーにも model を明示する」と 1 行足すだけにする**: 同じ趣旨の規約が既にあり、それでも約 88% が省いていた。足しても結果は変わらない見込みが高い
- **各 provider の使用率の時系列を持ち、リセット時の使用率を区間つきで予想して配分する**: 時系列があるのは Claude だけで、Codex と OpenCode は今の値しか無い。作るには取得の常駐が要る（ADR-0041 K14 が却下した案）。委譲 1 回の消費量は、並行 session が混ざるので測らないと ADR-0055 が決めた
- **usage-line の予想が 100% を超えたら ahead とする**: 作業中はほぼ常に ahead になる（Context）。作業中の速さを 3 時間に限って外挿する先読みで、この過大さを 3 時間分にとどめた

## Consequences

- リスクは次のとおり（ID は振り直さない）
  - R1: usage-line の Mod が動いていない、または予想ファイルの形が変わると、先読みは止まる。理由を毎回 1 行出し、形は `v` と型で確かめ、fixture の照合で形の変化を CI が検出する
  - R2: 速さは連続した観測区間の平均で、分母は観測時間である。2 時間の観測なら、10 分の山は 1/12 の重みで残る。並列のレビュアーのような山で、先読みが ahead になりうる。観測 2 時間の下限で刻みを 0.5pt/h にした。誤って ahead にしたときの損は外部へ渡す手間で、見逃したときの損（週の途中で Claude の枠が尽きる）より小さい
  - R3: model を省いた Agent のたびに CLI の起動が増える。ADR-0055 の実測は 1 回約 100ms で、受け入れた上限は 600ms だった。この ADR の実装で測った `delegation open` は、agent 定義が読めたとき 64ms、読めなかったとき 57ms だった（2 回目以降の実行、load average 6.2）。600ms は CLI 単体の上限で、Mod が待つ上限は 300ms である。超えると pending を作らずに Agent が進み、記録が抜ける。測った値は 300ms の約 1/5 である
  - R4: レビュアーの記録が増えると、記録待ちと lapse も増える。`[delegation]` の行が出なかった委譲は lapse になる。割合は `delegation review` で見る
  - R5: 予想ファイルの置き場は、他の利用者が書けないことを前提にする。usage-line と同じ規則を使い、所有者と通常ファイルを確かめる
  - R6: probe で作った pending（opencode、2026-10-29）を lapse にしたので、opencode の組の lapse が 1 件増えた。件数が少ないうちは、review の表示で読み替える
  - R7: `chezmoi apply` が途中で失敗し、Mod だけが新しくなると、古い CLI は model の無い Agent をすべて開き、組み込みの agent まで unknown で載る。載った行は、review の unknown の組で見つかる。pending が上限（200 件）に達すると古いものから lapse になるので、記録したい pending が押し出されうる
- S5 を規約だけで守ることを受け入れた。route を引かずにレビュアーを起動でき、強制する機構は無い。推奨文の hook に組み込むかは、観測の 4 つ目で決める
- 閾値（3 時間、観測 2 時間、25pt、25 分、1 時間）と、規模の区切り（150 行・400 行）は、計測から決めた値ではない。次の観測 4 つで見直す
  - 先読みで ahead になった週のうち、実際に週の目安を超えた割合
  - 試す候補を採った委譲の件数と採用率
  - `short`・`stale` が出る割合
  - route を引かずに起動されたレビュアーの割合
  - 観測は、route か record が振り返りを促したときに `delegation review` の表示で読む（`model-offloading.md` の委譲の手順 5）
- review の規模は行数で決め、impl などほかの種類の規模と基準が違う。route は種類と規模の組で数えるので集計は混ざらない。2026-10-29 までのレビュアーの記録は、手で付けた M で、文書の長さを区別していない
- Codex 経路のレビュアーの記録は ADR-0056 の手順に従う。`bad-arguments` 以外の理由で失敗して Claude でやり直した Codex の起動の行は、その手順では閉じられず、7 日で lapse になる
- K4 の範囲の限界
  - プロジェクトの `.claude/agents/` と plugin の agent は読まない。plugin の名前は `:` を含むので正規表現で外れる。Explore などの組み込みの agent は定義ファイルが無いので載らない
  - プロジェクトの `.claude/agents/` に同名の定義があり、そちらが使われても、CLI は `$HOME/.claude/agents` の model で載せる
  - frontmatter を行で読むので、harness の YAML パーサと解釈が食い違う書き方（複数行の引用符の中の `model:` の行など）では、別の model で載るか載らない。害は台帳の記録の違いにとどまる
  - 定義由来の行の model は、呼び出し時に実際に使われたモデルではなく、`$HOME` の定義の値である。route は記録済みの行を種類と規模の組で数えるので、`record` で kind が付いた後に、その組の sonnet の件数と採用率に入る。移行の前に model を省いて起動した Agent は台帳に無いので、移行の前後で件数の連続性は切れる
  - `executor: codex` の依頼を model を省いて起動すると、Agent の行と中の Bash の行の 2 つが載る。規約に依存し、Mod では防げない
- K2 の範囲の限界
  - fstat の段の uid 検査は、別の uid のファイルを root なしで作れないため、テストで落とせない。コードを読んで確かめるものとして受け入れた
  - ディレクトリそのものの所有者と書き込み権限は確かめない。中のファイルは自分の uid のものしか採らないので、他人にできるのはファイルを隠す・消すことによる `no-file` への倒しだけで、値は注入できない
  - ディレクトリの全件を読んでから並べて 256 件に切る（順序を保証するため）。件数の多さは、書き込めるのは同じ uid のプロセスだけという前提なので受け入れる
  - 形が壊れたファイルは、同じ置き場に本物の stale のファイルがあっても `no-rate` が勝つ。形の変化はすべてのファイルに及ぶので、診断としてこちらを優先した
- usage-line への制約: 予想ファイルの `ratePerHour`・`observedMs` の意味か形を変えるときは `v` を上げる
- テストの実行時間が増えた。同じ load の下で、route のテストは以前の約 1.25 倍になった。プロセスを起動するテストのファイルは、load 7〜8 で 1.8〜2.1 秒から 2.8〜3.0 秒になり、1 ファイル 3 秒の上限に収まるかは確かめられていない。超えたときは、別の課題として、関数の呼び出しに置き換えるかファイルを分けて並列にする
- 「推奨:」「試す候補:」の行を読むのはメインループとテストだけである。試す候補の行が増える（最大 2 行）
