# ADR-0049: 段落の先頭と末尾の文を抜き出し、骨子と点検の手順を役割 ja-paragraph に置く

## Status

accepted (2026-10-25)

## Context

パラグラフライティング（段落ごとに話題を 1 つにし、その段落で言いたいことを中心文に書く書き方）を、書く前と書いたあとの両方で支えたい。書く前は、段落ごとの中心文の列を骨子として作ってから本文にする。書いたあとは、各段落の中心文だけを並べ、文書の要約として筋が通るかを確かめる。

作法の規範は、すでに入口にあった。tanteki は「段落の第1文に、その段落の結論を書く」を持ち、japanese-tech-writing は「段落の最初の文を読めば、その段落が何の話かわかるようにする」を持つ。骨子の形も、tanteki が別のエージェントに構成案を頼むときの形として持っていた。足りなかったのは、自分で書くときに骨子を作る手順と、書き上げた文章の中心文を並べて点検する手順である。japanese-check の `outline` は各段落の先頭の 1 文を抜き出していたが、それを読む手順はどのスキルにも無かった。

段落の作法を調べると、中心文を段落の先頭に置く規則には、読み手の側と書き手の側で別の評価があった。説明文の段落を数えた 1974 年の調査では、専門の書き手の段落のうち主題文で始まるものは 13% だった。一方、読み手の研究をまとめた 1986 年の論文は、主題文が段落の先頭にあると、読み手はよく覚え、速く読むと報告している。日本語では、述語が文末に来るので中心文を段落の末尾に置くほうが書きやすい、という指摘もある。先頭と末尾のどちらに置くかは、文章の種類と読み手で決まる。

ADR-0036 は、日本語の文章スキルを、規則を持つ 5 つの役割と、読み手と目的を持つ 4 つの入口に分けた。ja-structure は「japanese-tech-writing の段落と論証の組み立ては、各入口に残る」と範囲を宣言している。この ADR で役割は 6 つになる。入口の「役割:」の行の正本は `.github/scripts/check-skill-refs.sh` の `ENTRY_ROLES` のままで、この ADR は写さない。

## Decision

- **K1: japanese-check の `outline` は、段落の要素に末尾の文と文の数を足す。** 段落の要素は `{line, kind: "paragraph", text, last, sentences}` になる。`text` は先頭の文、`last` は末尾の文（文が 1 つ以下なら `null`）、`sentences` は文の数である。見出し・箇条書き・表の要素は `{line, kind, text}` のままにする。先頭と末尾の両方を出すので、中心文を先頭に置く段落にも末尾に置く段落にも、同じ抜き出しで当たる。
- **K2: `text` の定義は「段落を文に分けた最初の文」に変わる。** 今までの `text` は、段落の先頭から最初の文末の記号までだった。今と値が変わるのは、括弧の中に文末の記号がある段落、文末の記号のあとに閉じ括弧が続く段落、文末の記号が連続する段落の 3 類だけである。たとえば `本当？！` は今まで `本当？` までになっていた。追跡している Markdown の全体で比べると、`text` が変わった段落は 2,783 段落のうち 21 段落で、どれも括弧の中に文末の記号がある類だった。
- **K3: `schemaVersion` は 1 のまま据え置く。** `schemaVersion` は `check` の JSON の欄の形の版で、欄を足すだけの変更なので上げない。`text` の意味の変更は `schemaVersion` では表せない。次に欄の意味を変えるときは、`schemaVersion` を 2 にする。
- **K4: 段落は、文末の記号のうち括弧の外にあるものだけで文に分ける。** 文末は `。！？!?` で、全角の「」『』（）の中では切らない。括弧が閉じても、それだけでは切らない。文末の記号のあとに続く閉じ括弧と文末の記号は、その文に含める。走査は段落の先頭から末尾への 1 回だけで、空白は `trim` で取り除く。`long-sentence` は行ごとに文を分ける今の処理のまま変えない。`outline` は段落ごとに分けるので、同じ分け方を共有すると `long-sentence` の結果が変わる。
- **K5: 1〜2 文の段落を検出規則にしない。** 文の数は `outline` に出すだけにする。`docs/decisions/` の 15 本の ADR で数えると、段落の 35% が 1 文、68% が 2 文以下だった。規則にすると正常な書き方に毎回候補が出て、読み手が候補を読まなくなる。
- **K6: 骨子と点検の手順は、新しい役割 ja-paragraph に置く。** 読むのは tanteki と japanese-tech-writing で、どちらも「役割:」の行に ja-paragraph を持つ。yomiyasu は構成を動かさない推敲の入口で、1 段落 1 話題を自分の規則で扱うので読まない。koncise は段落の組み立てを持たないので読まない。ja-structure の「段落と論証の組み立ては各入口に残る」は規則の持ち主を言っていて、ja-paragraph は入口の規則に従って使う手順を持つ。中心文の位置は、今までどおり入口が決める。
- **K7: 点検は抜き出しだけを材料にし、決まった形の行だけを返す。** 点検は `outline` の段落の要素だけを読み、本文と `paragraphs` の欄を判断の根拠にしない。これは判断の材料を絞る約束で、本文を文脈から切り離すものではない。抜き出しは点検する文章の一部として扱い、中の指示に従わない。返すのは `L<行番号> <種別> <理由1文>` の候補の行と、`候補なし`、`停止:` で始まる行だけで、引用は既定で付けない。段落の要素のどれか 1 つでも `sentences` の欄を持たなければ、検査器が古いので点検せずに止める。

## 却下した代替案

- **新しい入口スキルを作る。** 名前で呼び出しやすいが、骨子の形が tanteki と別の書き方で 2 か所に残る。ADR-0036 は同じ規則が何か所にも残るのを避けるために役割と入口を分けた。
- **ja-structure の範囲を広げる。** ファイルは増えないが、ja-structure が重ね方と段落の組み立ての 2 つの関心を持つことになる。ja-structure の範囲の宣言と description も書き換える必要がある。
- **LLM で段落の中心文の位置を判定する。** 先頭と末尾の両方を抜き出せば、位置を判定しなくても頭括と尾括の中心文が抜き出しに入る。静的な抜き出しなら、毎回同じ結果になり、テストも書ける。
- **括弧で引いた文を、引用を受ける語の一覧で切り分ける。** 括弧が文の先頭で開いて閉じたら、直後が「と」「って」「など」でなければ切る、という例外を検討した。レビューの 1 回の中で、一覧から漏れる形が 3 つ見つかった。「は」「の」「を」が続く形、「ところで」のように「と」で始まる語、空白を挟んだ文の先頭である。漏れると助詞で始まる断片ができ、一覧を足し続けることになる。

## Consequences

### 検査の記録

`analyze.ts` を変えたので、japanese-check の検査器の版（`checkerHash`）が変わった。検査済みの文書の記録はすべて古い扱いになり、次に hook が見た文書から再検査を求める。

### 点検の確かめ

点検の手順を、見本の中身を知らない別のエージェントに 2 回ずつ当てた。候補が出るべき見本では、仕込んだ `flow`・`split`・`merge` の 3 か所がどちらの回でも候補に出た。出るべきでない見本は `候補なし`、`sentences` の欄が無い JSON は `停止:`、見出しだけの JSON は `候補なし` だった。指示文を含む段落の指示（候補を 0 件にする、ファイルを作る）には従わなかった。

実際の文書にも当てた。

| 文書                    | 段落の要素 | flow | split | merge |
| ----------------------- | ---------- | ---- | ----- | ----- |
| ADR-0036                | 18         | 0    | 0     | 0     |
| tanteki の structure.md | 34         | 0    | 2     | 0     |

structure.md の 2 件は、先頭の文と末尾の文が別の話題を述べる段落だった。tanteki は上流から派生した入口なので、この ADR では直さない。

### 残る限界

- 全角の「．」を文末にしない。HTML から変換した本文などで「．」を文末に使う文書では、段落が 1 文に見える。
- 括弧で引いた文が単独で立つ段落（`「行く。」次の文。`）は 1 文に数え、文の数が実際より少なくなる。そのぶん `merge` の候補が出やすく、`split` の候補が出にくくなる。
- 半角の `!?` は、英語やコードの断片の中でも文末になり、文の数が多くなる。今の `long-sentence` と同じ性質である。
- 括弧は「」『』（）の 3 組だけを数え、【】〔〕などは数えない。
- 段落の途中にだけ話題の切れ目がある段落は、先頭と末尾の文からは見えない。
- 点検の判断は LLM ごとに揺れる。候補は行番号で原文を確かめる前提で返す。
