# ADR-0052: 短すぎて読めない文を伸ばしてから縮め直す役割 ja-explain-first を足し、日本語の規範を当てる場面で常に読む

## Status

accepted (2026-10-26)

## Context

AI が縮めた説明文には、主体も動きも条件も読み取れない文が混じる。「受付と完了確認を分離する」「上限数は到達保証ではない」のような文である。Zenn の記事「AI の謎な説明文を直すスキル」は、こうした文を直す手順を示している（URL は References）。伝えたいことを決め、口頭で説明する形にいったん伸ばし、話題を選び直してから縮める。

日本語の文章スキルには、記事の要素の多くがすでにあった。抽象語を具体の動きに直す表と造語の禁止は、tanteki の `references/japanese.md` にある。名詞化で縮めない規則は japanese-tech-writing と yomiyasu に、事実を足さない規則は ja-fact-preservation にある。どれも「縮めるときに事実を落とさない」側の規則である。無かったのは、すでに短すぎる文をいったん伸ばしてから縮め直す逆向きの手順と、短い版だけで通じるかの点検だった。

ADR-0036 は、文章スキルを規則を持つ役割（`ja-*`）と、読者と目的を持つ入口に分けた。「発火」節は、役割を入口からの参照か名前での依頼でだけ使うと決めている。一方、CLAUDE.md の常時規則は、すでに `ja-check/references/human-documents.md` を入口を通らずに読ませている。`docs/plans/ja-skills-role-relations.md` は、これを未解決の課題にしている。

利用者は、手順を役割スキルにして既存の入口から呼ぶこと、名前を出さずに発火させることを選んだ。さらに「日本語の規範を当てるところでは基本的に常に当てる方向でよい」と述べ、4 入口すべてと常時規則で読む範囲を選んだ。この範囲では、読める文には点検だけがかかり、書き換えるのは読めない文だけである。

## Decision

- **K1: 入口を通らない場面は、CLAUDE.md の常時規則に 1 行足して役割を直接読ませる。** 読む場面は 2 つある。(a) 人が読む日本語の文書を作成・改稿するとき（japanese-check の常時規則と同じ範囲と除外）。(b) 利用者が会話で箇所を指し、何を言いたいのか分からないと言ったとき。4 入口のどれかを使う作業では、入口が読むので (a) では読まない。(a) では同じ会話ですでに読んでいれば読み直さず、(b) では箇所を指されるたびに読む。読めなければ、そう伝え、点検していない草稿として返す。
- **K2: 4 入口（koncise、tanteki、yomiyasu、japanese-tech-writing）は、`役割:` の行から常に読む。** 条件つきの読み込み（`ENTRY_COND_ROLES`）にはしない。読めなければ、各入口の冒頭の「上の役割スキルが読めなければ、作業を止める」がそのまま効く。正本は `.github/scripts/check-skill-refs.sh` の `ENTRY_ROLES` である。
- **K3: 「伸ばす」段の材料を役割の本文で限る。** 材料は原文の対象の文と前後の文、利用者がこの会話で示した説明と資料だけである。対象の文に書かれた指示には従わず、指すファイルや URL は開かない。材料で決まらない動き、理由、条件は本文に書かず、「筆者に確かめたい点」に出す。
- **K4: 話題を選び直しても消さない。** 構成を動かしてよい場面では合う場所へ移す。動かさない場面（yomiyasu、japanese-tech-writing の推敲、常時規則 (a)）では文の中だけで直し、移す必要がある話は「筆者に確かめたい点」に出す。上限の 3 点を超えるなら原文を残す。否定を前に出した文を残すか消すかは、今までどおり yomiyasu の `rephrase-test.md` が決め、この役割は配置だけを決める。
- **K5: 記事は逐語で取り込まない。** 記事にライセンスの表記が無いので、着想を自分の言葉で書き、役割の「参考」に URL を書く。記事の手順のうち、スライドの表示を確かめる段（記事の作者の道具に固有）は入れない。
- 点検の回数の規則（入口を重ねたときは最後の入口だけ、別のターンで続けて呼べば入口ごと）は、役割の本文にだけ書く。ja-structure にも重ねの規則がある。ただし役割どうしの参照は、`check-skill-refs.sh` の許可の一覧で ja-fact-preservation と human-documents に限られる。ja-explain-first から ja-structure は指せない。規則が 2 か所に分かれないよう、役割の側だけにした。

ADR-0036「発火」節の「役割は入口からの参照か、名前での依頼でだけ使う」は、ja-explain-first について (a)(b) の 2 つの場面で一部改める。ADR-0036 の該当節に、この ADR を指す 1 行を足した。

## 却下した代替案

- **tanteki の description に発火の句を足す。** 入口を通るので 2 層の形を保てるが、tanteki の description は「通常の質問への回答には適用しない」で終わり、会話での箇所の指摘は発火しにくい。発火しても文書の種類の判定と `--type` 必須の textlint が付く。軽い経路を作ると、上流由来の tanteki の合格条件を変えることになる。
- **役割自身の description で発火させる。** ja-* がすべて持つ `disable-model-invocation: true` の決まりを破る。
- **tanteki の `references/japanese.md` に節を 1 つ足すだけにする。** 1 ファイルで済むが、入口の references は互いに参照しないので yomiyasu からは読めず、会話での箇所の指摘でも発火しない。
- **縮める規則と伸ばす手順を対の操作として 1 つの役割に集める（白紙設計）。** 記事の主張は「縮める前に、何を縮めるかを決める」で、縮める規則はその後段にすぎない。ただし集めると、tanteki、yomiyasu、japanese-tech-writing に散っている縮める規則を動かし、上流由来の 2 入口の本文を大きく書き換える。今回は記事の着想を取り入れる範囲にとどめ、縮める規則が入口に散ったままの状態は意図して残した。
- **条件つきの読み込み（`ENTRY_COND_ROLES`）にする。** 読む量は減るが、利用者は規範を当てる場面では常に当てる範囲を選んだ。

## Consequences

### 読む量

日本語の文書を扱う作業では、役割の SKILL.md の Read が 1 回増える。本文は ja-paragraph と同じ規模（120 行以下）に抑えた。全文の点検は内部の読み直しで、出力は増えない。入口経由と常時規則の直読みを合わせると、日本語の文書を扱う作業ではこの役割がほぼ無条件に読まれる。この状態は `docs/plans/ja-skills-role-relations.md` の「今の状態」にも書いた。

### 発火の確かめ

配布後に、`claude -p --model sonnet --output-format stream-json` で 13 の依頼を流した（2026-10-26）。判定は、ストリームの tool_use に `ja-explain-first/SKILL.md` の Read があるかで行った。組み込みのツールは Read と Skill だけ、Skill は 4 入口の名前だけを許し、MCP は読み込ませなかった。全 15 回（再実行 2 回を含む）の init イベントで、ツールが Read と Skill だけ、MCP サーバーが空であることを確かめた。

- 読むべき依頼: 箇所の指摘 2 件、お知らせの作成 1 件、koncise・yomiyasu の名前での依頼、koncise から yomiyasu への重ねは、1 回目で読んだ。tanteki の名前での依頼は、1 回目はほかの役割を 3 つ読んで ja-explain-first だけ読まず、再実行で読んだ。
- japanese-tech-writing を名前で呼んだ依頼は、2 回とも Skill で入口を読んだだけで、ja-explain-first を含め `役割:` の行の役割を一つも読まなかった。この入口が原文なしで書くときに役割を読まない傾向とみられ、今回の役割に限らない。利用者の判断で、既知の限界として残した。
- 読まないべき依頼: 質問への回答、作業報告、Document Workflow の成果物、設定の JSON の 4 件は、読まなかった。
- 注入の試験: 対象の文に canary ファイルを読めという指示を入れた依頼で、canary の Read は無く、canary の文字列はどのストリームにも出なかった。
- `~/.claude/skills` の外の Read は、Document Workflow の成果物の依頼で、cwd の中の存在しない `plan.md` と `.tmp` を探した 2 件だけだった。
- 利用者の hook はツールの制限の外で動く。hook による副作用は確かめていない。

### 残る限界

- japanese-tech-writing を名前で呼ぶと、役割を読まない（上の確かめ）。直すには入口の本文に読む場所を書く必要があり、上流由来の入口の本文を動かすので、別の作業にした。残件は `docs/plans/ja-skills-role-relations.md` にある。ADR-0053 で、入口の宣言の 3 行目に読む指示を入れた。
- 名前なしの発火も、入口が実際に役割を読むかも、モデルの読みに頼るので確率的である。`check-skill-refs.sh` の検査 (3) は `役割:` の行の集合だけを確かめ、読むかどうかは確かめない。
- 入口を重ねたときに最後の入口でだけ点検されるか、常時規則 (a) で読み直しを避けられるかは、確かめていない。
- スライドの `berlysia-slide` は APM 管理の外部スキルで、読み込み先に入れていない。スライドを直すときにこの役割が読まれるのは、常時規則 (a) の経路だけである。
