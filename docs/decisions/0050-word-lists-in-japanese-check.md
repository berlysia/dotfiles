# ADR-0050: 語で検出する規則の語を japanese-check の一覧にまとめ、check がすべて照合する

## Status

accepted (2026-10-26)

## Context

語の辞書で検出する規則が、4 か所に分かれていた。

| 置き場                                                           | 中身                                                                                      | 照合                   | いつ走るか                                                                           |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------ |
| tanteki の `no-ai-jargon`（上流の派生）                          | カタカナ語など 9 語と、型 4 つ（段 + 数、最適化される、価値の解放、アラインメントを取る） | kuromoji の形態素      | tanteki を入口にしたときだけ                                                         |
| npm の `textlint-rule-preset-ai-words-ja` 1.2.1 の `no-ai-words` | 54 項目                                                                                   | kuromoji の形態素      | 自動では走らない。`textlint-global` を呼ぶのは CI の smoke と permissions だけだった |
| japanese-check の `data/words.json`                              | 名指しの直訳語                                                                            | 正規表現               | hook `translationese-scan.ts` が警告する。`cli.ts check` は読まなかった              |
| japanese-check の `analyze.ts` の `calques()`                    | 動詞 7 語と名詞 4 語の定数                                                                | Sudachi の正規形と品詞 | 人が読む文書には必ず走る（ADR-0047 のゲート）                                        |

人が読む文書に必ず走るのは `cli.ts check` だけである。`data/words.json` は、`review` の動作と Sudachi の `lemma` の照合を欄としては持っていたが、照合する実装は無かった。

利用者は、置き場を `data/words.json` の 1 か所にすると選んだ。語は落とさず全部取ると答え、「扱いは変えて良いが、取り漏らしたら私が毎回指摘することになる」と述べた。この ADR の判断の軸は、旧の規則が検出していたものを新しい照合が取り漏らさないことである。

AI 以前の Qiita（1,200 本、和文 115 万字）では、旧の 2 つの規則のどの語も、検出された文書の割合が 2% 未満だった。一方、手元の AI の返答（372 セッション）での検出の大半は、このリポジトリの用語だった（検査の段、yomiyasu の照合、ADR-0036 の入口、reviewer を走らせる）。

## Decision

- **K1: 語の置き場は `data/words.json` だけにする。** tanteki の `no-ai-jargon` は消した。その `.textlintrc.json` の `allow` の 3 語（可観測性、レバレッジ比率、ロバストな推定）は、移した項目の `allow` に移した。グローバル textlint からは `preset-ai-words-ja` を外した。rule の無い設定では、`textlint-global` が「No rules found」を出して終了コード 1 で止まる。そこで設定は `preset-japanese` にした。これは仮の設定である。tanteki と `textlint-global` の検査をまとめる構想（`docs/plans/textlint-own-rules.md`）が runner と `textlint-global` の役割を決める
- **K2: 語は落とさない。違いは扱いで付ける。** 旧の項目（`no-ai-words` の 54、`no-ai-jargon` の 13、`calques()` の定数の 11 語）を、`action: review` の項目として移した。このリポジトリの用語（検査、照合、走る、経路、ゲート）も残し、`fix` の文に「この文書で定義済みの用語なら残してよい」と書いた。用語を `allow` で外すと、比喩として使った用法まで落ちるためである
- **K3: 一覧は `cli.ts` が読み、`check()` と `calques()` は一覧の順を保った 1 つの配列で受け取る。** `analyze.ts` はファイルを読まない。`lemma` の項目は Sudachi のトークンの正規形と品詞で、`regex` の項目は散文の行で照合する。候補の `rule` は、`calques()` の定数から来た項目では今までどおり `translation-candidate` になる。移した語では `word-jargon`、`word-metaphor-verb`、`word-slop` になる。同じ行、同じ桁、同じ表層の候補が 2 つの項目から出たら、一覧で先にある項目の候補だけを残す
- **K4: 一覧に 1 項目でも使えないものがあれば、受領証を作らない。** 一覧が無い、壊れている、検証で 1 項目でも落ちたときは、残った項目で照合し、`limitations` に理由を書き、`verification` を `null` にする。受領証のハッシュは一覧のファイルから計算するので、落ちた項目を除いた検査でも、完全な検査と同じハッシュの受領証になるためである。ゲートは受領証の無い文書を未検査として扱う
- **K5: hook は名指しの直訳語（`action: fix`）だけを警告し、`review` の項目は `check` だけが出す。** 人が読む文書には `check` が必ず走るので、`check` で検出できる。hook に足すと、書き込みのたびに用語の警告が出る。名指しの直訳語と重なる語（道具）は、`check` が名指しの項目を照合しないので、`review` の項目として別に持つ
- **K6: ADR-0036 と ADR-0045 の本文は書き換えない。** ADR-0036 の「tanteki の rule を上流の派生のまま持つ」のうち、`no-ai-jargon` だけをこの ADR が外す。ほかの 4 本の rule と週次の追跡は今のまま残る。ADR-0045 K3（語を足すのは利用者の名指しだけ）は `named-translationese` の項目の決まりで、`review` の項目は第三者の辞書から足してよい

### 取り漏らしの確かめ

旧の項目の移し忘れは、旧の項目 1 つにつき 1 行の台帳（`home/dot_claude/hooks/tests/fixtures/japanese-check/word-migration-ledger.json`）で確かめる。test は、行数（54、13、11）と、各行の行き先が一覧にあること、どの行からも指されない `review` の項目が無いことを確かめる。

用法の取り漏らしは、旧の規則を消す前に、3 つのコーパス全体で旧と新を突き合わせて確かめた。突き合わせのキーは（文書、行、新の項目の語）である。新はコードと引用の行を照合しないので、旧がその行で検出した分は分けて集計した。

| コーパス        | 旧の検出 | 新に無かった検出 | 直した後も残った差                                |
| --------------- | -------: | ---------------: | ------------------------------------------------- |
| AI 以前の Qiita |      252 |               13 | ゲートウェイ 5                                    |
| 2026 年の Qiita |    4,758 |              158 | ゲートウェイ 62、地名の廈門 2、URL の直後の本文 1 |
| AI の返答       |    6,400 |              160 | インラインコードの中の語 4、「各段 1 回ずつ」1    |

残った差は、どれも外すと決めた用法か、旧の規則の誤検知か、前からある不具合である。

- ゲートウェイは、kuromoji が「ゲート＋ウェイ」に割るので旧の規則が検出していた。`allow` で外した
- 廈門と「各段 1 回ずつ」は、旧の規則の誤検知である。`nonExamples` に入れた
- URL の直後の本文は、`markdown.ts` が URL を伏せるとき、後ろに続く全角の「）。以下は…」まで伏せる不具合で隠れていた。語の一覧と関係なく、check のすべての検査に影響する

新に無かった検出のほとんどは、Sudachi と kuromoji の分割の差だった。kuromoji は名詞として使う連用形を動詞の原形に戻し（突き合わせ、見落とし、効き、疑い）、複合語を細かく割る（事故＋る、穴＋掘り、焼き＋直す、実測＋値）。Sudachi は名詞や 1 語として返すので、原形の `lemma` の項目では検出できない。そこで、これらの項目は語幹の正規表現にし、字義どおりの用法だけを `allow` にした（焼き鳥、落とし穴）。

## 却下した代替案

- **語の置き場を今のまま分ける（差分最小案）。** `no-ai-words` は自分の辞書に置き換えて kuromoji のまま動かせるので、照合の仕組みを替える取り漏らしは起きない。しかし `no-ai-words` は自動で走らず、54 項目が今後も成果物に当たらない。走る経路を別に作ると、照合の仕組みが 2 つ残る
- **textlint に寄せる（自作の rule が `data/words.json` を読む）。** runner を決める構想が先に要り、ゲートから textlint を呼ぶ経路も新しく要る
- **用語を `allow` で外す。** 比喩として使った用法まで落ちる
- **取り漏らした形を `lemmas` に足す。** Sudachi は複合語ごとに別の正規形を返すので、一覧が閉じない
- **解析器を先に kuromoji へ寄せてから語を移す。** 下の計測のとおり根拠はあるが、解析器の入れ替えは check のすべての検査の結果を変える。今の一覧で取り漏らしは 0 件に届いたので、解析器の判断は `docs/plans/ja-morphological-analyzer.md` に送った

## Consequences

### このリポジトリの文書での候補の数

`docs/decisions/` の 52 本と `.skills/ja-check/SKILL.md` に、新しい `check` をかけた。

- `rule` ごとの合計: `word-jargon` 504、`translation-candidate` 413、`word-metaphor-verb` 131、`word-slop` 7
- 1 文書あたりの `review` の候補の中央値は 6 件。多かったのは `.skills/ja-check/SKILL.md` の 67 件と ADR-0036 の 51 件、ADR-0023 の 50 件で、ほぼすべてが用語（検査、照合、走る）だった

利用者は、今のまま受け入れることを選んだ。文書ごとに用語を宣言して候補を外す仕組みは、残件として別に計画する。宣言した文書では比喩の用法まで外れるので、取り漏らしとの引き換えになる（`docs/plans/japanese-check-detection-followups.md`）。

### textlint-global の出力

`preset-japanese` だけの設定で ADR-0045 を検査すると、指摘は 7 件だった（文の長さ 4、助詞の重複 2、読点の数 1）。手で呼んだときの出力は、語の検出から一般の校正に変わる。

### 解析器の速さ

同じ 7,406 行（34 万字）を 1 行ずつ渡すと、Sudachi（WebAssembly 版、モード C）は 557 秒、kuromoji は 1 秒だった。別の処理が CPU を 1 つ使っている間に続けて測った値で、遅さの原因は確かめていない。

### 残る限界

- 配布の後は、検査器のハッシュが変わり、既存の検査記録はすべて `stale` になる。追跡中の文書は check し直す
- `lemma` の照合は Sudachi の辞書の版に依存する。辞書の版は検査器のハッシュに入らない
- `data/words.json` の項目の順が、重なった候補で残る `rule`（keep の印の当たり先）を決める
- 半角カナの濁点（ｶﾞ）を含む行は、Sudachi のトークンを原文の位置に戻せず、check が止まる。語の一覧より前からある不具合で、AI 以前の Qiita の 6 文書で起きた
- 語幹の正規表現にした項目は、原形の `lemma` の項目より誤検知の幅が広い
