# ADR-0035: 承認依頼の Executive Summary を「前提→目指す状態→今の状態→やり方→確かめ方」で始める

## Status

accepted (2026-10-19)。2026-10-23 に Amendments で改訂した。

ADR-0026 が「Executive Summary の書式」として workflow.md に残した規則の、書式そのものを改訂する。規則を workflow.md に置く理由（hook の通知が Bash の stamp では届かない）は変わらない。

## Context

利用者から、spec や plan の承認時に「spec がこうなので、こういう状態を目指すために、今こういう状態から、こういうやり方をする、こうやって確かめながらやる」という説明がほしい、と依頼があった。spec と plan の両方に使える 1 つの書式でよい、という。

それまでの書式は、Goal / Proposed Approach / Experience Delta / Scope / Key Decisions / Risks / Review Status / Open Questions / Next Action を並べるだけだった。書式の定義は `rules/workflow.md` の節と、pass 後の Write / Edit で `plan-review-automation` が出す `buildSummaryReminder` の 2 か所にある。この書式には次の問題があった。

- 項目間のつながり（なぜその状態を目指すか、どこから始めるか、どう確かめるか）を書く場所が無い。
- 「今の状態」は Experience Delta の変更前の中に埋もれ、「確かめ方」には欄が無い。
- plan-N.md では、親 spec のどの決定を受けた plan かが書かれない。

以前にも、承認の質問をレビューの細部や仕組みの説明から書き始め、利用者に「読んでもわからん」と 2 度指摘されたことがある（agent-learnings L-ff9dd5979b8e）。

workflow.md は常時ロードされるので、予算テスト（`workflow-md-budget.test.ts`）が大きさに上限を置いている。

2026-10-23 の改訂の前提になった計測がある。ある時点の集計で、Document Workflow の session 84 件の承認のうち、応答時間が取れた 236 件の 87 件（37%）が 60 秒未満で返っていた。直前の要約の長さの中央値は約 2,000 字で、即答との相関は無かった。87 件は、読まずに承認した場合と、議論済みで読み直しが要らなかった場合を区別できない。承認しなかった 47 件のうち 12 件は、要約の中身の説明し直しを求める返答だった（「つまりどういうこと」「読んでもわからん」）。要約が `ask-approval` より後に書かれていたのは、直近の transcript の標本で 184 件中 169 件だった。

要約が読み手の記憶に頼っていた型は 3 つある。

- 再承認の要約が、前回との差分だけで終わる（「Goal は変わりません」）。
- K-id・タスク番号・関数名が、指す中身なしに書かれる。「写す」規則が、ID だけを写して指す文を写さなかった。
- レビューの指摘や決定の理由が、言い直されない。Key Decisions には採用と却下の代替案の欄しか無く、却下の理由や直した点を書く場所が無い。

## Decision

- **K1（5 項目と順）**: 承認依頼の冒頭に、前提 → 目指す状態 → 今の状態 → やり方 → 確かめ方の 5 項目を、この順に、前の項目を受けて 1-2 行ずつ書く。ラベル付きの箇条で書く。やり方には途中の確認点を含める。Goal / Proposed Approach / Experience Delta はこの 5 項目に置き換える。Scope 以降の 6 項目は文面を変えずに後ろに残す。
- **K2（層ごとの出どころ）**: 書式は 1 つにし、層ごとに違うのは出どころだけにする。hook はファイル名で出し分けず、各項目のプレースホルダに層ごとの出どころを並べて書く。spec.md と単層 plan.md は、前提を元のオーダーの引用、目指す状態を Goal、確かめ方をテスト計画（spec.md は選んだ品質特性）から取る。plan-N.md は、前提を親 spec の K-id / Scope、目指す状態を担う K の完了像、確かめ方を ISO 25010 具体テストケースから取る。今の状態とやり方は、どの層も research.md の観察と Tasks の順から取る。元のオーダーを書く欄はどの文書にも無いので、会話の原文から要約せずに引用する。
- **K3（写して足さない）**: 写す出どころは、文書、元のオーダー、オーダー以降の利用者の発言、この session のレビュアーと triage の出力の 4 つである。主張・数値・決定は、この 4 つから写して足さない。無ければ `N/A`。会話から引くのは原文だけで、context の圧縮でできた要約の中の言い換えは原文として引かない。引用は要約せずに行う。レビュアーと triage の出力は、tool の結果として session に残っている記録で、利用者の記憶ではない。triage が文書に残すのは件数だけなので、除外した指摘の中身と理由はここから写す。出力が session に残っていなければ、除外は件数だけを書く。作業ツリー・ブランチ・session-id は、session の環境（作業ディレクトリ、git の状態、workflow の dir の出力）から取る事実で、主張ではない。4 つとは別の 5 つ目として扱う。用語の説明は足してよいが、新しい主張を含まない。この規則を節の先頭に 1 つだけ置く。
- **K4（自己検証）**: 「Experience Delta が Goal の達成に直結しているか」に代えて、「確かめ方の各行が目指す状態のどれを確かめるか」を自己検証する。
- **K5（2 か所の一致）**: workflow.md の節と `buildSummaryReminder` の文面を、同じ項目、同じ順、同じ出どころの語でそろえる。テストで両方を読み、項目名の並びと出どころの語が一致することを確かめる。
- **K6（読み手は何も覚えていない）**: 承認依頼の Executive Summary は、読み手が何も覚えていないと仮定し、要約だけで読めるように書く。自分の最後の発言さえ、経過時間や並列作業によって確かではない。K7〜K9 は、この原則から出る規則である。
- **K7（前提を毎回、どの作業かから書く）**: 前提は条件を付けずに毎回、次の行を古い順に書き、全項目を書き直す。経過時間や並列作業で記憶が落ちるかは、書き手には分からないからである。(1) どの作業か（1 行）: 文書の題、作業ツリー・ブランチ、session-id の先頭 8 桁。値は要約を書く直前に確かめ直し、確かめられなければ文書の題だけを書く。(2) 元のオーダーの引用（spec.md と単層 plan.md）、または親 spec の K の中身（plan-N.md）。(3) オーダー以降に文書を直させた利用者の発言を、古い順に 1 件 1 行で引く。「進めて」のような中身の無い発言は引かない。長ければ、原文から要点の 1 文を抜き、省いた所を「…」で示す。該当が無ければ無いと書く。発言が session に残っていなければ、引用を作らずに確認できないと書く。(4) 反映（1-2 行）: (3) の発言を受けて、文書のどの節をどう直したかを、文書の今の本文から書く。どの項目も「変わりません」「前回どおり」で済ませない。前提には 1-2 行の上限を当てず、(1) と (4) の行数だけを決める。前提以外の 4 項目は 1-2 行のままである。
- **K8（ID に中身を添える）**: K-id・タスク番号・関数名・ファイル名を、ID だけで書かない。文書に定義があれば、それを写して添える。文書に無ければ、読んで確かめた範囲で何をするものかを添える。性質や保証を述べる説明（「〜なので安全」）は書かない。確かめていなければ ID を出さず、文書の言葉で書く。行に収まらないときは ID の数を減らす。
- **K9（理由と除外を言い直す）**: Key Decisions には、採用と却下した代替案に、それぞれの理由を添える。レビューで変えた決定は、指摘の中身（reviewer 名や round 番号ではなく）とどう変えたかを書く。triage で除外した指摘は、中身と除外の理由を書く。利用者は triage まで指摘を見ていないからである。Key Decisions に限り、決定 1 件につき 1-2 行で最大 5 件とし、レビューで変えた点と triage の除外はそれぞれ別の 1-2 行にする（多ければ主なものを挙げ、残りは件数）。理由は ID のように減らして収められないからである。Scope 以降の他の項目は 1-3 行のままである。ラベルと出どころの語（「採用と却下した代替案」を含む）は変えず、理由の要求は規則の行に置く。
- **K10（規則の届け口と予算）**: 規則は届く場面が違う 3 か所に置く。常時読み込まれる workflow.md の節、承認の質問を作る直前の `ask-approval` の stderr の注記、pass 後の Write / Edit の hook の通知である。規則の本体（K7〜K9 の具体的な書き方）は注記と hook の通知に置く。workflow.md の節の先頭の文は、原則・出どころ・3 つの型に 1 句ずつ・`ask-approval` を先に読むこと、の形にする。あわせて、後続の項目の行に Key Decisions の行数の例外を足す。workflow.md の予算は 13 × 1024 から 13 × 1024 + 256 バイトに上げる。最小版（原則と `ask-approval` を読む順だけ、予算を上げない）は退ける。要約が `ask-approval` より先に書かれる流れ（上の標本で 184 件中 15 件、約 8%）では workflow.md だけが届き、最小版ではそこで 3 つの型のどれにも規則が届かないからである。増分は全 session が払い、利益はその 8% の流れだけが受ける非対称を承知のうえで、規則を失うことより小さいと判断する。実地確認で効果が見えなければ、最小版に戻す。実装後の実サイズが新しい予算を超えるときは、文を縮める。予算はこれ以上上げない。
- **K11（注記の契約）**: 注記は固定文で、文書から取った文字列を補間しない。承認待ちの文書があるとき、1 回の呼び出しにつき 1 回だけ（文書ごとにではなく）、既存の注記の最後に足す。足すのは 5 行で、原則 1 行、前提 2 行（構成と例外）、ID と Key Decisions が 1 行ずつである。1 行は 1-2 文で 150 字以内にする。既存の行の文言と順、stdout は変えない。承認待ちの文書が無く `ask-approval` が失敗するときは、注記を出さない。承認を依頼する場面ではないからである。stdout を変えないのは、承認の記録がそれを質問と照合するからである。
- **K12（規則の行は 1 つ、3 か所の一致を縛る）**: 規則の行を 1 つの配列にし、hook の通知と `ask-approval` の注記が同じ配列を出す。workflow.md は静的な文書で生成できないので、行ごとの識別語が workflow.md にもあることをテストで縛る。workflow.md・注記・hook の文には、ADR 番号とリポジトリ内のパスを書かない。配られる文書と、他のプロジェクトで model が読む文面だからである。K5 の一致は、注記を加えた 3 か所に広がる。

## 却下した代替案

- **旧 9 項目を残し、「今の状態」と「確かめ方」を足す（差分最小案）**: 項目の順が Goal → Approach → Delta のままで、オーダーの流れにならない。Goal と目指す状態、Proposed Approach とやり方が重なり、同じことを 2 回書くことになる。
- **5 項目を 1 文の連鎖で書かせる**: 読みやすいが、項目が抜けても気づきにくく、テストで項目を確かめられない。
- **spec 用と plan 用に書式を分ける**: 承認者が知りたいこと（なぜ・どこへ・どこから・どうやって・どう確かめるか）は層で変わらず、違うのは出どころだけである。分けても読み手の得るものは増えず、規則と hook の文面が倍になる。
- **旧書式と新書式を併用する**: 利用者が「spec と plan の両方」の意味だと確かめたので採らない。
- **書式を stamp の出力に載せて届け方を直す**: ADR-0026 の見送り課題で、今回の依頼（説明の中身）とは別の問題なので扱わない。
- **K3 の 1 文だけを「事実は足さないが用語の説明は足す」に分ける（2026-10-23）**: ID の定義のない型には効くが、再承認で差分だけの要約と、指摘や理由を言い直さない要約には効かない。K3 は何を写すかの規則で、前回の要約を前提にしてよいかも、理由を書くかも言っていないからである。
- **`ask-approval` が文書から要約の骨格を機械で組む（2026-10-23）**: 文書の節名は層やテンプレートの版で揃っておらず、抜き出しの規則は K2 の出どころの表を機械で再実装することになる。再承認で利用者の最後の発言をどう反映したかは文書に無く、会話にしか無いので、骨格からは作れない。
- **workflow.md を最小版にして予算を上げない（2026-10-23）**: 要約が `ask-approval` より先に書かれる流れで、3 つの型のどれにも規則が届かない（K10）。

## Consequences

1. workflow.md の予算を 13 × 1024 + 256 バイトに上げ、その分を使った（K10）。これ以上は上げず、次に workflow.md へ足す変更は、どこかを削って収める。上げる理由を書いた ADR が要る点は ADR-0032 K7 のとおりである。
2. 流れのある説明になるか、要約が本文と食い違わないかは、機械では検査できない。model が規則に従うことに頼る。
3. spec 層と plan-N 層の承認依頼は、導入の時点で試していない。spec 層の「確かめ方」は、選んだ品質特性までしか書けない。具体的なケースは plan-N に書く決まりだからである。持ち越した確認は `docs/plans/approval-summary-narrative-followups.md` にある。
4. hook の通知は、引き続き pass 後の Write / Edit でしか出ない（ADR-0026 の Consequences 2）。Bash の stamp で終える流れでは、workflow.md の節だけが届く。
5. 規則が文面に載ったことはテストで確かめられるが、model が従うかは確かめられない。tool の結果の中の注記は、常時読み込まれる規則より従われにくい可能性もある。型の出現と説明し直しの要求を数える実地確認を、持ち越しの確認に置いた。
6. 37% の即答は減らないかもしれない。即答には、議論済みで読み直しが要らない場合が混ざる。効果の指標は、承認しなかった件のうち説明し直しの要求が占める割合（変更前は 12/47）とする。
7. 動いている session では、旧い workflow.md と新しい注記・hook が混在する。workflow.md は session の開始時に読み込まれ、hook と CLI は呼び出しごとに実行されるからである。ラベル・順・出どころの語・stdout を変えないので、混在しても要約の形と承認の記録は壊れない。
8. 規則の行の唯一の置き場は、レビューの hook のコアのモジュールである。`ask-approval` がそこから import するので、依存の向きは変わらない。
9. `chezmoi apply` の途中で、新しい CLI が古いライブラリ（配列が無い）を import して、数秒失敗しうる。apply の間に限られ、失敗は終了コードで見えて承認は記録されないので、互換の分岐は足さない。

## Amendments

### 2026-10-23: 読み手は何も覚えていないと仮定する

利用者から、承認の Executive Summary が読み手の記憶を前提にしている問題に取り組みたい、という依頼があった。承認の 37% が 60 秒未満で返り、説明し直しの要求も出ていたためである。依頼の当初は、読み手が自分の最後の発言までしか覚えていないと仮定する形だった。利用者は注釈で「最後の発言すら若干怪しいと思ってください。経過時間や並列作業に依存しています。」と直した。これを受けて、読み手は何も覚えていないと仮定する原則（K6）を立てた。

変えた決定は K3（出どころを 4 つと環境の事実にし、用語の説明を足してよいとした）である。K6〜K12 を足した。K5 の一致の対象は、K12 で注記を加えた 3 か所に広がった。K1・K2・K4 は変えない。

### 2026-10-23: `ask-approval` の stdout を変えた

K11 の「stdout は変えない」は、この ADR の計画の範囲での制約だった。並列の作業を見分けるため、ADR-0023 の 2026-10-23 の改訂で、承認の質問（stdout）に作業の識別と文書の題を載せた。注記（stderr）は K11 のとおり固定文のままで、文書から取った文字列を補間しない。
