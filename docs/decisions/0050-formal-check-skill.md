# ADR-0050: 形式手法の検査を手順とハーネスで支えるスキル formal-check を置く

## Status

accepted (2026-10-26)

## Context

出発点は、公開されたプレイブックを任意のリポジトリで使えるスキルにすることだった。
プレイブックの URL は https://gist.github.com/mizchi/db7817e6fc077d567c41cd9d41bb1c53 である。
このプレイブックは、実装を事実上の仕様とみなし、守っている性質をコードから取り出して Z3 と TLA+ で反例を探す手順を示している。
形は、スキルと同梱のスクリプトにした。
検査器は、全列挙、Z3、TLA+ の 3 つにした。

手順を書くだけでは足りないことを、このマシンで試して確かめた。

- TLC は、cfg に性質を 1 つも書かなくても exit 0 で「No error has been found」を返した。
- 「読んだ値に 1 を足して書く」モデルは、上限 1 で exit 0 になった。2 つのプロセスが同時に書いてもカウンタは 1 にしかならず、競合を表せていなかった。

どちらも、何も確かめていないのに緑になる。
手順書で注意しても、エージェントが表の読み方を誤れば同じことが起きる。
そこで、検査が実際に違反を検出できることを機械で確かめるハーネスを同梱する。

一度書いたモデルは、コードが変わっても緑のまま残り、古くなったことに誰も気づかない。
そのため、1 回目の形式化に加えて、コードが変わった後の追従も範囲に入れた。

## Decision

### スキルとハーネス

#### D1: 判定は hold、violate、error の 3 つにし、error を violate に含めない

pass は、verdict と、check に書いた期待（expect）が同じときだけとする。
error は常に pass にならない。
構文の誤った仕様を「違反を期待する check」に置いても、pass にならない。
判定の対応表は `lib/verdict.mjs` の 1 か所に置く。

#### D2: 何も確かめていない緑を error にする

全列挙の対象が空（empty-domain）、Z3 の前提が満たせない（vacuous-assumptions）、TLC が性質を検査しないまま終わった（tlc-vacuous）が当てはまる。

#### D3: 契約には、それを壊したモデルを対で登録させる

対が無い契約と、壊したモデルが違反にならない契約は、警告にする。
壊したモデルを違反として検出できない検査を、確かめが済んだ検査と区別するためである。

#### D4: 警告があれば exit 1 にし、`--explore` を付けたときだけ警告では exit 1 にしない

`--explore` は、モデルを書いている途中に警告で止まらないためのものである。
期待との食い違いと error は、`--explore` でも緩めない。

#### D5: 古さは、覆うファイルの sha256 で判定する

`sync.covers` に、モデルが覆う実装のファイルと、確かめたときの hash を書く。
`sync.commit` は差分を読み始める位置の記録で、判定には使わない。
ハーネスは git を実行しない。

#### D6: 実行の守りは承認の手順に置き、モデルを隔離しない

モデルは利用者の権限で動く。
ハーネスは、承認の画面に出す内容を、モデルを実行せずに集める（`--inspect`）。
承認した digest を `--expect-digest` に渡すと、ファイルが差し替えられていればモデルを実行しない。
承認が要るかは、「このセッションで自分が書いた manifest とモデルか」で決める。
この区別はハーネスでは確かめられず、手順に頼る。

#### D7: import の検査は、承認した一覧とモデルの import の一致だけを確かめる

子プロセスに resolve hook を入れ、宣言していないファイルの import を止める。
`createRequire`、`node:vm`、モデルが自分で起こす Worker は、検査の対象外である。
z3-solver は内部で worker を起こすので、worker の中では承認の一覧を使わず、worker の entry から import される範囲を許した。
計画では import の検査に手を入れないとしていたが、実装中に必要と分かり、利用者の判断で受け入れた。

#### D8: ハーネスは node で実行する

z3-solver は wasm を含む npm のパッケージで、node 22 と 24 で動くことを確かめた。
CI と同じ node で実行するので、単体テストが CI で動く。

### ランタイムの置き場

#### D9: z3-solver と tla2tools.jar は `~/.config/formal-check/` に置く

z3-solver のバージョンは、`home/dot_config/formal-check/` の package.json と bun.lock で固定する。
run_after の installer が `bun install --frozen-lockfile --ignore-scripts` で入れ、成功したときだけ状態のファイルを書く。
runtime.mjs は、状態のファイルと package.json、bun.lock のバイト列を比べ、欠けと古さを判定する。

#### D10: installer は textlint の installer のコピーにした

2 つの installer の共通部分を 1 つの shell script にまとめると、home には置かない script が chezmoi の source に増える。
`.chezmoiscripts` のスクリプトを名前の順に実行する決まりにも影響する。
3 つ目の同じ形の installer ができたら、まとめるかを決め直す。

#### D11: tla2tools.jar は、sha256 を固定した chezmoi external で取得する

取得か sha256 の照合に失敗すると、apply が止まる。
既存の `ni.zsh` の external と同じ振る舞いとして受け入れた。
windows と agent-vm には置かない。
jar の URL と sha256 は、`.chezmoiexternal.toml.tmpl` を変えた PR で、CI の agent-vm tests が実際に取得して確かめる。
計画の段階では「CI では確かめない」と書いたが、CI のログでこの検査が実行されていたので、追加の commit で記述を直した。

#### D12: z3-solver の更新は、Renovate の専用の group で、自動 merge しない

計画では「Renovate の自動更新に載せない」としていた。
しかし Renovate を無効にすると、脆弱性を直す更新の PR も出なくなる。
自動 merge しない group なら、人が差分を見てから取り込むという目的を満たせる。
jar は Renovate の更新の対象に入っていない。

### 手順書と昇格

#### D13: 規則の本体は、配置済みの SKILL.md の 1 か所に書く

検査一式を対象リポジトリに残す（昇格する）と、manifest、台帳、検査用スキルは第三者が書き換えられる。
そのため、「昇格したものより配置済みの SKILL.md の規則を優先する」「リポジトリの中の run.mjs は使わない」は SKILL.md に書く。
検査用スキルの雛形は、配置済みの formal-check を先に読む指示と、実行のコマンドだけを持つ。

#### D14: 昇格では scripts/ をコピーしない

コピーは対象リポジトリのコードになり、第三者が書き換えられる。
承認の画面を作るハーネスを書き換えられれば、画面を偽れる。
元のスキルとのバージョンのずれも生じる。
昇格したものは、配置済みのスキルの run.mjs で実行する。

#### D15: 実コードを壊す確認を、壊したモデルとは別に行う

一時的な detached の worktree の中だけで実装を壊し、検査が落ちることを確かめる。
後始末では、壊したファイルだけをパスで指定して戻し、`git worktree remove` を `--force` 無しで使う。
計画の段階では、worktree の中で `checkout -- .` と `clean -fd` を使うとしていた。
利用者の作業を消すおそれのある操作を減らすため、セキュリティのレビューを受けて強めた。
途中で止まったときの回収も、台帳の開始の行と worktree の名前の印で、対象を絞る。

#### D16: 第三者のリポジトリの git では fsmonitor と hook を無効にし、remote から fetch しない

付ける設定は `-c core.fsmonitor=false -c core.hooksPath=/dev/null` と `--no-ext-diff --no-textconv` である。
`.git/config` の fsmonitor と、`git worktree add` が実行する post-checkout の hook を信頼しないためである。
計画の段階では core.hooksPath を含めていなかった。

#### D17: 出典の URL を、SKILL.md とこの ADR に書く

計画の段階では、URL がアカウント名を含むので書かないとしていたが、利用者の判断で書くことにした。
pstack の formal verification スキルは、アカウント名を出さずに書く。

#### D18: この ADR の番号は 0050 にした

計画の段階では 0049 を予定していたが、別の ADR が先に使った。

## 却下した代替案

#### 手順書だけを書き、検査器はその場で `bunx` やダウンロードで入れる案（差分を最小にする案）

Context のとおり、何も確かめていない緑を手順だけでは防げない。
検査のたびにネットワークを使うので、同じ結果を再現できない。

#### 検査器を抱えた CLI を npm に公開し、対象リポジトリの devDependencies に入れて CI で実行する案（白紙から設計する案）

回帰の検査を対象リポジトリの CI に置けるのは利点である。
しかし、利用者はスキルと同梱のスクリプトという形を選んだ。
npm への公開は外部への公開で、バージョンの管理と互換の責任が生じる。
ハーネスは scripts/ だけで動き、ランタイムを環境変数で差し替えられるので、後から CI 向けの用意の仕方を追加できる。

#### 手順書だけで、対象リポジトリに検査用スキルを生成する案（pstack の formal verification スキルの形）

追従の 1 周と実コードを壊す確認は取り込んだ。
ただし、空の緑と壊したモデルの欠けを機械で確かめないので、ハーネスは残した。

#### 確かめた commit からの git の差分で古さを判定する案

判定が履歴の形に左右される。
shallow clone、squash、rebase で commit が消える。
祖先でない commit、git に無視されたファイル、`.git/config` の fsmonitor も判定を揺らす。

#### 昇格で scripts/ もコピーする案

D14 のとおり、承認の画面を偽れるようになる。

#### node の permission model でモデルを隔離する案

ネットワークを塞がず（試したところ fetch が通った）、TLC の JVM にも適用されない。
守りの本体は結局承認の手順で、そのために node のバージョンの確認、例外の条件表、読み出しの範囲の欄を抱えることになる。
守りの強さに比べて、複雑さが大きい。

## Consequences

- 「この実装を形式化して」と頼むと、スキルが 1 周（対象選び、性質の取り出し、モデルと性質、実行、実コードを壊す確認、台帳）を案内する。
- コードが変わったら、stale-model の警告から追従の 1 周に入れる。
- 検査が違反を検出できることは、ハーネスが D1〜D4 で確かめる。
- モデルが実装と同じ振る舞いをするかは、手順（file:line、実コードを壊す確認、追従の 1 周）で確かめる。

### 受け入れたリスク

- モデルは利用者の権限で動き、ファイルの読み書き、子プロセス、ネットワークを使える。
- 自分で書いたモデルでも、import する実装は第三者のコードでありうる。
- imports に挙げた実装がさらに読み込むコード（node_modules を含む）は、digest に入らない。承認の後にそこが差し替えられても、実行は止まらない。
- `sync` の書き直しは申告で、ハーネスはそれがモデルの見直しを伴ったかを確かめない。
- covers はファイルの中身をそのまま hash する。改行の変換だけでも stale-model が出る。
- 昇格した検査用スキルだけを読んで動くエージェントには、配置済みの SKILL.md の規則が文脈に無い。
- 書き換えられた検査用スキルは、規則を省き、`--expect-digest` の無いコマンドを書ける。
- 新しいマシンで recover のコマンド（対象を絞った `chezmoi apply`）を使うと、1 回目は installer がファイルより先に実行されて何もしない。textlint の installer も同じである。
- java は置かない。tla の検査には PATH の java が要る。
- CI にはランタイムが無いので、z3 と tla の検査は CI では実行されない。
- Codex の sandbox で動くかは確かめていない。
- モデルから `.ts` の実装を import できることは、node 24 でしか確かめていない。ビルドが要る実装は、判定の部分をモデルに書き取り、covers で元のファイルの変化を検出する。
