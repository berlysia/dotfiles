# ADR-0051: japanese-check の形態素解析を語の契約の上で行い、解析器に lindera-unidic を使う

## Status

accepted (2026-10-26)

## Context

日本語の文章の検査で、形態素解析器が 2 つ使われていた。
japanese-check は npm の `sudachi@0.1.5`（Sudachi の WebAssembly 版）を使っていた。
tanteki の独自の textlint ルール `no-vague-action` と `no-opaque-compound` は、kuromojin（IPADIC）を使っていた。
どちらも、検査の規則が解析器の出力に直結していた。

- japanese-check は Sudachi の正規形と品詞の和名で照合していた。正規形が 効く を 利く に寄せるので、語の一覧に 効く と 利く を並べていた。名詞として使う連用形（見落とし、疑い）は原形で照合できず、約 9 項目を語幹の正規表現にしていた（ADR-0050 の語の一覧）
- tanteki の 2 本は、kuromoji の `pos`・`pos_detail_1`・`basic_form` を読んでいた

WebAssembly 版は遅かった。
7,406 行（34 万字）を 1 行ずつ渡すと 557 秒かかった。
原因は、`hata6502/sudachi-wasm` の npm 0.1.5（commit `39aa1d90`）が、`tokenize` を呼ぶたびに辞書を読み直すことだった。1 回の呼び出しに 71〜131 ms かかる。

ADR-0050 の語の一覧は、解析器を寄せる判断を `git show f7cc3f1dec:docs/plans/ja-morphological-analyzer.md` に送っていた。
この ADR がその判断を引き取る。

判断の方針は利用者が決めた。

- 検査が持つ独自の部分と、解析器の挙動による部分を分ける。Sudachi に固執しない
- 上流から来た規則は、検出したいことに解体して自分のものにする
- 活用を理解し、原形（語幹）が取れる道具を使う

## Decision

- **K1: 検査は語の契約だけを読む。** 契約（`home/dot_claude/japanese-check/contract.ts`）は、語ごとに次を持つ。原文の切り出し、原文の UTF-16 の位置、原形、品詞の閉じた列挙、活用の種類。品詞は英字の識別子にし、和名との対応は adapter が持つ。検査は、契約が export する述語（名詞か、動詞か、接尾辞か など）だけで品詞を判定する。品詞の値は型で隠してあり、検査からは直接読めない。活用の種類から連用形を作る関数（`renyokei`）も契約に置き、adapter ごとに同じ表を持たない
- **K2: 原形は、表記を保った辞書形にする。** 解析器の正規形は使わない。効く は 効く のまま返る。文書の筆者が書いていない形（効く と書いたのに 利く）を語の一覧に加えることはしない
- **K3: 名詞として使う連用形は、印を付けた動詞の項目だけで照合する。** 動詞の項目に `nominal: true` を付けると、その項目は名詞も検出する。検出するのは、原形の連用形（見落とす → 見落とし）と全体で一致する名詞である。すべての動詞に当てはめると、引き・通り・足し のようなありふれた名詞まで検出するので、項目ごとに印を付ける
- **K4: 解析器は、関門と量で比べてから選んだ。** 関門は 3 つにした。契約のテストの入力 24 件（位置の境界、辞書形、活用、品詞）、配布の条件、速さである。候補は、kuromoji、Sudachi のネイティブ版（SudachiPy）、lindera の IPADIC と UniDic の 4 つだった。関門を通ったのは、lindera-unidic と Sudachi のネイティブ版である。語の一覧の例文（検出する 160 件、検出しない 73 件）と、本文での原形と正規表現の照合の件数は、2 つとも今の WebAssembly 版と同じだった。terms と固有名詞の件数は違ったが、どちらが正しいかは判定していない（Consequences）。配布と呼び出しの手間が少ない lindera-unidic を利用者が選んだ
- **K5: adapter は 1 つだけ出荷し、解析器の識別を検査器のハッシュに入れる。** adapter は、エンジンの名前・パッケージのバージョン・辞書の識別を返す。この識別は、`check` の出力の `analyzer` の欄と検査器のハッシュに入る。解析器か辞書を替えると、既存の受領証（ADR-0047 の、文書ごとの検査の記録）は古くなる。解析器を切り替える設定は持たない
- **K6: tanteki の 2 本を `check` の検査として作り直した。** 新しい rule 名は `vague-action` と `opaque-compound` である。候補は `check` の `findings` に出る。上流のコードは引き継がず、上流のテストの例文を入力として、同じ文で検出することを確かめた。ADR-0036 は「tanteki の rule を上流の派生のまま持つ」と決めている。この ADR は、そこから 2 本と共通の `rules/lib/japanese-rule.mjs` を外す。ADR-0036 の本文は書き換えない。残る `stock-boundary` と `table-cell-length`、週次の追跡は今のまま残る
- **K7: 語幹を正規表現で照合していた項目のうち、4 つを原形の照合に移した。** 移したのは 疑う・見落とす・突き合わせる・溶かす で、原形の照合と K3 の印で検出する。焼く・効き・穴・実測・事故 は正規表現のまま残した。残した理由は、語の一覧の `reason` の欄に書いた。`reason` は検出を変えないので、検査器のハッシュに入れない
- **K8: 解析器は、版と中身を固定して入れる。** lindera とその native パッケージは `~/.config/japanese-check` に入れる。lockfile を固定し、install の script は走らせない。UniDic の辞書は SHA-256 を固定した chezmoi の external で取得し、読み込む直前にファイルごとのハッシュを確かめる。実行環境の dir は、持ち主が自分で、他人が書き込めないことを確かめる。実行環境が無い手元では、辞書を要るテストを skip し、CI では skip せずに失敗させる。lindera は同じプロセスの中で動く。そのため、別プロセスの解析器のための条件（shell を使わない起動、PATH から実行ファイルを探さない、時間の上限）は持たない

### 当初の設計との差

- 当初は「効きが悪い」を、動作の動詞の項目（原形 効く）に K3 の印を付けて検出する予定だった。実装では、効き は正規表現の項目のまま検出する。効く は「動作の動詞」という項目が持つ原形の 1 つで、その項目に印を付けると、同じ項目の 引く・通る・足す の連用形（引き・通り・足し）まで検出するためである
- 当初は、品詞の列挙の `nonIndependent`（非自立）を、tanteki の 2 本の述語の終わり（「対応していません」の「ていません」など）の判定に使う予定だった。実装では使わない。UniDic の「非自立可能」には する も入るので、adapter で `nonIndependent` に対応させると、する が動詞と判定されなくなり、原形の照合で検出できなくなる。述語の終わりは、原形の一覧（いる・おる・ある・しまう・おく・いく・くる・なる）と、て・で・ば の並びで判定する。列挙の `nonIndependent` は、今の adapter が返さないまま残る

## 却下した代替案

- **Sudachi の WebAssembly 版の呼び出し方を直す。** 辞書の読み直しはパッケージの中のコードで、パッケージは 2021 年から更新されていない。まとめて渡すと隣の行を文脈に使い、1,000 行中 23 行で、行の先頭か末尾にある語の品詞と正規形が変わった
- **Sudachi のネイティブ版（SudachiPy）。** 関門は通ったが、Python 3.10 以上と venv、子プロセスの管理が要る。契約の Tokenizer は同期の関数なので、全行を先に非同期で解析して結果を覚える作りが要った。macOS の Python は chezmoi が入れない
- **kuromoji と lindera-ipadic。** 契約のテストの入力 24 件のうち 22 件しか満たさなかった。IPADIC は ロバスト を「ロ」と「バスト」に割り、形状詞として返せない。「疑った」の原形を 疑る（ラ行五段）にする
- **すべての動詞の項目で、名詞として使う連用形を照合する。** 引き・通り・足し のようなありふれた名詞が候補に増える
- **tanteki の 2 本の効果語・容器語を、語の一覧の区分にする。** 効果語（向上、最適化 など）と容器語（基盤、システム など）は、1 語では候補にならず、名詞句の中の並び方で決まる。語の一覧は 1 項目が 1 つの候補になる形なので合わない

## Consequences

### 計測の値

どれも実測値で、条件が違う値どうしを比べてはいない。

- 速さ: lindera-unidic は、7,406 行で 626 ms だった（3 回の中央値。解析器の初期化と全行の解析だけを数え、bun の起動と検査の時間は含まない）。作り直した 2 検査は、別の本文の 8,901 行で 738 ms だった（1 回。解析を含む）
- 量の差: 基準の WebAssembly 版に比べ、terms は 5,360 件から 5,397 件、facts の固有名詞は 482 件から 298 件になった。英字の 1 字ずつの並びを 1 語にまとめる前は、terms が 4,650 件（13% 減）だった。UniDic は英字を 1 字ずつに割る（API → A／P／I）ので、まとめる処理を adapter に入れた。どちらの解析器の結果が正しいかは測っていない
- tanteki の 2 本の前後: 8,901 行（34 万字）で、上流の 2 本は `no-vague-action` 6 件、作り直しは `vague-action` 8 件だった。6 件は同じ箇所で出た。増えた 2 件は「それに対応」で、IPADIC が「それに」を 1 語の接続詞として割るので、上流は指示語として読まなかった。`opaque-compound` は前後とも 0 件だった

### 上流と違う点

作り直した 2 検査は、次の点で上流と違う。

- 行をまたいで検出しない。`check` は行ごとに行番号と桁で報告するためである
- 裸の URL の後ろに続く日本語は検出する。japanese-check は、URL を最初の非 ASCII 文字までとして扱う
- 入り口（適切に、これを など）から 40 語で、動作の名詞を探すのを打ち切る。長い行で処理が増えないようにする上限である
- 参照式のリンク（`[text][ref]`）は、記号が句を切る
- 引用の判定は、行の先頭の `>` だけで行う

### 残る限界

- lindera-unidic の配布元は新しい（npm の 6.0.0 は 2026-09-23 の公開）。バージョンを固定し、更新は CI の結果を確かめてから取り込む
- 名詞として使う連用形の照合が成り立つ証拠は弱い。名詞の形の例 12 件のうち、実在の文は 0 件だった。AI 以前の Qiita の 197 万字で、この照合が出した候補は 2 件で、どちらも既存の正規表現が同じ箇所で検出していた
- 同じプロセスで動く解析器には、時間の上限を強制できない
- 配布すると検査器のハッシュが変わり、既存の受領証はすべて古くなる
