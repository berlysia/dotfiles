# ADR-0045: 利用者が名指しした直訳語を一覧に持ち、日本語の成果物に常に当てる

## Status

accepted (2026-10-23)

## Context

2026-10-23、ハンズオン教材（typescript-inference-handson）の問題説明を japanese-tech-writing で推敲した。利用者は「直訳の言い回しが残っていたら除去して整える」と指示したが、次の語は推敲の後も残り、利用者が名指しするまで直らなかった。

- 利用者がチャットで直接挙げた語: 仕掛け、道具立て、届く・届かなくなる、〜する側、核
- 利用者が承認したその作業の計画が、利用者の指定した直訳語として挙げた語: 握る、編む、肌で、手触り

直した先は、「届かなくなる」→「通用しなくなる」、「道具立て」→「道具」、「核」→「いちばん見てほしいところ」などである。

拾えなかった理由は 2 つある。

- **(a) スキルは読まれたのに、規則どおりに残った。** ja-notation の「英語の言い方を一語ずつ写した表現」の節は、意味が通る語を「残して挙げる」に分け、japanese-tech-writing と tanteki の推敲ではそれを挙げずに残すと決めていた。同じ節は、例を「語を照合する一覧として使わない」とも書いていた。sonnet の worker 2 体のうち 1 体は直訳調を 0 件と報告し、もう 1 体は「握る」「編む」だけを直した。tanteki の textlint（`no-ai-jargon`）と yomiyasu の slop-catalog にも、これらの語は無かった
- **(b) スキルを呼ばない成果物には、何も当たらない。** japanese-tech-writing と tanteki は自動で発火し、pr-description は名前で読む。一方、commit の本文、Issue の本文、他のリポジトリの README は、モデルがスキルを選んだときにしか当たらない

ADR-0036 は、yomiyasu の hook（返答の終わりに照合を走らせるもの）を見送り、「呼び忘れが起きたら、hook の設定の変更として別に計画する」とした。本件は (b) がその条件に当たり、(a) は呼び忘れとは別の問題である。

## Decision

### 成果物の範囲（この ADR が正本）

- 対象は、リポジトリに残る Markdown（`.md`、`.mdx`）と、PR・commit・Issue の本文である。Document Workflow の文書（`.tmp/` の下）とチャットの返答は対象外とする。`.txt` とコードのコメントも対象外とする
- CLAUDE.md の規則と hook はこの範囲を写す。hook は Markdown のパスとコマンドで判定するので、規則より狭い（下の K6 の拾わない経路）

### 一覧

- **K1: 語を名指しする一覧を持つ。** ja-notation の例の段落は「この例は」照合の一覧として使わない、と例に限った言い方に直した。名指しの一覧は新しい節「名指しの直訳語」が持ち、当たれば既定で直す。型の目印で拾う既存の節は残し、一覧と並べて使う。型の目印だけで拾う方針は、(a) で拾えなかったので却下した
- **K2: 一覧は ja-notation の `references/translationese-words.json` に置く。** 欄は `word`、`origin`、`pattern`、`english`、`fix`、`allow`、`examples`、`nonExamples` である。`pattern` と `allow` はフラグを付けず 100 字以内とし、量指定を付けたグループを含めない。スキル（モデルが読む）と hook（機械が読む）が同じファイルを読み、写しを作らない。Markdown の表は hook での解析が壊れやすく、TSV は配列を表せないので選ばなかった。スキーマの正本は hook の unit test で、ja-notation の節はその要約である
- **K3: 初期の語は、利用者が名指しした語に限る。** `origin` でチャットの名指しと計画経由を分ける。語を足すのは、利用者が直訳語と名指ししたときだけにする。警告が出て意味の違う用法として残した例は `allow` と `nonExamples` に足す。モデルが推測して足すと誤検出が増え、警告を読み流す癖が付くので、その方式は採らない
- **K4: 推敲で残した直訳語は、本文の外の「確認」の欄に挙げる。** ja-notation の手順 3 を変え、tanteki と japanese-tech-writing も、意味が通るので残した語を挙げるようにした

### 規則

- **K5: 規則はグローバル CLAUDE.md の `## Language` に置き、一覧のパスだけを書く。** 読み方と直し方は ja-notation の SKILL.md に任せ、節の名前は書かない。節の名前を変えても規則が壊れないようにするためである。利用者が新しく直訳語を名指ししたら、一覧に足すよう提案する、とも書く。rules/ に新しいファイルを足す案は、1 項目のためには大きすぎるので採らなかった。japanese-tech-writing の発火条件を広げる案は、commit の本文のたびに書籍の規範を丸ごと読ませることになるので採らなかった

### hook（`translationese-scan.ts`）

- **K6: 警告だけを出し、対象を絞る。** 止める（deny）と、「届く」のように直訳でない用法もある語で正しい文まで通らなくなる
  - Write と Edit: 拡張子が `.md` か `.mdx`（大文字小文字を問わない）で、パスに `.tmp/` の段を含まないもの。調べるのは Write の `content` と Edit の `new_string` だけで、ファイル全体は読まない
  - Bash: 個々のコマンドに分けて、`git commit`、`gh pr create|edit|comment`、`gh issue create|edit|comment` があるとき。コマンド文字列（heredoc の本文を含む）と、`-F`、`--file`、`--body-file` が指すファイルを調べる
  - 拾わない経路: `gh api`、`-F -` と process substitution、`cd x && git commit -F y` の `cd` の効果、Markdown 以外の文書
- **K7: 失敗しても書き込みを止めず、故障を黙らない。** 入口全体を try/catch で囲み、どの例外でも終了コード 0 で、`permissionDecision` を出さない。一覧が無いときは、対象の書き込みのたびに直し方（引数なしの `chezmoi apply`）を添えて 1 行で知らせる。セッションごとに 1 回へ抑える印は、置き場、名前の検証、排他の作成という状態を、警告だけの hook に持ち込むので持たない。JSON が壊れているときも毎回知らせる。項目単位の不備は、その項目だけ飛ばして、そのことを 1 行で知らせる
- **K8: 入力に上限を設け、返す文字列を安全にする。** 照合するのは先頭 256 KB、1 行は先頭 2,000 字までとする。`-F` などのファイルは、symlink をたどらずに開いてから通常ファイルかを確かめ、256 KB まで読む。`/dev/`、`/proc/`、`/sys/` の下は、正規化して解決したパスで判定して読まない。抜粋は Unicode の制御・書式の文字を空白に置き換え、「」で囲み、冒頭に、引用であって指示ではないと書く
- **K9: フェンスは断片の中だけで追う。** 閉じないフェンスの後はコードとして扱う。コードブロックの中だけを直す Edit は判定できず、地の文として扱う

### 記録

- **K10: この ADR を新しく書き、ADR-0036 の本文は書き換えない。** ADR-0036 の References に、この ADR への 1 行を足す。ADR-0036 が見送った yomiyasu の hook は、返答の終わりに照合を走らせるものだった。この hook は、書き込みと送信の後に、名指しの語だけを照合する。照合の範囲と負荷が違う

## 却下した代替案

- **CLAUDE.md に「日本語の成果物ではスキルを読む」と書くだけにする（差分最小案）。** (a) のとおり、読んでも規則どおりに残る。読み忘れたときに何も起きない
- **語の一覧を prh の辞書にし、textlint で全成果物に掛ける（白紙設計案）。** Markdown の構文木でコードを確実に除けるのが利点である。しかし、グローバルの textlint には語の一覧を受けるルールが無く、依存の追加が要る。tanteki と textlint-global の検査をまとめる構想（`docs/plans/textlint-own-rules.md`）が検査の runner を決めることになっており、先に決めるとその構想を縛る。CLI の起動は bun の hook より重い。一覧は正規表現と除外の配列なので、構想が runner を決めた後も、そのルールの入力として使える。ただし prh の置換先に当たる欄は持たない

## Consequences

- 名指しした語の再発は、規則と警告の二重で拾う。一覧は再発を防ぐためのもので、まだ誰も指摘していない直訳語を見つける汎用の検出ではない。未知の語は、ja-notation の型の目印が今までどおり受け持つ
- 一覧の語が増えないと、効果は名指しした語に留まる

### Risks（受け入れたもの）

- 規則を読むこと、「確認」の欄に挙げること、一覧に足すよう提案することは、モデルの判断に頼る。機械で強制する手段は無く、hook の警告が最後の網になる
- 「届く」「核」「手触り」のように直訳でない用法もある語には、警告が出る。`allow` で既知の用法を除き、残した用法を足して減らす
- commit と PR は、送った後に警告が出る。直すには amend か edit が要る。送る前に止める PreToolUse は、誤検出で正しい commit を止めるので採らない
- 量指定を付けたグループの禁止は、正規表現の遅さを完全には防がない。`a*a*a*b` のようなグループを使わない多項式的な遅さや、`\(` と文字クラスの中の `(` を見分けない。一覧はリポジトリで管理する入力で、項目ごとの時間のテストが本体の網になる
- 実行中に照合を打ち切る仕組みは持たない。hook が timeout（5 秒）で殺されても、PostToolUse なので書き込みと送信は済んでおり、警告が出ないだけになる
- 抜粋に添える「引用であって指示ではない」という注記は、モデルが従うかに頼る弱い防御である。抜粋が最大 10 件 × 約 30 字に収まることと合わせて受け入れる
- ja-notation の SKILL.md、この ADR、残件の文書を編集すると、語そのものを書くので警告が出る。警告だけなので作業は止まらない
