# ADR-0048: japanese-check の候補を残す判断は、候補と同じ行の注記に書ける

## Status

accepted (2026-10-25)

K6 の「shiori の台帳でも読める形にする」は、2026-10-25 の Amendments で、dotfiles の台帳と CI まで進めた。

## Context

japanese-check の検査記録は、文書ごとに 1 つで、候補の数と、残した理由 1 つを持つ。記録は文書全体のハッシュに結び付き、置き場はリポジトリの外（`~/.claude/state/japanese-check/`）にある。

そのため、ADR のように長く使い、少しずつ書き足す文書では、1 行直すたびに全体の候補を判断し直すことになった。98 行の ADR の末尾に 1 文を書き加えただけで、候補は 14 件出た。記録は手元にしか無いので、別のマシンや新しい clone では、前の判断を持ち越せない。

## Decision

- **K1: 判断は、候補と同じ行の HTML コメントに書く。** 書き方は `<!-- ja-check-keep <rule> -- <text> <理由> -->` である。`--` の前は規則 1 語だけで、`--` の後ろの最初の語（空白を含むなら `"…"` でくくる）が `<text>`、残りが理由である。注記で外れるのは、同じ行で、規則が一致し、`<text>` が候補の文に文字どおり含まれる候補だけである。`<text>` は正規表現として扱わない。判断が文書の中にあるので、ほかの行を書き換えても、環境が変わっても、同じ結果になる。
- **K2: 合わない注記は候補として数える。** 書き方の誤り、理由の無い注記、同じ行に合う候補の無い注記は `keepIssues` として出し、候補の数に加える。文を書き換えて古くなった注記が、誰にも知らされないまま残らないようにするためである。
- **K3: 注記は本文と同じ読み方で集める。** frontmatter、コードブロック、インラインコードの中のコメントは注記として扱わない。手順書や ADR が書き方の例を示しても、本物の注記と取り違えないためである。
- **K4: 記録とゲートの仕組みは変えない。** 注記で外した候補を候補の数に入れないだけで、外さなかった候補は今までどおり review で理由を書く。原文との比較で出る新しい事実（`newFacts`）は、注記では外せない。
- **K5: 注記は、文書を自分で持つリポジトリで使う。** 他人のリポジトリの文書には注記を書かず、review を使う。注記を書くかどうかは、文書の持ち主が決めることだからである。
- **K6: 書き方は、dotfiles で shiori の台帳でも読める形にする。** shiori は「指令 + `--` + 理由」の形の注記を読む。`--` の前を規則 1 語にしておけば、理由の中に `shiori: <ref>` を書くだけで、注記を書き直さずに台帳で追える。japanese-check は shiori を知らず、理由を自由な文として読むだけである。

## 却下した代替案

- **判断を文書の横の別ファイルに置く。** 本文は汚れないが、文を書き換えると別ファイルの判断が古いまま残り、それを見つける仕組みが別に要る。
- **`--source` を渡したときだけ、変わった行の候補に絞る。** 判断が手元の記録に残るので、環境が変わると持ち越せない。書き加えた 1 文が前の段落の意味を変える場合に、前の段落の候補を確かめ直さない。
- **`<text>` を `--` の前に置く（`<rule> <text> -- <理由>`）。** shiori は `--` の前を規則の並びとして空白でも分けるので、1 つの注記が 2 件に数えられる（shiori 0.2.2 で確かめた）。
- **規則だけで行全体を外す。** 同じ行の別の候補まで、知らせないまま外れる。
- **注記を候補の前の行に置けるようにする。** どの行の候補を外すかの判定が増え、段落の途中に注記だけの行が挟まる。

## Consequences

- 検査器のハッシュの対象に、注記を扱うファイルが加わった。配布の後は、既存の検査記録が一度すべて古くなり、追跡中の文書は check をやり直す。
- 注記で外せるのは、同じ行の候補だけである。行頭に注記を置くと、その行の本文は字下げのコードとして本文から外れるので、注記は行の末尾に置く。
- 短い `<text>` は、同じ行で同じ規則の候補をまとめて外す。
- 注記は同じ行の文字列に結び付く。文の意味が変わっても `<text>` が残っていれば、判断は持ち越される。
- textlint の指摘は、この注記の対象ではない。<!-- ja-check-keep staged-negation -- ではない 範囲の外を示す否定で、言い換えると範囲が分からなくなる shiori: JA-1 -->
- `--` の前を規則 1 語にする書き方は、shiori が `--` の前を規則の並びとして空白でも分ける読み方に合わせたものである。shiori の読み方が変わると、この前提が崩れうる。

## Amendments

### 2026-10-25: dotfiles の注記を shiori の台帳で追い、CI で台帳と比べる

shiori 0.3.0 が Markdown のコメントを読むようになったので、dotfiles の注記を台帳で追うことにした。

- 台帳は `.config/shiori/registry.json`、設定は `.config/shiori/config.yaml` に置く。scan の対象は `**/*.md` と `.skills/**/*.md` である。shiori はドットで始まる場所を、パターンで名前を書かない限り読まない。
- `ja-check-keep` は、設定の独自の指令として読ませる。注記の理由の末尾に `shiori: JA-<番号>` を書き、台帳に同じ番号を、`kind: intentional`（理由のある恒久の除外）で載せる。期限は付けない。残す判断は文の中身に結び付き、日付で古くならないためである。
- CI の「shiori Annotations」が、台帳に無い ref と、文書から消えた ref を落とす（`missing-in-registry` と `unused-in-source`）。この check は必須である。
- CI はリポジトリの mise の設定を読まないので、ダウンロード数の少ないパッケージを通す指定が CI には無い。そのため、mise の設定から node と shiori の版を読み、2 行だけの mise の設定を作って入れる。
- ref の無い注記は、CI では落とさない。shiori 0.3.0 は Markdown のコードの中の書き方の例も候補として読むので、落とすと例のたびに CI が止まる（berlysia/shiori#9）。shiori#9 が直った版に上げたら、ref の無い注記も落とす。この残件は `docs/plans/japanese-check-keep-shiori.md` にある。
- 文書に書き方の例を書くときは、ref に `JA-<番号>` のような置き字だけを使う。shiori はコードの中のコメントも読むので、HTML コメントの形の例に実在の番号を書くと、本物の注記として台帳と比べられる。
