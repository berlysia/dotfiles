# ADR-0041: 使用率と到達予想の 1 行を単体 mod usage-line で出す

## Status

accepted (2026-10-22)

## Context

ccstatusline の 2 行目は、context の割合、5h 枠と週枠の使用率、リセットまでの残り時間を出していた。5h 枠と週枠が 100% に届く時刻の予想は、別リポジトリ llm-dashboard のダッシュボードを開かないと見えなかった。llm-dashboard は、全セッションの使用率を recorder が spool に追記し、その時系列から予想を計算する。

利用者は、dotfiles の単体 mod として作り、llm-dashboard の recorder は変えずに残すと決めた。llm-dashboard を置いていない機械や、recorder が止まっている機械でも行が出ることを求めた。

## Decision

- **K1: 行は `$.state` の値 1 つに置き、`PromptHint` の tail に足して描く。** `$.ui.status` で出した行は、2 セッションでの実機確認で警告マーク付きの黄色に描かれた。そのため `ui.render` の `PromptHint` に hook し、既存の tail があれば空白 2 つを挟んで後ろに足す。行を書き換えれば描き直される。
- **K2: 標本の記録規則は llm-dashboard の recorder と同じにする。** measure のたびに 5h 枠と週枠を拾い、使用率が 0〜100 の有限数で、リセット時刻が日時として読めるものだけを使う。前回の記録と使用率かリセット時刻が違うとき、または前回から 10 分以上経ったときに、窓ごとに 1 標本を足す。
- **K3: 予想は llm-dashboard の予想の関数を移植し、同じ入力に同じ結果を返す。** 変えたのは 2 点だけで、サービスの区別を持たず Claude 固定にしたことと、平均期間を既定値（5h 枠 1 時間、週枠 24 時間）に固定したことである。Claude 固定なので、25 分を超える空白で区間を切る規則は常に掛かる。
- **K4: 履歴は `$.store` にセッションごとの key で持ち、読むときに全 key を連結する。** key は `samples:v1:<session id>` である。値は `[記録時刻 ms, 窓 0/1, 使用率, リセット時刻 秒]` の配列にする。各セッションは自分の key だけを書くので、同時に動くセッションが互いの key を上書きしない。merge は key の辞書順に連結し、記録時刻の昇順に安定ソートするだけにする。値の加工、単調化、重複の排除はしない。llm-dashboard のダッシュボードも、spool の全行を時刻順に並べて予想に渡している。session id は書くたびに読み直し、変わったら新しい key を空から始める。
- **K5: 7 日より古い標本は落とす。** 自分の key は、書くたびに 7 日より古い標本を落とす。セッションの開始時には、`samples:v1:` で始まる key のうち、最新の標本が 7 日より古いものと、読める標本が残らないものを消す。他の版や他の用途の key は読まず、消さない。書き込みが拒まれたら、その回の記録をあきらめて表示は続ける。
- **K6: 他セッションの key は、自分が記録したときに読み直し、10 分に 1 回までに絞る。**
- **K7: 書式は `ctx 34.9% │ 5h 42.9% 100%→14:10 (reset 16:00) │ 週 61.2% 予想 88.7% (reset 木 09:00)` の形にする。** 割合は小数 1 桁へ切り捨てる。こうすると、使用率が 100.0% と出るのは使い切ったときだけになる。時刻は実行環境のローカル時刻で出し、週枠の時刻には曜日を付ける。予想の状態は、各窓の表示を「到達時刻」「リセット時の予想値」「使用率だけ」から選ぶことにだけ使う。リセット時刻を過ぎた窓は出さない。表示している窓の最新標本がどれも 25 分より古いときは、末尾に `HH:MM 時点` を付ける。
- **K8: 表示が古くなる時刻とリセット時刻に timer を張り、行を作り直す。** 張るのは、最新標本が古い扱いになる時刻とリセット時刻のうち、最も早いものである。8 日より先になる時刻は、壊れた入力とみなして張らない。
- **K9: ccstatusline の 2 行目は行ごと消す。** 1 行目（model / git）と 3 行目（session id / cwd）は残す。

## 却下した代替案

- **llm-dashboard の spool を `$.fs` で読み、予想だけを mod で計算する。** 時系列が 1 系統になり、ダッシュボードと数値が必ず一致する。しかし spool は別リポジトリの中にあり、そのリポジトリが無い機械や、recorder が止まった機械では何も出ない。単体 mod という利用者の決定と合わない。
- **ccstatusline のコマンドウィジェットで、spool を読むスクリプトを呼ぶ。** status line を描くたびに外部プロセスが起動し、データは llm-dashboard に依存したままになる。
- **複数セッションの標本を、同じリセット時刻の中で最大値より小さいものを捨てて merge する。** 移植元に無い加工である。表示と予想の出どころが分かれ、補正したときの扱い、使い切ったときの値、timer の時刻に例外規則が連鎖した。止まっていたセッションが古い使用率を記録する事態は、実機確認では起きなかった（Consequences）。起きるようになったら再検討する。

## Consequences

- 時系列は spool と `$.store` の 2 系統になり、予想の関数も 2 か所に置かれる。移植元の変更は手動で追う。移植元と結果が一致するのは、移植した時点の関数に、リセット時刻を秒に切り捨てた同じ入力を与えた場合に限る。記録するセッションの集合が違うので、ダッシュボードとは数値がずれうる。
- 2 セッションでの実機確認の結果は次のとおり。
  - 後から起動した側は先の側の key を読めた。先の側も、次の記録で後の側の key を読めた。両方の key が残った。`$.store` は mod ごとに 1 つのファイルで、プロセス間で共有されていた。
  - 同じ窓のリセット時刻は、2 セッションで秒まで一致した。
  - 片方が止まっている間にもう片方が使用率を進めても、止まっていた側の次の measure は新しい値を報告した。
  - これらが外れるようになったら、spool を `$.fs` で読む補助入力を足す余地がある。
- 他セッションの key 12 個（1 万 8 千標本）を読み直すのに 75〜157 ms かかった（実機、3 回）。50 ms を超えたので、読み直しを 10 分に 1 回までに絞った。他のセッションが記録した標本は、最大 10 分遅れて予想に入る。
- 移植元のテストは既定でサービスを Codex にしており、25 分の空白の規則が掛からない。移植先では常に掛かるため、疎な入力のケースは、同じ傾きの密な入力に置き換えて期待値を保った。移植元と移植先を乱数の入力で突き合わせ、結果が一致することも確かめた。
- 同じ記録時刻の標本が並ぶとき、値が下がらなければ予想の計算は飛ばす。値が下がる並びは、移植元どおり減少として区間を切る。
- 時刻はローカル時刻で出すので、TZ が JST でない機械ではダッシュボード（JST）と表記がずれる。
- `PromptHint` の tail は terminal でしか描かれず、行の端で切れる。リモートコントロールでは見えない。
