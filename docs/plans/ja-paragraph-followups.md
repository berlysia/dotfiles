# ja-paragraph と outline の残件

段落の先頭と末尾の文を抜き出し、骨子と点検の手順を書いた役割 ja-paragraph を足した作業（ADR-0049）のあとに残った課題である。下の節がすべて片付いたら、このファイルを消す。

## 抜き出しを人が読む文字の形で出す

`outline` の出力は JSON だけである。段落ごとに `行番号: 先頭の文 / 末尾の文（n 文）` のような文字の形でも出せると、書き手が点検の材料を自分の目で読める。今は `jq` などで JSON を読む。

## 全角の「．」を文末にする文書

段落の文の分け方は、全角の「．」を文末にしない。追跡している Markdown に「．」を含むものは無いが、HTML から変換した本文などで「．」を文末に使う文書では、段落が 1 文に見える。そうした文書を点検する場面が出てきたら、文末の記号に加えるかを決める。

## 段落の途中の話題の切れ目

先頭と末尾の文からは、段落の途中にだけある話題の切れ目が見えない。点検を使ってみて、見逃しが目立つかを見てから考える。

## 中心文の位置を入口ごとに決める

tanteki と japanese-tech-writing は、どちらも中心文を段落の先頭に置く規則を持つ。ブログや論考のように末尾で締める書き方を入口ごとに認めるかは、利用者が入口ごとに決める。認める入口が出たら、その入口の規則として足す。

## 他動詞の連用形を名詞として使う文を見つける

「koncise は段落の組み立てを持たない」は不自然だが、「重ね方と段落の組み立ての 2 つの関心を持つ」は自然に読める。同じ「段落の組み立て」でも、物のように持つ・支える対象にすると不自然になる。連用形名詞を調べた論文は、他動詞から来た連用形名詞は名詞としての自立性が弱く、連体修飾節の中で使いにくいと述べている（例「*資金の集めが悪い」）。読めたのは抄録だけである。

語の形は文によって自然にも不自然にもなるので、直訳語の一覧の正規表現では拾えない。使う道具は、japanese-check の語の契約の述語（`isNoun`、`isVerb` など）と、活用の種類から連用形を作る `renyokei` である。これで「名詞＋の＋他動詞の連用形の名詞」を見つけ、直後に「を持つ」「を持たない」「が無い」「を支える」のような述語が続くときに候補を出す規則が考えられる。直し方は「組み立て方」のように「〜方」を付けるか、動詞のまま書く。

作るかどうかは、次の 2 つを確かめてから決める。

- lindera-unidic が「組み立て」のような語を名詞として返し、`renyokei` で作った連用形と全体で一致するか（他動詞かどうかは、契約の活用の種類だけでは分からない）
- 追跡している Markdown で候補がいくつ出て、そのうち何件が誤検出か。誤検出が多いと、候補の行が読まれなくなる

## long-sentence が閉じ括弧を別の文に切る

`long-sentence` は行ごとに `/[^。！？!?]+[。！？!?]?/gu` で文に分けるので、「はい。」」の `」` を別の文として切る。今は長い文の検出にしか使っていないので実害は小さいが、文の数を使う処理を足すときは `splitSentences` の分け方にそろえるかを決める。
