# 日本語の形態素解析器をどれに寄せるか

日本語の文章の検査で、形態素解析器が 2 つ使われている。japanese-check は npm の `sudachi@0.1.5`（WebAssembly 版）を使い、tanteki の独自の textlint ルールは kuromojin を使う。どちらかに寄せるか、別の解析器に入れ替えるかは、まだほとんど決まっていない。

決めることは次の 3 つである。

- 寄せる先の解析器。今の 2 つのどちらかか、別のものか
- 寄せる範囲。japanese-check だけか、tanteki のルールも含めるか。tanteki は上流から派生したスキルなので、ルールを書き換えると上流との差が広がる
- 寄せる前に何を比べるか。語の区切り、品詞、正規形が変わると、検出規則の結果が変わる

## 比べる材料

ADR-0050 で、kuromoji で照合していた語の規則を、Sudachi で照合する japanese-check の一覧に移したときに、次のことが分かった。

- **語の区切りと原形**: kuromoji は、名詞として使う連用形を動詞の原形に戻す（突き合わせ → 突き合わせる、見落とし → 見落とす、効き → 効く、疑い → 疑う）。複合語も細かく割る（事故＋る、穴＋掘り、焼き＋直す、実測＋値）。Sudachi（モード C）はこれらを名詞や 1 語として返すので、原形で照合すると検出できない。移した語では、こうした項目を語幹の正規表現にして取り漏らしを防いだ
- **kuromoji の細かい区切りによる誤検知**: 廈門を「廈＋門」、自走を「自＋走（走る）」、ゲートウェイを「ゲート＋ウェイ」に割る。旧の規則は、これらを誤って検出していた
- **速さ**: 同じ 7,406 行（34 万字）を 1 行ずつ渡すと、Sudachi（WebAssembly 版、モード C）は 557 秒、kuromoji は 1 秒だった。別の処理が CPU を 1 つ使っている間に続けて測った値で、遅さの原因（呼び出しごとの初期化か、WebAssembly 版そのものか）は確かめていない
- **Sudachi のモード A**: 今の呼び出し方では空の結果を返した。値の対応の問題とみられるが、確かめていない
- **原文の位置への対応**: 半角カナの濁点（ｶﾞ）を含む行では、Sudachi のトークンを原文の位置に戻せない。そのため check が止まる（`docs/plans/japanese-check-detection-followups.md`）

決めるときは、今の解析器を前提にした残件も見直す。`docs/plans/ja-paragraph-followups.md` の「他動詞の連用形を名詞として使う文を見つける」は、Sudachi の品詞を使う前提で書いている。
