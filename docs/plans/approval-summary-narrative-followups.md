# 承認依頼の 5 項目（ADR-0035）の持ち越した確認

ADR-0035 で、承認依頼の Executive Summary を「前提 → 目指す状態 → 今の状態 → やり方 → 確かめ方」で始める書式にした。導入時に試せたのは単層 plan.md の承認依頼だけで、spec 層と plan-N 層ではまだ試していない。

## 二層モードでの実地確認

次に spec + plan-N で承認を依頼するとき、次の 3 点を見る。

- plan-N.md の「目指す状態」（担う K の完了像）が、親 spec の K から 1-2 行で写せるか。
- spec.md の「確かめ方」が、選んだ品質特性だけで読み手に伝わるか。
- 5 項目を読んだ利用者が、追加で質問せずに、なぜ・どこへ・どこから・どうやって・どう確かめるかを把握できたか。

利用者が追加で説明を求めた場合や、項目が羅列になって流れが読めないと言われた場合は、次を見直す。

- K1: ラベル付きの箇条で書く
- K2: 層ごとの出どころ

**消す条件**: spec 層と plan-N 層で 1 回ずつ承認を依頼し、3 点とも問題がなかったとき。問題があれば、見直しの内容をここに書き足す。

## 記憶を前提にしない要約の実地確認

ADR-0035 の 2026-10-23 の改訂（読み手は何も覚えていないと仮定する）が効いたかを、変更前の集計と同じ基準で数える。数値は計画で決めた目安であり、統計的な判定ではない。

- 起点: 改訂の commit が master に入った日（`git log` で導出する）
- 母集団: 起点から 30 日の DW session の承認の質問。30 日で承認しなかった件が 30 件に満たなければ、30 件に達するまで延ばす（変更前の分母 47 件に近い数にする）
- 分類: 説明し直しの要求は、変更前の集計と同じ基準で数える。承認の質問への返答のうち、承認せずに要約の中身の説明を求めたものである（例「つまりどういうこと」「読んでもわからん」）
- 指標:
  - 承認しなかった件のうち、説明し直しの要求の割合（変更前は 12/47 = 26%）
  - 要約の長さの中央値（変更前は約 2,000 字）
  - 「冗長だ」「長い」という反応の件数
  - 3 型（差分だけ・ID だけ・理由なし）の出現件数
- 分け方: 要約の前に `ask-approval` が走った流れと、要約が先の流れ（変更前は 92% / 8%）を分けて記録する。母数が小さいので、判定は全体の割合だけで行う
- 判定:
  - 説明し直しの割合が 15% 未満（変更前のおよそ 4 割減）なら、効果ありとしてこの節を消す
  - 20% 以上（変更前との差が母数の揺れと区別できない水準）のままなら、workflow.md を最小版（原則と `ask-approval` を読む順だけ）に戻すかを利用者に諮る
  - 15〜20% なら、期間を 30 日延ばして同じ基準で数え直す
  - 「冗長だ」という反応が承認 10 件に 1 件を超えたら、前提の 4 段の無条件の適用を見直す
- 範囲の外の課題:
  - 注記を読んでから質問を出すまでに文書を直すと、記録が質問を拒否する。今の記録の確認の注記で回復できるので、workflow.md には足していない
- 別計画の候補: ID の定義を `ask-approval` が文書から機械で展開する。着手の条件は、実地確認で ID だけの型が残り続けたとき

**消す条件**: 判定で効果ありとなり、この節を消したとき。20% 以上で最小版に戻す判断が済んだときも消し、判断を ADR-0035 の Amendments に書く。範囲の外の課題と別計画の候補は、節を消す前に残す価値があれば別の節に移す。
