# plan 層の重さの見直し（一部決着）

ADR-0032 で、plan にテストと実装のコード本体を書かないと決めた。plan に書くのは契約・不変条件・テストケース（入力 → 期待）とタスクの分割で、レビューもその抜けを見る。下位モデルへの委譲は、契約とテストケースが確定していることを条件にし、plan に無い判断を worker に報告させる。下の「未解決の設計判断」のうち 1 つ目と 4 つ目はこれで答えた。承認の単位とレビューの時期は残っている。

## ADR-0032 の後に観察すること

- 新しいテンプレートで書いた plan の行数とレビューのラウンド数。ADR-0032 の集計では、指摘の多くが契約と不変条件だった。変更後にこの種類の指摘が減っていないかを見る。
- 書き捨てのスクリプト（集計・調査）の依頼で、レビュアーや logic-validator が起動しないか。削除を伴うスクリプトが通常の routing に乗るか。
- worker が「plan に無い判断」をどれだけ報告し、そのうちメインループが差し戻したものがあるか。

## 問い

Document Workflow の plan は、実装とほぼ同じ水準まで書かれている。そこまで書くなら、plan を書かずに実装した方がよいのではないか。

plan を commit しなくなったので、plan はリポジトリを膨らませない。残る費用は、plan を書く時間、レビューが読む量、承認する人が読む量である。

## plan が担っている役目

plan をやめる、または軽くする場合、次の役目の置き場を決める必要がある。

| 役目                                 | 根拠                                                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 人間が書き込みの前に承認する単位     | gate は、承認済みの plan の Files に載ったパスへの書き込みを通す                                           |
| 保護対象への書き込みを人間が見る機会 | ADR、規則、skill への書き込みは委任できず、plan の承認が要る                                               |
| 下位モデルへ渡せる粒度の指示         | `rules/model-offloading.md` は、plan が確定していることを委譲の条件にしている                              |
| 実装の前に誤りを見つける場           | plan のレビューが、設計の見落とした参照を実装の前に見つけた例がある                                        |
| 計画から外れた点の基準               | 「記録を移す」タスクは、plan と実際の差を中身で振り分ける（決定の変更と、帰結として残る制約だけを ADR へ） |

## 未解決の設計判断

- 承認の単位を何にするか。候補は、今のまま plan、spec だけ（差分は PR で見る）、Files と判定基準だけの短い plan、の 3 つ。
- レビューをいつ行うか。plan に対して行うのか、実装した差分に対して行うのか。
- どの種類の作業に当てるか。文書の書き換えが中心の作業では plan の大半が書き換えの表と全文だったが、コードを書く作業でも同じことが言えるかは、確かめていない。

## 確かめていないこと

- plan を書く時間と、実装の時間の比。下位モデルによる実装の側の時間は測ったが、plan を書いてレビューを通すのに掛かった時間は測っていない。
- plan のレビューが見つけた誤りのうち、実装した差分のレビューでも見つかったはずのものの割合。
