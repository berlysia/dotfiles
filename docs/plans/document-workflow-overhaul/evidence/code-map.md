## 4. `cc-hooks-ts` runtime semantics

Deployed version at `~/.claude/node_modules/cc-hooks-ts` is **2.1.238**; repo's declared dependency (`home/dot_claude/package.json`) is **2.1.251** — a version gap exists between what's committed and what's actually running until the next `chezmoi apply` + `bun install`. **`createContext` (dist/index.mjs:61-88)** — what each `context.*` method actually returns:

```js
function createContext(input) {
  return {
    defer: (handler, options) => ({
      kind: "json-async",
      run: handler,
      timeoutMs: options?.timeoutMs,
    }),
    blockingError: (error) => ({ kind: "blocking-error", payload: error }),
    input,
    nonBlockingError: (message) => ({
      kind: "non-blocking-error",
      payload: message,
    }),
    success: (result) => ({
      kind: "success",
      payload: {
        additionalClaudeContext: result?.additionalClaudeContext,
        messageForUser: result?.messageForUser,
      },
    }),
    json: (payload) => ({ kind: "json-sync", payload }),
  };
}
```

**`handleHookResult` (dist/index.mjs:485-529)** — what happens to each `kind` at process-exit time:

```js
case "blocking-error":
    if (hookResult.payload) console.error(hookResult.payload);
    return process.exit(2);
...
case "json-sync":
    console.log(JSON.stringify(hookResult.payload.output));

case "non-blocking-error":
```

**Answers to the specific questions:**

1. **PreToolUse deny**: `document-workflow-guard.ts` calls `context.json(createDenyResponse(reason))` → `kind: "json-sync"` → `console.log(JSON.stringify(payload.output))`, `process.exit(0)`. The JSON body (`{hookSpecificOutput:{hookEventName:"PreToolUse", permissionDecision:"deny", permissionDecisionReason: reason}}`) is what Claude Code's harness parses to block the tool call — **not** `messageForUser`/`systemMessage`. `permissionDecisionReason` is what reaches the model as the deny explanation.

2. **PostToolUse `additionalContext`**: `plan-review-automation.ts` calls `context.json({event:"PostToolUse", output:{hookSpecificOutput:{hookEventName:"PostToolUse", additionalContext}}})` — same `"json-sync"` path, printed as JSON to stdout. Claude Code's harness reads `hookSpecificOutput.additionalContext` and injects it into the model's next-turn context (this is the channel the hooks README, quoted below, calls out as reaching the model).

3. **Stop `decision:"block"`**: `resume-incomplete-work.ts` calls `context.json({event:"Stop", output:{decision:"block", reason}})` — again `"json-sync"`, `console.log(JSON.stringify({decision:"block", reason}))`, `exit(0)`. Claude Code's harness reads top-level `decision`/`reason` (not nested under `hookSpecificOutput` for Stop) to block the stop and feed `reason` back to the model as why it must continue.

4. **`context.success({messageForUser})` reaching the model — it does NOT, for PreToolUse/PostToolUse/Stop.** Per the `"success"` case above: for `UserPromptSubmit`/`SessionStart` only `additionalClaudeContext` is printed (and `messageForUser` is silently dropped even if set); for **every other event** (`PreToolUse`, `PostToolUse`, `Stop`, etc.), only `messageForUser` is printed via plain `console.log`, and `additionalClaudeContext` is dropped. Plain stdout on a PreToolUse/PostToolUse/Stop hook is **not** structured JSON, so Claude Code's harness does not parse it as a decision — but per `home/dot_claude/hooks/README.md` (lines 174-179) and `session.ts`'s inline comment (lines 255-262), plain stdout **is** attached to the model's context as a `hook_success` attachment for at least some events, while `systemMessage` (only reachable via `context.json`) shows in the UI but never reaches the model. **This last distinction (`hook_success` attachment vs. `systemMessage`) is asserted from real-binary testing referenced in `docs/plans/hook-target-diagnostics-followups.md` "課題 A", not directly visible in the `cc-hooks-ts` library source itself** — the library only decides what gets printed to stdout; Claude Code's own hook-output parser (outside this repo) decides what printed stdout does afterward. Treat this boundary as the one place where library source and CLAUDE.md/session.ts's runtime claims must both be checked, since they describe two different layers (library formatting vs. harness consumption).

Records **deferred** improvements from a 13-item feedback list (P1-P13), of which 7 were **adopted** in the originating session (P1 code-reference field, P3 test-fixture-sharing convention, **P9 PreToolUse self-audit** = `spec-plan-self-audit.ts`, **P10 PostToolUse placeholder grep** = `spec-plan-placeholder-scan.ts`, **P12 lessons-learned auto-inheritance (lightweight MVP)** = `lessons-learned-extractor.ts`, P13 Phase-1-non-provided format). ## 6. ADR-0001 & ADR-0003 summary

- **ADR-0001** (`docs/decisions/0001-document-workflow.md`, accepted 2026-02-18): Fixed the decision to adopt Document Workflow instead of Plan Mode (Plan Mode's ExitPlanMode-only single-shot verification and read-only constraint made iterative annotation impossible). Fixed: `session.ts` auto-sets `DOCUMENT_WORKFLOW_DIR`; flow is research→plan→annotation→approval→implementation; `plan-review-automation` auto-reviews on plan.md edits; `document-workflow-guard` blocks pre-approval implementation; approval is human-only. **Amended by ADR-0013** (2026-09-04): the "session.ts auto-sets the env var and it reaches PreToolUse" mechanism was found not to actually deliver the value to the hook process; ADR-0013 moved workflow-dir resolution to session-id derivation (`workflow-resolve.ts`) with env demoted to a verified override. - **ADR-0003** (`docs/decisions/0003-document-workflow-enforce.md`, accepted): Fixed the migration from `DOCUMENT_WORKFLOW_WARN_ONLY=1` (warn-only rollout) to enforce mode, based on a warn-only period showing zero false positives (19 unit tests passing) — left open/kept: the `DOCUMENT_WORKFLOW_WARN_ONLY` code path itself remains in `document-workflow-guard.ts` (`warnOnly` check, guard lines 93/153/193) for future staged rollouts elsewhere. **Amended by ADR-0013**: enforce mode had implicitly assumed the env var reached the hook process, but it only reached Bash execution environments — sessions that didn't explicitly pin the var saw the guard silently no-op (measured: zero denies from 2026-07-28 onward). The "enforce" decision itself is unchanged; only the delivery-mechanism assumption was corrected.
