# 残件の入口の作業から持ち越した課題

ADR-0030 の作業（2026-10-07）が、範囲の外に回した課題である。
決定は `docs/decisions/0030-followups-written-when-raised.md` にある。

## 1. 「記録を移す」手順の見直し

- **内容**: 計画の最後のタスクが記録を移す手順を、表の行ごとの行き先の記入から、原本の見出しごとの照合へ見直す。
- **分かっていること**:
  - ADR-0029 の 1 回目の移し替え（`43e1949`）は、research の「未確認」の節と、plan にあった検証のコマンドを落とした。2 回目（`caaa4fa`）で足した。
  - 漏れに気づいたのは、commit の本文に書いた原本の見出しの一覧を、1 つずつ「どこへ行ったか」と突き合わせたときである。
  - 表の行ごとに行き先を書く手順では、行に当たる内容を狭く読むと漏れる。
  - 検証のコマンドは「移さない」行（Tasks）の中にあった。ADR の別の文がそれを参照していたので、要ると判断した。
  - 事例はこの 1 件だけである。手順を足すと、今後のすべての作業の終わりに費用が掛かる。
- **未決**: 見出しごとの照合を、毎回の作業に足すかどうか。

## 3. commit を指す参照と、取り込み方の制約

- **内容**: ADR が commit の hash を参照として書く運用（ADR-0029 K4）は、hash を書き換える取り込み方と両立しない。取り込み方の制約を、規則か設定にするかを決める。
- **分かっていること**:
  - 壊れるのは、取り込む前の PR の中の commit を指す参照である。squash と rebase は、その commit を master の履歴に残さない。既に master にある commit を指す参照と、PR 番号は、取り込み方に関係なく残る。
  - リポジトリの設定は、merge commit が可、squash が可、rebase が不可である（`gh api repos/berlysia/dotfiles`、2026-10-07）。squash は止められていない。
  - auto-merge は有効で、マージしたブランチは自動で消える設定である（同）。ADR に書いたブランチ名は、マージの時点で辿れなくなっていた。
  - ADR-0029 の Context は「直近 40 件に squash merge は無い。commit を指す参照は、この運用が続く限り辿れる」と観察を書くだけで、制約としては決めていない。
- **未決**:
  - squash を設定で止めるか、規則の文に書くか、PR の中の commit を参照に書かない（PR 番号で指す）と決めるか。
  - 依存の更新の bot が auto-merge で使う取り込み方は、確かめていない。squash を止める前に確かめる必要がある。
