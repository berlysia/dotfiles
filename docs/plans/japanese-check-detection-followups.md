# japanese-check の検出を広げる残件

直訳語の一覧から字義どおりの「届く」と動詞の「写す」を外した作業（#396）のあとに残った課題である。下の節がすべて片付いたら、このファイルを消す。

## 語の置き場

語の置き場は、japanese-check の一覧（`home/dot_claude/japanese-check/data/words.json`）に決まった（ADR-0050）。名指しの直訳語は `action: fix` の項目として hook と check が、名指しでない語は `action: review` の項目として check が照合する。

- 調べた資料の語は、この一覧に足す
- `no-ai-words` の辞書の語（「入口」「土台」「事故」「既定」「定石」「効く」「静か」）は、もう一覧にある。資料から足すのは、辞書に無い語（別物、要点など）と文書の構成の型である

## 文書ごとに用語を宣言して、その語の候補を外す

提案・未決。

- **内容**: 名指しでない語には、このリポジトリの用語（検査、照合、走る、経路、ゲート）も入れた。用語を多く使う文書では、直すたびに用語の候補が数十件並ぶ。
- **分かっていること**: ADR 52 本と ja-check の SKILL.md に check をかけると、1 文書あたりの候補の中央値は 6 件だった。多いのは ja-check の SKILL.md（67 件）、ADR-0036（51 件）、ADR-0023（50 件）で、ほぼすべてが用語だった（ADR-0050）。keep の印は行ごとで、このリポジトリでは shiori の台帳の番号も要る。
- **再開の入口**: 文書の中で 1 回だけ「この文書ではこれらの語は用語」と書き、その語の候補を外す仕組みを考える。宣言した文書では比喩として使った用法まで外れるので、取り漏らしとの引き換えになる。書き方、範囲、ゲートと keep の印との関係を決めるので、着手するときは Document Workflow を通す。

## 調べた資料から検出の型を加える

提案・未決。

- **内容**: AI が書いた日本語の特徴を調べた資料から、japanese-check に加えられる型が3つ見つかった。
  - 文書の構成の型（導入、本論、結論の三段構成、「まとめると」「本稿では」のような自分の構成への言及、最後を一般論や呼びかけで締める結び）
  - 役割や位置を場所や物にたとえる語（「入口」「土台」「事故」「既定」「別物」など）
  - 評価の名詞で文を締める型（「〜が定石です」「〜が要点です」）
- **分かっていること**:
  - 構成の型は、Open Data Lab の報告（長井、2026-07、[PDF](https://odl.or.jp/wp-content/uploads/2026/07/Detection-of-Generative-AI-Derived-Structural-Characteristics-in-Japanese-Documents-and-Support-for-Their-Improvement.pdf)）で、AI の文 50 本と人の文 15 本の発火率の差が大きかった（三段構成 44% 対 6.7%）。この型は正規表現では検出できない。同じ報告は、ローカル LLM に有無を判定させている。
  - 物にたとえる語と評価の名詞で締める型は、逆瀬川の Qiita の集計（[記事](https://nyosegawa.com/posts/qiita-writing-before-after-ai/)）から来ている。どちらも、AI 以前に比べて急増した語から選んだ。この集計は、AI が書いた記事の増加と人の書き方の変化を区別していない。`japanese-tech-writing` の SKILL.md は、すでにこの2つを文章の規範として持っている。
  - 同じ報告は、通説から作った語の規則のうち 4 つが人の文への誤検知だったと書いている。
- **再開の入口**: 型ごとに、AI 以前の人の文（Qiita 2019〜2021 の記事など）で誤検知しないかを測ってから加える。構成の型は、検査器に LLM の判定を持ち込むかどうかの設計判断を含むので、spec から Document Workflow を通す。
